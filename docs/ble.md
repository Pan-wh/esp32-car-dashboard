# BLE 数据源（iPhone Core Location → 仪表）

改造方向见 `archive/AI_TASK_IPHONE_BLE_DASHBOARD.md`。本机**无板载 LC76G GNSS**
（原理图网表证实无 GPS 的 SDA/SCL 网络），故速度/航向/时间改为 **iPhone Core Location 经 BLE 下发**。

## 导航消息（阶段 2，2026-10-13）

### 设计取向

参考开源项目 [moto-gps-waveshare](https://github.com/mx3353672833-debug/moto-gps-waveshare)
的**字段取舍与分层思路**（它验证了哪些字段真正必要、哪些是冗余），
但**沿用本项目既有的 JSON 风格**，不采用它的二进制帧（magic/CRC/分片/会话）：

| 取舍 | 理由 |
|------|------|
| 不引入二进制帧 | 我们已有可单测的稳定 JSON 解析器；512 B 重组上限内二进制收益有限，却要两端同时改造并丢掉现有测试覆盖 |
| **不引入字符串字段** | 用户决策不显示路名 → 省掉中文字体（Flash）与解析器改造 |
| 复用 Telemetry 特征 | 用 `"t":"nav"` 与遥测分流，不新增特征与订阅流程 |

> ⚠️ **许可证提示**：moto-gps 采用 PolyForm Noncommercial（非商业）。
> 本项目**只参考其设计**，未复制其代码。

### 消息格式

与遥测**同一特征**（`7D2A0002`，Write）下发，用 `t` 字段区分：

```json
{"t":"nav","state":1,"maneuver":2,"dist_m":500}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `t` | string | **必填**，固定 `"nav"`。遥测包无此字段（或 `t":"tel"`）|
| `state` | int | 导航状态，见下表。越界 → `5`(无数据) |
| `maneuver` | int | 转向动作，见下表。越界 → `0`(未知) |
| `dist_m` | int \| null | 距下一转弯距离（米）。`null` 或超范围 → 无效（显示 `--`）|

**导航状态**：`0` 未开始 / `1` 导航中 / `2` 重新规划 / `3` 已到达 / `4` 数据过期 / `5` 无数据

**转向动作**：`0` 未知 / `1` 直行 / `2` 左转 / `3` 右转 / `4` 掉头 / `5` 靠左 / `6` 靠右 / `7` 到达

### 容错语义（重要）

| 情况 | 行为 |
|------|------|
| 字段**缺失** | **保留旧值**（不因缺字段清空显示）|
| 字段为 `null` | **明确无效**（与缺失语义不同）|
| 解析失败 | **完全不改动状态**（原子性）—— 畸形包不会让仪表闪回"无数据" |
| 未知字段 | 忽略（**向前兼容**，未来加字段不破坏旧固件）|
| 越界枚举值 | 钳制到安全值（动作→未知、状态→无数据），绝不越界访问 |

### 过期与断连

| 事件 | 行为 |
|------|------|
| BLE 断开 | **立即**置为"无数据"（不等超时）|
| 10 秒无更新 | 置为"数据过期" → **停止显示旧指引**（§6.3 安全原则）|

> 过期阈值 `NAV_STALE_MS = 10s`，**远长于遥测的 2.5s**：导航数据变化慢
> （一次转弯可能几分钟），用遥测阈值会频繁误报过期。

### 调试

```bash
# 通过 BLE 下发（⚠️ 必须指定 telemetry，否则写到 Command 特征）
swift tools/ble_command_test.swift '{"t":"nav","state":1,"maneuver":2,"dist_m":500}' telemetry

# 或用串口直接喂模拟数据（不依赖手机）
nav 1 2 500 68
```

## 地图窗口消息（阶段 4，2026-10-14）

### 设计取向

让圆屏能画出"眼前的路"（灰路 + 灰楼 + 白路线 + 固定车头箭头，航向朝上），
这类界面需要**周边几何数据**。做法沿用参考项目的分工（**设计参考、代码自写**，
见 [decisions.md](decisions.md) D-009 / D-010）：

> **手机/网关持有地图数据，只把当前位置附近约 500 米的几何窗口发给设备。**
> 设备不保存整座城市的地图，也**不做任何经纬度/墨卡托运算**。

### 为什么不分片（重要设计决定）

窗口数据约 2.2 KB，超过 BLE 单包（iOS 实到约 185 字节）。但**不引入分片层**：

**一条道路 / 一栋建筑 / 一段路线各发一条独立消息**，每条都远小于单包上限。
这样可以直接复用既有的"文本消息 + 攒到 `}` 就解析"通路，
固件只需在分流处多认几个 `t` 值，无需新增重组、序号、CRC 逻辑。

代价是写入次数变多（约 40 次 vs 12 次）。但**窗口只在移动约 100 米后才更新一次**，
且每次都是小包，可接受。

### 消息格式

```json
{"t":"mw"}                                        窗口开始
{"t":"mr","c":3,"p":[[134,-4],[25,-3],[7,-1]]}    一条背景道路
{"t":"mb","p":[[10,20],[30,20],[30,40]]}          一栋建筑轮廓
{"t":"mp","p":[[0,0],[12,-30],[40,-60]]}          路线折线（白色粗线）
{"t":"me"}                                        窗口结束（此刻才切换显示）
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `t` | string | `mw`=窗口开始 / `mr`=道路 / `mb`=建筑 / `mp`=路线 / `me`=窗口结束 |
| `c` | int | **道路等级**，见下表（仅 `mr`）|
| `p` | array | 点序列 `[[x,y],…]`，**局部米坐标**（见下）|

**道路等级 `c`**（与网关 `mapwindow.js` 的映射一致，数值越小越主要）：

| c | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 含义 | 高速 | 主干 | 次干 | 支路 | 辅路/服务 | 其它 |

### 坐标系（**关键约定**）

- 坐标是**以窗口中心为原点的局部米坐标**：`x` 向东为正，`y` 向北为正
- 量程 ±1500 m（半径上限），**int16 足够**
- **投影由网关完成**，设备端只需"**按航向旋转 + 缩放 + 平移**"
- 窗口中心是**手机发起请求时的位置**，不是车辆当前位置

### 自车位置：`nav` 消息新增 `ox` / `oy`

窗口中心与车辆当前位置不重合（车辆在动）。为了让设备**不必做坐标换算**，
`nav` 消息新增两个字段，表示**车辆在窗口局部坐标系中的偏移（米）**：

```json
{"t":"nav","state":1,"maneuver":2,"dist_m":500,"ox":13,"oy":-42}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `ox` / `oy` | int \| null | 自车相对**窗口中心**的偏移（米）。无窗口时省略或为 `null` |

设备据此把地图整体平移 `(-ox,-oy)`，使自车始终落在屏幕中心的固定箭头上。

### 更新时机与原子性

- 手机在**移动超过 100 米**、或距上次更新超过 **15 秒**、或路线重算后重新请求窗口
- 设备把 `mw…me` 之间的消息**累积到"待用缓冲"**，收到 `me` 才整体切换 ——
  避免画面出现"画了一半"的中间态
- **超时丢弃**：`NAV_MAP_BUILD_TIMEOUT_MS = 5000`（5 秒）**内一条地图消息都没收到**才丢弃本次累积
  （视为传输中断）。这是**「无消息」计时**：从**最后一条消息**重新起算，
  **不是**从 `mw` 起算 —— 逐条应答的正常传输不会因窗口总量大而被误判
- 窗口**过期**：超过 60 秒未更新则视为过期（手机断连 / 无网），此时隐藏地图层，
  保留路线与转向提示（那部分仍来自 `nav` 消息）

### 预算（决定 BLE 可承载）

对齐参考项目的窗口量级，网关侧已强制：

| 项 | 上限 |
|----|------|
| 背景道路 | 24 条 / 192 点 |
| 建筑 | 16 栋 / 128 点 |
| 路线折线 | 96 点（设备侧上限）|

### 署名义务（必须保留）

地图数据来自 **OpenStreetMap（ODbL 1.0）**，瓦片由 **OpenFreeMap** 提供。
界面或"关于"页必须提供可见的 `© OpenStreetMap contributors` 与许可链接
（见 [decisions.md](decisions.md) D-010）。

## 遥测协议（版本化 JSON，v=1）

```json
{
  "v": 1,
  "ts_utc_ms": 1791765900000,
  "speed_mps": 19.03,
  "speed_accuracy_mps": 0.8,
  "latitude": 1.3521,
  "longitude": 103.8198,
  "horizontal_accuracy_m": 5.2,
  "course_deg": 120.0,
  "location_valid": true,
  "speed_valid": true
}
```

规则：
- `ts_utc_ms` = UTC Unix epoch 毫秒（不传本地格式化字符串作为唯一时间源）。
- `speed_mps` 米/秒；仪表换算 `km/h = m/s × 3.6`。`< 0` 视为无效（`speed_valid=false`）。
- `course_deg` 地面行进方向 0..360（不是磁罗盘）；无有效值传 `null` 或缺省。
- 经纬度/精度可为空（传 `null`），**不得伪装成 0**；缺省字段以 `has_*` 标志区分。
- 缺省 `speed_valid`/`location_valid` 为 false（保守）。
- 解析器 `simulator/ui/telemetry.{c,h}`（纯 C，107 项单测），只解析受控扁平 schema，不做通用 JSON。

## MTU 与分包

- ESP32 侧请求 MTU 247；iOS/macOS 实际协商约 185，故完整 JSON（~200 字节）会**跨多个 BLE 包**。
- 固件在 `ble_telemetry.cpp` 里做**重组**（累积到 `{...}` 完整后再解析），实测 203 字节能正确重组解析。
- 若后续字段继续增多，优先**收紧包体**或改用紧凑二进制协议（见任务书 §4）。

## 数据质量与校验（§5.4 / §7）

分两层，职责不重叠：

1. **iOS 侧质量门槛（§5.4）** —— `ios/.../TelemetryQuality.swift`，阈值集中可调：
   - `maxHorizontalAccuracyMeters = 50`：水平精度差于此 → `location_valid=false`
   - **测速精度门槛按速度分档**（iOS 17+ `speedAccuracy`）→ `speed_valid=false`：

     | 速度档 | 阈值 |
     |--------|------|
     | 低速 < 10 km/h | `±5.0 m/s` |
     | 中速 10–40 km/h | `±2.5 m/s` |
     | 高速 ≥ 40 km/h | `±2.0 m/s` |

     **为什么分档**（2026-10-16 真机问题驱动）：GPS 测速是**位置差分**，
     误差 ∝ `位置误差 / 采样间隔`，与速度强相关 —— 低速时相对误差爆炸。
     原先用固定 `2.0`，导致**起步/堵车时几乎必然被拦**，仪表频繁从 LIVE
     掉到 `--`；而高速时反而正常。用户看到的现象是"速度质量经常被拦，
     定位质量却通过"（两者是 iOS 给的独立指标，不同步是常态）。
     任务书 §5.4 也早已指出：*"低速时 GPS 速度可能跳动"*。

     **为什么不干脆放大成一个更大的固定值**：那会让高速时把漂移当真实
     车速（表显 80 实际 60），**比显示 `--` 更危险**。故低速放宽、高速保持严格。

     `speedAccuracy < 0` 表示 iOS 未提供精度估计，此时**放行**（总比全拦好）。
   - 判定结果写进 `location_valid`/`speed_valid`，**仪表端不需要重复这套业务规则**
2. **固件侧兜底校验（§7）** —— `telemetry_plausible()`（纯 C，含单测）拒绝超范围/自相矛盾：
   - 速度 > `TELEMETRY_SPEED_MAX_KMH`(400) 或 < -1 m/s 语义矛盾
   - 航向越界、经纬度越界、精度为负、`location_valid` 却无经纬度
   - 被丢弃的包计入 `不合理` 计数并在串口打印，**不驱动 UI**

> 实测：正常包接受（54 km/h）；720 km/h 与纬度 95 的包均被丢弃并计数。

## 速度平滑（§5.4「轻量平滑但必须限制滞后」）

固件用 `telemetry_ramp_*()`（纯 C，含单测）按真实经过时间推进指针：

| 规则 | 原因 |
|------|------|
| 加速约 `450ms` 到达目标 | 覆盖手机约 2Hz 的数据间隔，避免走走停停 |
| 减速约 `250ms` 到达目标 | 刹车读数更快下降 |
| 每帧按 `dt_ms` 插值 | 动画速度不依赖主循环调用次数 |
| 无效/超时/断连 → 立即重置为 0 | 遵守「不显示旧值」核心原则 |

旧 EMA 方案会在 2Hz 数据源下呈现阶梯运动，已删除；原因与性能数据见
[`troubleshooting.md`](troubleshooting.md) 和 [`perf/README.md`](perf/README.md)。

## 线程与数据过期

- BLE 写回调运行在 BLE 任务，只在回调里**解析+加锁入库**（`FreeRTOS` 互斥量 `s_mtx`），不触碰 LVGL。
- 主循环 `ble_poll()` 取数 → 推 `ui_speed_set_*`；`ble_check_stale()` 超过 `BLE_STALE_MS`（2500ms）
  无有效遥测即**把速度置无效**（不残留旧值）。
- 速度有效定义：`speed_valid && speed_mps >= 0`。

## Status 特征（Read/Notify）

固件在校时等状态变化时 `ble_telemetry_set_status()`，App 可读可订阅。实测（`tools/ble_status_test.swift`）：
属性 `0x12`(=Read|Notify)；读回 `"time-synced"`；写入遥测触发校时后收到 Notify ✓

## 设备控制（下行命令特征）

功能①：亮度 / 息屏，以及为多表盘（功能③）预留的切换命令。

| 项 | 值 |
|----|-----|
| 服务 | `7D2A0001-8F4A-4B7C-9D21-5E6A3B8C1000` |
| Command 特征 | `7D2A0004-8F4A-4B7C-9D21-5E6A3B8C1000`（Write）|

命令格式（JSON，扁平结构）：

```json
{"cmd":"brightness","value":128}   // 亮度 0-255
{"cmd":"screen","value":"off"}     // 息屏（也接受 value:0）
{"cmd":"screen","value":"on"}      // 亮屏（也接受 value:1）
{"cmd":"face","value":2}           // 切表盘：直接指定 id
{"cmd":"face","value":-1}          // 下一个表盘
{"cmd":"face","value":-2}          // 上一个表盘
{"cmd":"rotate","value":90}        // 屏幕方向 0/90/180/270（度）
{"cmd":"face_enabled","value":3,"on":0}   // 隐藏表盘 3（on 也接受 "on"/"off"）
{"cmd":"face_enabled","value":3,"on":1}   // 启用表盘 3
{"cmd":"demo_speed","value":45}           // 演示车速 45 km/h（App「模拟速度测试」滑块）
{"cmd":"demo_speed","value":-1}           // 退出演示（value < 0 即退出）
```

`demo_speed` 是**调试/演示**用途（无真实遥测时看动画），安全语义如下：

| 项 | 行为 |
|----|------|
| 状态标识 | 仪表状态行显示 **`DEMO`**（琥珀色 `0xFFB020`），与真实数据的绿色 `LIVE` **明显区分** |
| 收到真实遥测 | **固件自动退出演示**（不依赖 App 发 `-1`）—— 演示值让位给真实数据 |
| BLE 断开 | **固件自动退出演示**（App 可能已经不在了）|

> 这两条自动退出是**固件侧**的安全保证：否则命令一丢，演示速度就会在真正开车时继续显示。

`face_enabled` 的两条**设备侧规则**（App 无需重复判断，但界面上要能解释）：

| 规则 | 行为 |
|------|------|
| 不能隐藏最后一个表盘 | 拒绝该命令（否则仪表无内容可显示）；`ui_face_set_enabled` 返回 false |
| 隐藏的正是当前表盘 | 自动切到下一个仍启用的表盘（避免停在隐藏页） |
| 变更后的效果 | 持久化到 NVS，且**立即重新上报**表盘列表 |

### 照片表盘命令（2026-10-19，同 Command 特征）

照片的**导入走 SD 卡**（Wi-Fi 上传已放弃，见
[`wifi-upload-postmortem.md`](wifi-upload-postmortem.md)），但**切图与轮播设置走 BLE**：

```json
{"cmd":"photo_prev"}                              // 上一张
{"cmd":"photo_next"}                              // 下一张
{"cmd":"photo_play","value":3}                    // 直接切到第 3 张（0 起，越界夹取）
{"cmd":"photo_get"}                               // 查询设置（结果打到串口日志）
{"cmd":"photo_slide","value":1}                   // 轮播开/关
{"cmd":"photo_shift","value":1}                   // 像素位移（烧屏防护）开/关
{"cmd":"photo_screenoff","value":1}               // 自动息屏开/关
{"cmd":"photo_interval","value":30}               // 轮播间隔（秒）
```

| 命令 | 语义 | 设备侧规则 |
|------|------|-----------|
| `photo_next` / `photo_prev` | 手动切上/下一张（循环）| 有文件才生效；会把该张"钉住"（关闭轮播时停在这张）|
| `photo_play` | 切到第 N 张 | `n<0→0`、`n≥count→count-1` |
| `photo_slide` | 轮播开关 | **关闭轮播时强制像素位移**（用户要求，即使 `shift=0`）|
| `photo_shift` | 像素位移开关 | 画面每 2 分钟整体偏移几个像素，防 AMOLED 烧屏 |
| `photo_screenoff` | 无交互自动息屏 | 60 s ~ 24 h |
| `photo_interval` | 静态图停留时间（秒）| `photo_settings_sanitize()` 统一夹取 |

> 与 `face_enabled` 一样，**解析层只管语法**（`control.c`），业务收敛在
> `photo_slide.c` / 固件侧完成 —— 这样纯逻辑可单测（`test_photo_slide` 54 项）。
>
> ⚠️ 设备**不在连接时主动上报照片清单**：App 只知道"能不能切"，
> 不知道卡上有几张。要显示清单需要新增上报（未做，见 `docs/photo-gif-design.md` §九）。

## 表盘列表上报（`Faces` 特征，2026-10-13）

### 为什么要有它

此前 App 把表盘列表**硬编码**在 `ContentView.swift` 里，必须与固件手工保持一致
—— 已经漏过一次（固件加了 `nav` 表盘后 App 选择器里没有它）。
改为**设备上报、App 渲染**后，新增表盘只需改设备一处。

### 载荷格式（Read 取回，**紧凑数组**）

当前实现（6 个表盘约 **173 字节**）：

```json
{"t":"f","c":6,"m":63,"u":5,"bright":200,"rot":0,"screen":1,
 "f":["analog","digital","speed","color","nav","photo"]}
```

| 字段 | 说明 |
|------|------|
| `t` | 判别字段。**`"f"`**（旧版是 `"faces"`，App 两个都认）|
| `c` | 表盘总数 `count` |
| `m` | 启用位掩码 `mask`（bit i = face id i）|
| `u` | **当前正在显示**的表盘 id（`-1` = 未知）。App 据此标注"正在用哪个" |
| `f` | **表盘名数组**，**顺序即 id**。App 自己推导 `group`（名字映射）与 `on`（`(m>>id)&1`）|
| `bright` | 当前亮度 0-255（2026-10-15 起上报）|
| `rot` | 当前屏幕方向（度，0/90/180/270）|
| `screen` | 1 点亮 / 0 息屏 |
| `trip_km` | 累计里程（km，两位小数）——**由设备累计**，见下 |
| `trip_max` | 最高速度（km/h）|
| `trip_avg` | 加权平均速度（km/h）|
| `trip_s` | 有效行驶时长（秒）|

> **为什么不发对象数组**（2026-10-20 的血泪教训）：iOS 单次 BLE 读取上限约
> **184 字节**，而 `{"id":..,"name":..,"label":..,"group":..,"on":..}` 的 6 个表盘要
> **476 字节** —— 必然被截断，`t` 也一度被改成 `"f"`，结果是 **App 里一个表盘都看不到**。
> 压到 371 仍不够，最终只发名字数组 → **173 字节**，稳在 184 以内。
>
> **兼容**：App 仍保留旧格式（`"t":"faces"` + `faces:[{...}]`）解析，
> 但设备**已经不再发旧格式**（截断分支也已改为紧凑数组）。

### ⚠️ 184 字节：不是"建议"，是硬上限

| 项 | 数值 |
|----|------|
| iOS 协商后的 ATT MTU | 约 185 |
| 单次 Read / Notify 可用有效载荷 | **约 184 字节** |
| 6 个表盘的紧凑上报 | **173 字节** ✅ |
| 旧的对象格式（6 个）| 476 字节 ✗ |

表盘继续增加时（比如再加 2 个），**名字数组也会顶到 184**。届时要做的是：
- **Read 分片**（Read Blob 取回完整值，系统自动分片，与 MTU 无关）—— 见下文；
- 或进一步缩字段（名字本身也可改短，但会牺牲可读性）。

### 行程统计由**设备**累积（2026-10-16，P1-1）

`trip_*` 四个字段和 `bright`/`rot`/`screen` 同属"设备的属性"：

- 仪表**一直在跑**，行程由它持续累积；App 会被系统杀掉、免费账号 7 天就要
  重装一次 —— **App 本地算会一重启就归零**，与仪表上显示的数字对不上，
  比不显示更让人困惑。
- 因此 App 只**显示**，不参与计算。要归零用仪表的串口 `trip reset`。

上报节流：行程每帧都在变，跟着主循环上报会以数百 Hz 刷 BLE 把遥测/地图
挤掉，故**每 10 秒最多一次**，且仅在有效行驶（`time_ms` 增长）时才发。

字段缺省（设备未上报）时 App 显示 `--`，**不兜底成 0** ——
"还没拿到"与"真的是 0 公里"是两件事（刚出发时里程确实是 0）。

截断路径（`FACE_REPORT_MAX_PAYLOAD` 480 字节）仍保留：一旦超限，
报文体带 `"trunc":1`，`f` 数组**尽量多列**，并**保留** `bright`/`rot`/`screen`
（它们在表头）—— 与完整报文**同一套字段**，只是 `f` 变短。

```json
{"t":"f","c":32,"m":...,"u":5,"trunc":1,"bright":200,...,"f":["analog",...]}
```

正常情况下 6 个表盘只有 173 字节，走不到这条路径（32 个表盘才会触发）。

### ⚠️ 亮度/方向/息屏由**设备**上报，App 不得下发覆盖（2026-10-15）

这三项和表盘一样是**设备的属性**，不是 App 的设置：

- 用 App 把亮度调成 70 → 关掉 App 带着仪表上车，亮度仍是 70；
- 下次给仪表**单独上电**（根本没开 App），设备也应保持自己的状态。

因此约定：**设备上报 → App 显示**，App **不得**在连接时下发"它记得的亮度"。
否则会把用户在设备上（或串口上）设好的值悄悄冲掉。

> **反例（已修复的 bug）**：App 曾用 `@State brightness = 200` 当默认显示值，
> 重开 App 显示 200（并非设备真值），用户一碰滑块还把设备改成 200。
> 表现为"亮度调到 70，重开 App 又变回 200"。

**唯一该在连接时由 App 下发的是时间**（`ts_utc_ms`）—— 时间由 App 拥有
（设备无 GNSS、RTC 走时精度不足），性质与这三项相反。

**字段可缺省**：设备未上报某字段时，App **保持当前显示值**，不得兜底成默认值。
`0` 是**有效值**（亮度 0 / 方向 0° / 息屏），必须与"未上报"区分开 ——
把两者混为一谈正是上述 bug 的形态。

**截断时也必须带出**这三个字段（它们位于表头，不在 `f` 数组内），
否则表盘一多 App 就拿不到状态，又退化回"默认值覆盖设备"。

**改动来源不限 BLE**：串口改亮度/方向后设备同样会重新上报，
因此无论从哪条路径改，App 界面都会收敛到真值。

## 亮度曲线（App → 设备，`t":"bright"`，2026-10-17）

解决真机痛点：**晚上太亮刺眼、白天太暗看不清**。

```json
{"t":"bright","v":1,"on":1,"ds":420,"de":1110,"day":220,"night":40,"ramp":30}
```

| 字段 | 含义 |
|------|------|
| `t` | 恒为 `"bright"`（与 nav/map/遥测共用特征，靠它分流）|
| `on` | 1 启用自动 / 0 关闭 |
| `ds` / `de` | 白天开始/结束（**当天分钟数** 0-1439；420 = 07:00）|
| `day` / `night` | 白天/夜间亮度 1-255 |
| `ramp` | 过渡时长（分钟，0 = 硬切换）|

### 设计要点

- **不做天文计算**：用户直接给两个时间点（可左右滑动），比"算日出日落"
  更简单、可预测、可解释，也不需要位置信息。
- **时间用分钟数**：一次整数比较，且协议里无时区/格式歧义。
- **字段全部可选**（`has_*` 标志，不是 `-1` 哨兵）：将来加字段
  （按周/工作日）不会让旧固件整包丢弃。
  > 早先用 `-1` 表示"未提供"，但它同时是"提供了负值"，两者相撞会导致
  > **用户改了却没反应**（负值被当成"没说"而忽略）。改用显式 `has_*` 后
  > 负值能正常走夹取路径。
- **越界夹取而非拒绝整包**：亮度夹到 `[1,255]`（**不能是 0** —— 屏全黑会被
  当成死机）；时间夹到 `[0,1439]`；ramp 夹到 `[0,240]`。
- **设备不持久化**：每次连接 App 都重发，避免两边各存一份后不一致
  （那会导致"App 显示 07:00 但设备按 06:00 跑"）。

### 手动优先（关键交互规则）

用户手动调过亮度（App 滑块 **或** 串口 `bright`）后，自动曲线**暂停**，
直到：
- App 重发曲线（= 用户在 App 里重新打开自动开关），或
- 设备重启

否则会出现"我调好了它又给我改回去"的经典烦躁体验。
固件用两个入口强制区分这件事：`apply_brightness_user()` / `apply_brightness_auto()`
（**不用靠调用方记得置标志位** —— 那样迟早漏一处且极难复现）。

### ⚠️ 性能与稳定性教训（2026-10-19）

用户反馈三个症状：**初始化同步慢 / 时间与亮度同步好几次才对 / 运行中卡死**。
三个症状有**共同根因** —— 主循环被无谓的高频工作拖垮：

| 问题 | 根因 | 修复 |
|---|---|---|
| 同步慢、卡死 | `bright_poll()` **每帧读 RTC**（I2C 读 PCF85063 7 字节），主循环 100-200 次/秒，循环频率从 **198 掉到 78 次/秒** | 按 `millis()` 节流，**20 秒**才读一次 RTC（曲线只需分钟级精度） |
| 表盘列表被反复上报 | `sync_display_report_state()` 置 `s_faces_dirty`，而它被「亮度变化」和「每 10 秒行程统计」调用 → 整份 ~460 字节列表被反复推送（当时还是对象格式；现在紧凑格式 173 字节） | 上报**节流到最快 2 秒一次**（表盘列表本身几乎不变） |
| 未连接时仍空转 | `ble_telemetry_set_faces()` 在 `s_connected == false` 时仍执行 `setValue()`（460 字节 string 重分配）+ `notify()` | 未连接时**直接返回** |

修复后实测：循环频率 **78 → 195 次/秒**，空闲堆全程恒定 105640 B（无泄漏），
5 轮反复重连压力测试无卡死。

**教训**：主循环里的任何"每次调用"都必须先问"真的需要这么频繁吗"。
I2C 读寄存器看似廉价，乘以 200Hz 就是灾难。

### 系统性验证发现的问题（2026-10-19 第二轮）

用户报告"似乎没有复现了"后，我没有停在"看起来好了"，而是做了一轮
**系统性的覆盖分析**（模糊测试 / 属性测试 / 边界穷举），又挖出 4 个问题：

| # | 问题 | 怎么发现的 | 影响 |
|---|------|-----------|------|
| 1 | **过渡窗口重叠导致亮度突跳** | 属性测试：随机 20 万组配置 × 1440 分钟 | 跨午夜 + 大 ramp 时 07:05 是 114、07:10 突然 200 |
| 2 | **RTC 无效时白天用夜间亮度** | 覆盖分析：`rtc_ok=false` 路径从未测过 | 屏幕在阳光下几乎看不清 |
| 3 | **改曲线后要等 20 秒才生效** | 边界测试 | 用户以为"没反应" |
| 4 | **Swift 镜像存在同样的重叠 bug** | 交叉验证 | App 预览与设备不符 |

#### 1) 过渡窗口重叠（最隐蔽）

天亮过渡在 `[start-ramp, start)`，天黑过渡在 `[end, end+ramp)` ——
**两段都在夜间段里**。若 `2*ramp > 夜间段长度`，两个窗口重叠，
同一时刻既算天亮又算天黑，而代码用 `if/else` 只取其一 → **突跳**。

修复：把 `ramp` 夹到**夜间段长度的一半**。

> ⚠️ 我第一次用"白天段/2"做上限，**根本没触发**（白天段 1182 分钟，
> cap=591 > 222），bug 原样复现。约束必须针对**夜间段**。
> 这条记在这里是因为它很容易再错一次。

#### 2) RTC 无效时不应按曲线调亮度

`rtc_time_provider()` 在 `rtc_ok=false` 时把 `tm` 清零（"不伪造时间"），
于是 `now_min` 恒为 0（00:00）→ 曲线永远判定夜间 → **白天也调成夜间亮度**。

修复：`bright_poll` 里加两道闸 ——
- `!rtc_ok` → 直接 return（放弃自动，保持当前亮度）
- `tm_year + 1900 < 2020` → 同样 return（防电池掉电后寄存器归零）

#### 3) 曲线修改立即生效

`bright_poll` 有 20 秒的 RTC 读取节流（性能修复引入）。曲线变化时若只清
`s_bright_last_applied`，仍会被节流挡住 → 用户改完要等最多 20 秒。

修复：新增 `s_bright_recalc_now` 标志，曲线变化与校时成功时置位，
`bright_poll` 见到就跳过本次节流。

### 验证方法与结论

| 手段 | 规模 | 结果 |
|------|------|------|
| 解析器模糊测试 | 50 万次随机输入（合法模板 + 随机字节） | 零越界；合法 100% 解析，随机字节 0 误判 |
| 亮度属性测试 | 20 万组配置 × 1440 分钟 = **2.88 亿采样点** | 全部在 1-255，无突跳 |
| 极端配置真机测试 | 跨午夜/白天22小时/零长度/亮度极值 | 全部接受，无崩溃 |
| 长稳测试 | 180-298 秒连续运行 | 195/s 稳定，空闲堆恒定，零异常 |
| 全量回归 | **1175 项**（C 679 + Swift 496） | 全通过 |

**结论**：这一轮的问题都出在"冷门路径"——跨午夜、RTC 失效、极端 ramp。
默认配置下跑不出来，但用户一旦把区间拖到古怪位置就会撞上。
属性测试（随机配置穷举）是发现这类问题最有效的手段，建议后续改动继续沿用。

### 连接初始化延迟

App 侧 `sendTimeOnConnect()` / `sendBrightnessCurve()` 原先用 `.withResponse`
（每包等一次确认），而初始化已经串了 discoverServices → discoverCharacteristics
→ setNotifyValue×2。改为 `.withoutResponse` 降低延迟；两包都很小（<80 字节，
远小于 MTU），且都是幂等的 —— 丢一次可由后续遥测包/下次连接补上。

### 手动 / 自动 二选一（2026-10-19 用户反馈后重做）

**问题**：早先有两个独立滑块 —— 「亮度」和「亮度时段」里的「白天亮度」。
两者数据源完全不同（前者是设备上报的实际亮度，后者是曲线配置），
却都能改同一个物理亮度。用户改了一个、另一个不动，
**完全分不清"到底哪个说了算"**，实测反馈就是"改完没反应"。

**改法**：加一个 `手动 / 按时段自动` 切换，**同一时刻只有一套控件在管亮度**：
- **手动**：只显示「亮度」滑块，直接改当前亮度（触发手动优先）
- **自动**：只显示「白天/夜间亮度」，按时间调节；上面的亮度变成只读显示

#### 协议新增 `reset` 字段（必需，不是可选优化）

切回「自动」时必须带 `reset:1`。原因很隐蔽：

```
1. 自动，曲线 day=180 → 设备 180
2. 切手动，设 99     → 设备 99（手动优先）
3. 切回自动         → App 发的曲线**内容没变**（还是 180）
                    → 设备判定"重连重发" → 保持 99  ✗
```

`reset` 让 App 能明确表达"恢复自动"，而不依赖"曲线内容是否变化"这个
在**切换模式时根本不成立**的判断。

### ⚠️ 曲线包必须用 `.withResponse`（不能 `.withoutResponse`）

实测（2026-10-19）：短时间内连发 9 个曲线包，设备收到顺序是

```
130 160 170 140 120 110 180 100 150   ← 完全乱序
```

最终亮度停在 150 而不是最后发的 180。原因：`.withoutResponse` 是"即发即忘"，
BLE 栈按自己调度发送，**不保证到达顺序**。而曲线是**配置**，必须先来后到。

配合 **0.25 秒防抖**（拖动停止后才发最终值），避免拖动时几十个包挤在一起。
模式切换这类**离散操作**走 `sendBrightnessCurveNow()` 立即发，不等防抖。

### 亮度平滑跟随（不是"发一个包跳一下"）

用户反馈："调节亮度后设备同步不是线性的，而是发一个时间包重置的感觉"。
这是**两个**独立原因叠加：

#### 原因 1：App 只在松手时发

手动亮度滑块原先写的是 `Slider(...) { editing in if !editing { send } }` ——
拖动过程中**完全不发**，松手才发一次。所以屏幕在拖动时一动不动，
松手瞬间跳到目标值。

**修复**：拖动中持续下发（`setBrightnessLive`，50ms 限流 ≈ 20Hz），
松手时再用 `.withResponse` 补发最终值确保到位。

#### 原因 2：固件把中间值丢了（关键）

固件对 BLE 命令是 **latest-wins 合并**（`s_pending_cmd` 只有一个槽位）。
多条命令在同一个主循环帧之前到达时，中间值被覆盖丢弃 ——
即使 App 发得很顺，屏幕仍然只看到"起点 → 终点"。

**修复**：命令只设**目标值** `s_bright_target`，主循环每帧朝目标走
`BRIGHT_STEP_PER_FRAME`(3) 步。这样不依赖命令到达频率，
丢了多少中间值都无所谓，视觉上始终是连续渐变（255 满量程约 1.3 秒）。

> ⚠️ 过渡期间**不要**走 `apply_brightness()` —— 它会调
> `sync_display_report_state()` 置 `s_faces_dirty`，每帧上报会把 BLE 刷爆
> （就是之前"卡死"那类形态）。只在**到位那一帧**同步一次。

### 与 `bright` 上报的关系（两者不冲突）

| 方向 | 字段 | 谁拥有 |
|------|------|--------|
| App → 设备 | `t":"bright"` 的曲线包 | **App**（用户偏好）|
| 设备 → App | `faces` 里的 `bright` 当前值 | **设备**（实际生效值）|

即：**曲线由 App 决定，当前亮度由设备回报**。二者是"目标"与"实际"的关系。

### ⚠️ Read 才是取数据的正途，Notify 只是"变了"的提示

**BLE 单次通知受 MTU 限制**（iOS 实到约 185 字节）。当前紧凑格式 6 个表盘
**173 字节**，勉强能塞进一次读取；旧的对象格式 476 字节必被截断。

因此约定：

| 通道 | 用途 |
|------|------|
| **Read** | 取数据。系统会自动用 Read Blob 分片取回**完整值**，与 MTU 无关 |
| Notify | 仅作"发生了变化"的提示；App 收到后应**重新 Read** |

App 侧据此实现为：**能解析成完整 JSON 就用，解析失败就重新 Read**
（被截断的 JSON 一定解析失败）—— 无需额外状态机，且不会反复重读。

### App 端的界面层级（分组是一级，表盘是二级）

> App 已按 **5 个 Tab**（仪表 / 数据 / 导航 / 照片 / 设置）组织。
> 表盘相关内容在**仪表**页；照片的切图与轮播开关在**照片**页。
> 详见 `ios/CarDashboardPhone/README.md`（若有）。

```
表盘
  [时钟] [速度表] [导航]              ← 一级：分组（只列设备实际有的）
  ──────────────────────────────
  [🕐] 模拟时钟        ( ✓ )  [开关]   ← 二级：只列该分组的表盘
  [#]  数字时钟        ( → )  [开关]
  [🎨] 多彩时钟        ( → )  [开关]
```

行布局的取舍：

| 位置 | 内容 | 理由 |
|------|------|------|
| 左 | **表盘图标**（按 `name` 映射，未知表盘用通用图标）| 一眼区分"是哪种表盘"；放勾选标记既占位又不表意 |
| 中 | 中文名 | |
| 右一 | **切换按钮**：`→` 可切；`✓` 表示已是当前（禁用）| 切换与显隐是**两个动作**，各自要有明确控件；藏在"点名称"里不易发现 |
| 右二 | **开关**：是否出现在滑动序列中 | |

两条约定：

1. **只显示选中分组的表盘** —— 把所有表盘平铺会让分组失去意义。
2. **默认打开当前表盘所在的分组** —— 否则当前表盘在别的分组里，
   用户看不到 ✓，会以为"没有当前表盘"。

> **实现要点（踩过坑）**：分组的选中态与"当前表盘"都是**从上报派生的值**，
> 不另存本地状态再用 `onChange` 同步 —— 那样在上报到达时 `onChange` 未触发，
> 会出现"分组下没有内容""勾选指不到当前表盘"。能派生就不要同步。
>
> 另：设备**切换表盘后也会重新上报**（否则 App 拿不到新的 `cur`）。

> 旋转 / 亮度 / 息屏是**整机**行为，对所有表盘生效，因此放在独立于「表盘」的
> 「屏幕显示」节，避免被误认为"只影响当前表盘"。

### 新增表盘时 App 为什么不用改

本地化按 `name` 查表，**查不到就直接显示设备给的 `name` 本身**（ASCII）。
紧凑格式已经**不发 `label`** —— App 本来就有 `?? name` 兜底，去掉它省了 100+ 字节。
所以设备加一个新表盘后，App 会自动列出它，只是没有中文名。
想给它中文名，再在 `FaceDisplay.faceTitle` 里加一条即可 —— 不加也不影响使用。

### 屏幕方向（`rotate`）详解

| 字段 | 说明 |
|------|------|
| `value` | 方向**角度**：`0` / `90` / `180` / `270` |

- 用**角度**而非"索引"，避免与其余命令的 0 基索引混淆
- **仅接受 90 的整数倍**；其它值（如 `45`）会被**明确拒绝**
  （固件统计里"拒绝"+1），不会静默转到意外方向
- 超范围值按 `mod 360` 归一：`-90` → `270`，`450` → `90`
- 实现：**90°/270° 走面板硬件旋转（CO5300 MADCTL）**，LVGL 保持 `LV_DISP_ROT_NONE`
  （`set_display_rotation()` 写 `mad = (deg == 270) ? 0x60 : 0xA0`）；
  **只有 0°/180° 用 LVGL 软件旋转**（`lv_disp_set_rotation`）
- 本屏为**圆形**，旋转后仍是同一个圆，无长宽比/布局副作用
- 触摸坐标**由固件自己在采样层补偿**（`touch_apply_rot()`），
  **不是** LVGL 自动逆变换 —— 这样 LVGL indev 与 flick 手势判定都自动正确
- 取舍与真机数据见 [rotation-hardware-vs-software.md](rotation-hardware-vs-software.md)
- **方向持久化到仪表 NVS，重启后保持**
- 开销：0° 无开销；180° 约 +13ms；90°/270° 约 +20ms（整屏重绘时）。
  详见 [`troubleshooting.md`](troubleshooting.md#2026-10-13-屏幕旋转可行更正-2026-10-11-的错误结论)

## 表盘系统（功能③）

表盘由**注册表**驱动（`simulator/ui/ui_face.c`），当前注册 **6** 个：

| id | name | 内容 |
|----|------|------|
| 0 | `analog` | 模拟指针时钟（烘焙表盘 + 三针）|
| 1 | `digital` | 数字时钟（138px 时间 + 日期 + 同步状态）|
| 2 | `speed` | 速度表（烘焙表盘 + 驾驶员三态 + 指针 + 航向/行程 HUD）|
| 3 | `color` | 多彩时钟（Apple StandBy 风格四位数字 + 彩色字位）|
| 4 | `nav` | 导航卡片（转向提示 + 地图窗口）|
| 5 | `photo` | 照片表盘（SD 卡 `/photos/*.pgi`，静态 + 动图混排轮播）|

注册顺序即 id 顺序，也与 `ui_page_t` 一一对应。新增表盘只需在
`ui_pages_init()` 里多注册一项（照片表盘就是这么加的第 6 个），
分页、翻页手势、BLE/串口命令通路都无需改动。

> ⚠️ 新增表盘时**不要忘了设备侧的启用掩码**：掩码存在 NVS 里，
> 旧设备上新增的位是 0 → 会被当成"用户主动隐藏"，表现为**新表盘看不到**。
> 已修（存掩码时一起存表盘总数 `fcount`，`index >= fcount` 的视为新增并强制启用），
> 详见 [`troubleshooting.md`](troubleshooting.md#nvs-掩码导致新增表盘看不到2026-10-20已修复)。

固件串口命令（无 App 时验证）：

```
face              列出全部表盘与当前表盘
face 1            切到指定 id
face next/prev    下一个 / 上一个（循环）
```

约定与遥测上行一致：**BLE 回调只解析并暂存，硬件副作用（`setBrightness` /
`displayOff`）回到主循环执行**——BLE 回调运行在 Bluedroid 任务里，不能碰显示驱动。

亮度限幅：`0 → 1`（避免全屏黑被误认为死机），`>255 → 255`。

无 App 时可用串口验证：

```
bright 120      设置亮度
bright          查询当前亮度
screen off      息屏
screen on       亮屏
ble             查看控制命令统计（成功/拒绝次数）
```

解析层是纯 C（`simulator/ui/control.c`），带 58 项单元测试（`tests/test_control.c`）。
