# 指针流畅度实测（性能基线）

针对**最担心的问题——指针卡顿**的量化测量方法与基线记录。
设备常连电脑，随时可复测。

---

## 一、方法（为什么这样测）

心跳行里的「重绘/s」只在**有数据变化**时才有意义：
手机没连、速度不变时重绘率恒为 0，**看不出流畅度**。
要判断指针卡顿，必须让指针持续动起来，同时观察设备侧渲染耗时。

`tools/perf_needle.py` 把三步固化：

1. 经 BLE **持续注入连续变化**的车速（默认 2Hz，与真实 App 同频）
2. 同时从串口抓设备侧**每 5 秒的渲染统计**
3. 用固定口径统计（p50/p90/max + 尖刺计数），并记录 `uptime` 以检测
   测试期间是否被重新烧录（否则结果不可信）

车速轨迹分三段，覆盖不同动态特性：

| 段 | 轨迹 | 看什么 |
|----|------|--------|
| 1 | 慢扫 0→120 km/h（20s）| **连续平滑**移动 |
| 2 | 快扫 120→0→120（12s）| 急速变化时指针能否跟上（固件有时间斜坡）|
| 3 | 抖动 60±3 km/h | 小抖动是否被抑制（不该抖成噪声）|

### 复现命令

```bash
# 1) 编译 BLE 注入工具（只需一次）
swiftc -O -o /tmp/ble_speed_probe -framework CoreBluetooth \
  tools/nav_sim/NavSimBLE.swift tools/ble_speed_probe.swift

# 2) 测量
python3 tools/perf_needle.py --duration 150 --label after-speedUI \
    --out docs/perf/after-speedUI.json
```

## 二、基线结果（2026-10-14 00:01，速度表盘 UI 改版**之前**）

原始数据：[`baseline-2026-10-13.json`](baseline-2026-10-13.json)
（`uptime_delta = 155s`，与 150s 时长吻合 → **未被重新烧录**，结果可信）

| 指标 | p50 | p90 | max |
|------|-----|-----|-----|
| **单帧渲染最大耗时** | **29 ms** | 31 ms | 74 ms |
| 渲染占空比 | 10 % | — | 39 % |
| 重绘率（指针运动中）| 35 /s | — | 111 /s |
| QSPI 单次传输 | 1 ms | — | 19 ms |
| 主循环 | 177 /s | — | 198 /s |

**尖刺计数：>80ms 0 次、>100ms 0 次、>150ms 0 次**（150 秒内）

### 结论

- **稳态无卡顿**：29ms/帧 ≈ 34fps，占空仅 10% —— 有充足余量
- 最大 74ms 出现在**大幅扫表**（脏区大）时，属可接受的一次性开销
- 占空最高 39%，远未饱和

> 早期一次短测曾出现 110ms 单帧，事后确认是**切换表盘时的重建**造成，
> 不是稳态问题 —— 这也是为什么要用"注入连续车速 + 长窗口"来测，
> 而不是看空闲时的心跳。

## 三、附带验证：变更检测确实会收敛

固件以 **50Hz** 调用 `ui_speed_set_speed()`（有明确限频注释），
靠 setter 里的**浮点精确相等**做变更检测，避免 `lv_meter_set_indicator_value()`
无条件失效化造成重绘风暴。

这种写法看着脆弱（浮点相等），故**实测验证**：注入**恒定** 80 km/h 后静观 30 秒：

```
重绘/s 序列:  [4, 6, 6, 2, 0, 0, 0, 0, 0]     ← 收敛后完全静止
渲染最大序列: [45, 50, 50, 50, 3, 2, 2, 2, 2]  ← 降到 2ms
```

**EMA 确实收敛到浮点不动点**，重绘降到 0 —— 该设计可靠，不构成风险。

## 四、已知的性能设计（读代码得到，供改版时参考）

| 机制 | 位置 | 作用 |
|------|------|------|
| 50Hz UI 限频 | `dashboard.ino` `ble_update()` | 手机 2Hz，限频压低空转成本 |
| setter 变更检测 | `ui_speed.c` | 防 `lv_meter_set_indicator_value` 无条件失效化 |
| PSRAM 全帧绘制缓冲 | `dashboard.ino` | partial 模式下脏区 ≤ 缓冲即**只切 1 块**；`bufmode` 可切内部 1/10 屏做 A/B |
| QSPI 80MHz | `QSPI_SPEED_HZ` | 实测单次传输 p50 仅 1ms，**不是瓶颈** |

> 瓶颈是 **LVGL 渲染本身**（29ms），不是 QSPI。
> 若速度页改版后想进一步提速，方向是**缩小失效区域**（针尖/数字分开失效），
> 而不是继续提 QSPI 频率。
