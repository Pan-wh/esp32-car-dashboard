## 三、真机测试详情（iPhone 12 / iOS 27.0）

### 3.1 后台 + 锁屏（#2 / #3）

操作：开始驾驶 → 确认已连接 → 回主屏 → 锁屏。75 秒连续采样：

| 指标 | 结果 |
|------|------|
| 成功包 | 1376 → **1524**（+148 ≈ 2Hz）|
| 连接 | 全程 `已连接` |
| 数据龄 | 17–504 ms |
| 链路 | **全程 `LIVE`** |

**结论**：`allowsBackgroundLocationUpdates` + `bluetooth-central` 均生效。

### 3.2 定位权限被拒绝（#7）—— 修复了一个真实缺陷

**发现**：权限改为「永不」后**仪表仍以 2Hz 收到数据**（+53 包），而 App 已显示"已拒绝"。

**根因**（违反 §6.3「不得用旧值冒充当前值」）：
1. `locationManagerDidChangeAuthorization` 只设错误文案，**未清空 `lastLocation`**；
2. `tick()` 仅判断 `lastLocation` 非空 → 继续发送**过期坐标**；
3. `makePacket()` 缺少位置新鲜度校验。

**修复**：权限被拒时 `stopUpdatingLocation()` + 清空位置；`makePacket()` 增加
3s 新鲜度校验；新增 `hasFreshLocation(maxAge:)`。

**修复后验证**：成功包恒定不增长 → 2.5s 后 `STALE` → 数据龄持续增长（12s→49s）。
附带验证了 `BT OFF` 与 `STALE` 的正确区分。

> **iOS 行为记录**：权限在 App **处于后台**时被修改，iOS 不立即通知该 App，
> 后台定位会话会继续运行；**回到前台**才收到 `didChangeAuthorization`。

### 3.3 强退 App 后重开（#10）

| 指标 | 结果 |
|------|------|
| 自动重连 | ✅ 无需点任何按钮 |
| 恢复发送 | ✅ 2332 → **2403**（+71 ≈ 2Hz）|
| 链路 | 数据到达后自动转 `LIVE` |
| 数据龄 | 从 177s（旧值）→ **193ms**（证明是新数据）|

> 过程中观察到一次瞬态 `STALE`（数据龄 3431ms）随即恢复——2.5s 超时机制正确工作。
>
> **相关修复**：强退重开后曾出现「BLE 状态一直初始化中」，根因是
> `DriveSessionManager` 未转发子对象的 `@Published` 变化（`bleConnected`
> 是普通计算属性 → SwiftUI 不重绘）。已修复为 Combine 转发 + 启动自动连接。

### 3.4 30 分钟整链路长稳（#12）

室内静止靠窗，每 30s 采样，61 样本 / **1880 秒（31.3 分钟）**：

| 指标 | 结果 |
|------|------|
| 成功包 | 2633 → **4916**（+2283）|
| 平均速率 | **1.21 包/秒**（设计 2Hz）|
| BLE 断连 | **0 次** |
| 内存（空闲堆）| 120,320–120,348 B（**零漂移**）|
| 崩溃 / 重启 | **0 次** |
| 链路态 | LIVE 48 / STALE 11 / 断开 0 |

**结论**：无崩溃、无重启、无内存泄漏、无断连。

**关键发现 ①：数据速率 1.21Hz（非设计 2Hz）**
iOS 在设备**静止**时主动降频省电（系统策略，非缺陷）。
`desiredAccuracy` 已为 `BestForNavigation`、`distanceFilter` 已为 `None`，
配置已最优；**行驶时**会自然恢复 ≈2Hz。

**关键发现 ②：11 次瞬态 STALE（18%）**
全部满足「Δ包正常 + 刚过 2.5s + 30s 内恢复」→ 是**回调延迟**而非真实断流。
即用户观察到的「状态偶尔跳变」，已由**显示防抖**修复（见 §3.6）。

### 3.5 CarPlay / 导航共存（#4）

用户实机连接 CarPlay 并**正在导航**，本 App 同时运行，10 分钟 / 31 样本：

| 指标 | 结果 |
|------|------|
| 成功包 | 1212 → **1788**（+576）|
| BLE 断连 | **0 次** |
| **LIVE 期间无增长** | **0 次** ← 关键证据 |
| LIVE / STALE | 24 / 7 |

**结论**：CarPlay 导航**未抢占** CoreLocation，本 App 仍持续收到定位并下发。

**STALE 占比 23% 与 CarPlay 无关**（对比数据）：

| 场景 | STALE 占比 | 平均速率 |
|------|-----------|---------|
| 无 CarPlay（§3.4）| 18% | 1.21 包/秒 |
| CarPlay 导航中 | 23% | 0.93 包/秒 |

两者接近且本轮速率更低（车更静止→降频更明显），根因同为 iOS 静止省电降频。

### 3.6 瞬态 STALE 闪烁修复

**现象**：状态标签偶尔瞬间跳 `STALE` 又回 `LIVE`（用户观察，长稳数据量化）。

**根因**：iOS 静止降频至约 1.25Hz，偶发回调延迟擦过 2.5s 超时阈值。

**修复**：新增 `telemetry_debounce_apply()` **显示防抖**：
- STALE 需**连续 3 次**判定才切换；
- 恢复 `LIVE` **立即生效**；
- 非 STALE 状态直接透传。

**关键设计——显示与指针分离**（安全优先）：
```
link_raw  = 原始判定   → 驱动指针/数据有效性（过期即归零 §6.3）
link_disp = 防抖后状态 → 仅用于屏幕标签
```
防抖**只影响显示**，指针仍严格遵循「数据过期立即归零」。

> **未采用「放宽超时阈值」**：那会让真实断流时降级变慢，降低安全性。

## 屏幕旋转功能验证（2026-10-13，真机 + 模拟器）

**背景**：用户需要 App 控制屏幕方向（竖屏）。早先文档记录「90° 旋转不可行」，
经复核**该结论有误**——当时开着 `full_refresh`，LVGL 会直接拒绝旋转
（`lv_refr.c`: "cannot rotate a full refreshed display!"），画面不刷新被误判为撕裂。
官方示例 `06_LVGL_Widgets.ino` 证实软件旋转受支持（`disp_drv.sw_rotate = 1`
+ `lv_disp_set_rotation()`）。详见 [`troubleshooting.md`](troubleshooting.md#2026-10-13-屏幕旋转可行更正-2026-10-11-的错误结论)。

### 性能实测（真机，8 次整屏重绘取最大）

| 方向 | 渲染最大 | 相对 0° |
|------|---------|--------|
| 0° | 102 ms | 基线（不进旋转路径）|
| 180° | 115 ms | **+13 ms** |
| 90° | 123 ms | **+21 ms** |
| 270° | 122 ms | **+20 ms** |

**为何 90°/270° 不贵**：本屏为**正方形** 466×466，全屏脏区满足 `area_h >= area_w`
→ 走 `draw_buf_rotate_90_sqr()` **原地 4 向旋转**，不分配临时缓冲。

### 正确性验证（模拟器像素级）

真机无法回读面板内容，故用模拟器（同一份 LVGL 代码）量化比对：

| 方向 | 与「自身旋转」平均像素差 | 与未旋转原图 |
|------|----------------------|-------------|
| 90° | **0.00**（精确匹配逆时针 90°）| 32.66 |
| 180° | **0.00** | — |
| 270° | **0.00** | — |

### 端到端验证（BLE）

| 步骤 | 结果 |
|------|------|
| 发送 `{"cmd":"rotate","value":90}` | ✅ 写入成功，固件 `控制命令=成功 1`，方向变 90° |
| 发送 `{"cmd":"rotate","value":45}`（非法）| ✅ `拒绝 1`，方向**保持 90° 不变** |
| 重新烧录（芯片复位）后查询 | ✅ 仍为 **90°** → **NVS 持久化生效** |

### 顺带发现

测试过程中出现一次 **1002 ms** 单帧（270° 阶段），但随后 3 轮 × 3 角度
**均未复现** → 与旋转无关，是此前记录过的「偶发单帧 1000ms+ 尖刺」
（见「已知限制」），非本次功能引入。

| 充气前后像素一致性 | 页 0/2 各 **0/217156** 像素差异（逐像素完全一致）|
| 量化损失 | dial_speed 979→256 色：1.93% 像素、最大偏差 35/255，**肉眼不可分辨** |
| 滑页性能（未充气）| 168 ms ⚠️ 退化 +45ms |
| **滑页性能（充气后）** | **110 ms** ✅（比原 RGB565 的 123 ms 快 13 ms）|
| PSRAM 开销 | 1.36 MB（余 6.5 MB）|
| 内部堆 | 无变化（121,292 B）|

**为什么充气后反而更快**：绘制源从 Flash（走 mmap/缓存）变成 PSRAM，吞吐更高。

**降级行为**：PSRAM 分配失败时保持索引图 —— 功能不受影响，仅滑页慢约 45ms，
不会白屏或崩溃（已在代码中显式处理）。

**顺带修复的两个既有缺陷**：
1. `tools/make_images.py` 生成的 header 写 `#include "lvgl/lvgl.h"`，
   而本项目构建里该路径不存在（可编译的产物是 `"lvgl.h"`）——
   即**生成脚本与它能编译的产物不同步**，重新生成必然编译失败。
2. 两个生成脚本都是**直接以 "w" 打开输出文件**，中途抛异常会把仓库里的
   生成物**截断**（实测截断过一次 `ui_dial_faces.c`）。已改为**原子写入**
   （先写临时文件再 rename）。

## 四、已知限制（须写入交付说明）

1. **iOS 后台不保证**：强制退出 App、权限撤销、系统状态下 iOS 可能停止更新，
   无法无条件保证持续发送。实测上述场景均已按预期降级（转 `STALE`）。
2. **航向来源**：使用 `CLLocation.course`（地面行进方向），**非**磁罗盘；
   静止/低速时可能无效 → 发送 `null`，仪表不显示。
3. **速度为 GPS 速度**：非 OBD/CAN；室内/隧道会失效并按超时置无效。
4. **静止时数据速率约 1Hz**：iOS 省电策略，非缺陷；行驶时恢复 ≈2Hz。
5. **无法获取导航数据**：红绿灯、路线、转向提示**均不可得**（无公开 API，
   §5.1 禁止读取 Apple Maps 私有数据）。仅使用 CoreLocation 自身的
   速度/航向/坐标。
6. **本设备是辅助显示**，非认证车速计或安全关键仪表。
