## 已知限制（须写入交付说明）

1. **iOS 后台不保证**：强制退出 App、权限撤销、系统状态下 iOS 可能停止更新，无法无条件保证持续发送。
2. **航向来源**：使用 `CLLocation.course`（地面行进方向），**非**磁罗盘；静止/低速时可能无效 → 发送 `null`，仪表不显示。
3. **速度为 GPS 速度**：非 OBD/CAN；室内/隧道会失效并按超时置无效。
4. **本设备是辅助显示**，非认证车速计或安全关键仪表。
5. **本机无法完成的验证**：iOS 模拟器/真机运行（缺平台运行时）、CarPlay/后台实机测试。

**目的**：在无真实 GPS（室内）条件下，验证「CoreLocation → 质量门槛 → 数据生产」
正确性，与仪表侧消费解耦验证。

**方法**：`xcrun simctl location <udid> run "Freeway Drive"` 提供带速度/航向的

**结果**（`LinkDiagnosticsUITests` 通过）：
```

速度质量 = 通过             定位精度 = ±5 m
```

**踩坑记录**：首次运行该测试读到所有字段"缺失"，一度误判为定位回调未到达。

135°（0 km/h）与 297°（120 km/h）符合量程映射。

**结论**：链路（除物理 BLE 传输外）逻辑闭合。BLE 传输本身已在真机验证

仪表侧 75 秒连续采样：

| 指标 | 结果 |
|------|------|
| 成功包 | 1376 → **1524**（+148 包 / 75s ≈ 2Hz）|
| 连接 | 全程 `已连接`（BLE 未断）|
| 数据龄 | 17–504 ms（远低于 2.5s 阈值）|
| 链路状态 | **全程 `LIVE`** |

**结论**：后台定位（`allowsBackgroundLocationUpdates`）与后台 BLE
（`bluetooth-central`）均生效，锁屏不影响数据链路。

### #16 权限被拒绝 ✅（修复一个真实缺陷）

**发现**：把定位权限改为「永不」后，**仪表仍以 2Hz 持续收到数据**
（成功包 2204 → 2257，+53 包），App 界面却已显示"定位权限被拒绝"。

**根因**（违反 §6.3「不得用旧值冒充当前值」）：
1. `locationManagerDidChangeAuthorization` 只设置错误文案，**未清空 `lastLocation`**；
2. `tick()` 仅判断 `lastLocation` 非空 → 权限被拒后继续发送**过期坐标**；
3. `makePacket()` 缺少位置新鲜度校验。

**修复**：
1. 权限被拒/受限时 `stopUpdatingLocation()` + `lastLocation = nil`；
2. `makePacket()` 增加新鲜度校验（位置时间戳超过 3s 视为失效，不发送）；
3. 新增 `hasFreshLocation(maxAge:)` 供 UI/逻辑复用。

**修复后验证**（权限仍为「永不」，启动驾驶）：
```
成功包 2332 保持不变（不再增长）✓
链路状态 BT → STALE（2.5s 超时降级）✓
数据龄持续增长 12s → 49s ✓（正确反映数据已过期）
```

**附带收获**：本次同时验证了 `BT OFF` 与 `STALE` 的区分——
断开时显示 `BT`，连上但无数据时显示 `STALE`，且数据龄单调增长。

**iOS 行为记录**：权限在 App **处于后台**时被修改，iOS 不会立即通知该 App，
后台的定位会话会继续运行；App 回到前台才收到 `didChangeAuthorization`。
这是系统行为，需在文档中写明（用户应在前台撤销权限后才立即生效）。

## #18 整链路 30 分钟长稳 ✅（2026-10-13，iPhone 12 / iOS 27）

**配置**：App 前台运行 + 开始驾驶 + BLE 连接仪表；室内静止（靠窗）。
每 30 秒采样一次，共 61 个样本、历时 **1880 秒（31.3 分钟）**。

| 指标 | 结果 |
|------|------|
| 成功包 | 2633 → **4916**（+2283）|
| 平均速率 | **1.21 包/秒**（设计目标 2Hz）|
| BLE 断连 | **0 次**（全程 `已连接`）|
| 内存（空闲堆）| 120,320–120,348 B（**零漂移**）|
| 崩溃 / 重启 | **0 次** |
| 链路态 | LIVE 48 次 / STALE 11 次 / 断开 0 次 |

**结论**：整链路（iPhone CoreLocation → BLE → ESP32 → UI）连续 31 分钟
稳定运行，**无崩溃、无重启、无内存泄漏、无断连**。

### 关键发现：数据速率只有 1.21Hz（而非设计 2Hz）

**原因**：iOS 在设备**静止**时会主动降低定位更新频率以省电（系统策略，非缺陷）。
`desiredAccuracy` 已是 `BestForNavigation`、`distanceFilter` 已是 `None`，
配置已最优，无法进一步强制提速。**行驶时**（有实际位移）会自然恢复到 ≈2Hz。

### 关键发现：11 次瞬态 STALE（占 18%）

11 次瞬态全部满足：**Δ包正常（32–43）+ 数据龄刚过 2.5s 阈值 + 30s 内恢复**，
证明是**定位回调延迟**而非真实断流。

这就是用户观察到的「状态偶尔瞬间跳变」。已通过**显示防抖**修复：
连续 3 次判定才切 STALE，单次抖动被抑制；指针行为不受影响（仍严格按
数据过期归零，§6.3）。详见 `docs/troubleshooting.md`。
