# 硬件旋转 vs 软件旋转：显示完整度与性能取舍

> **用途**：记录硬件旋转问题的诊断过程、真机数据与最终决定，避免以后重复试验。
> 撰写时点：2026-10-14。相关提交见文末。
>
> **最终决定**：默认方向为 `0°`；需要 90°/270° 时采用厂商 BSP 的 CO5300
> 硬件旋转（MADCTL）并固定原生偏移 `(6,0)`。旋转态边缘可能有黑缺口，项目接受该限制。
> 自定义 flush 软件转置虽然能让画面完整，但会使秒针、指针和滑页明显卡顿，已从正式固件删除。

## 1. 硬件与既有条件

| 项 | 值 |
|----|----|
| 板子 | Waveshare ESP32-S3-Touch-AMOLED-1.75（**改装自有车机项目**）|
| 屏 | 466×466 圆形 AMOLED，**CO5300**，QSPI（80 MHz，4 线）|
| 触摸 | CST9217（I2C）|

| **面板地址偏移** | GRAM 为 480×480；未旋转可见窗口为 `x=6..471, y=0..465`。官方 IDF BSP 原文：`esp_lcd_panel_set_gap(panel_handle, 0x06, 0);` |
| 构造参数 | `Arduino_CO5300(bus, RST, 0, 466, 466, /*col1*/6, /*row1*/0, /*col2*/0, /*row2*/0)` |

## 2. 改动前（显示正常，但有撕裂）

```c
disp_drv.sw_rotate = 1;
lv_disp_set_rotation(NULL, LV_DISP_ROT_270);   /* 90°/270° 均如此 */
/* 面板 MADCTL 从不写 → 保持上电默认 0x00 */
/* 库的 setRotation() 从未被调用 → _xStart=6, _yStart=0（构造值）*/
```

- **显示：完整、方向正确**（用户确认"以前显示是正常的"）
- **问题：90°/270° 下画面撕裂**（0°/180° 不撕裂）

**已定位的撕裂根因**（实测数据）：

| 指标 | 实测 |
|------|------|
| 整屏 flush 耗时 | **43 ms** |
| 面板帧周期（59.6 Hz） | **16.78 ms** |
| LVGL 软件旋转 90/270° 时渲染 | **25–33 ms**，偶发 **1005 ms** 尖刺 |
| 面板帧周期对比 | 更新总耗时恒 > 一帧 → 必然跨帧 → 撕裂 |

`43 ms` 的构成（用 40/80 MHz 两个时钟 A/B 解出）：

- **约 11 ms** 是真正的 QSPI 传输（正好等于 80 MHz QIO 理论值 10.9 ms）
- **约 32 ms 是 CPU 侧固定开销** —— `Arduino_ESP32QSPI::writePixels()` 中把像素
  从 PSRAM **逐像素搬进内部 DMA 缓冲并重排**的循环：
  ```c
  for (i < l2) { p1 = *data++; p2 = *data++; MSB_32_16_16_SET(_buffer32[i], p1, p2); }
  ```
  该搬移**无法绕过**：LVGL 缓冲在 PSRAM，而 ESP32-S3 的 SPI DMA 只能从内部 RAM 取数。
- 已排除：`ESP32QSPI_MAX_PIXELS_AT_ONCE` 4096→16384（事务数 53→14）**耗时纹丝不动**。

> 另：软件 270° 下的 **1005 ms 渲染尖刺**会导致**中断看门狗复位**（见 §6，已单独修复）。

## 3. 改动后（撕裂解决，但显示不完整）

**把旋转改为面板硬件旋转**：

```c
/* 90/270° 走硬件旋转，LVGL 不旋转 */
90°  → MADCTL 0x60 / 0xA0（见下）
270° → MADCTL 0x60
lv_disp_set_rotation(NULL, LV_DISP_ROT_NONE);
gfx->setRotation(librot);        /* 让库重新分配 _xStart/_yStart */
bus->writeC8D8(0x36, madctl);    /* 再覆盖 MADCTL 为硬件旋转值 */
```

**遇到的第一个问题：库的偏移只能加不能减**

- `Arduino_TFT::setRotation(r)` 按索引把偏移分配到不同轴，本工程构造参数下**只有 3 种组合**：
  `case0 → (6,0)`、`case1 → (0,0)`、`case3 → (0,6)`
- `_xStart/_yStart` 是 `uint8_t` → **无法表达负偏移**
- 而旋转后需要的偏移**很可能是负的**（MADCTL 的 MX/MY 会反转扫描方向）

**已否决的实验**：曾新增子类重写**虚函数** `writeAddrWindow()`（`Arduino_TFT` 里是 `virtual ... = 0`），
用 `int16_t` 承接**有符号**偏移：

```cpp
class DashboardCO5300 : public Arduino_CO5300 {
  void writeAddrWindow(int16_t x, int16_t y, uint16_t w, uint16_t h) override {
    if (changed) {
      int32_t xs = (int32_t)x + _ox, ys = (int32_t)y + _oy;   /* _ox/_oy 为 int16_t */
      _bus->writeC8D16D16(CO5300_W_CASET, xs, xs + w - 1);
      _bus->writeC8D16D16(CO5300_W_PASET, ys, ys + h - 1);
    }
    _bus->writeCommand(CO5300_W_RAMWR);
  }
};
```

并加入过 `gap <x> <y>`（运行时设偏移，支持负值）、`edges`（画标定图形）命令。
真机验证证明偏移只能移动缺口，不能补回内容，因此自定义地址窗口和这些实验命令均已删除。

## 4. 已验证的事实

### 4.1 MADCTL 四角度实测（LVGL 不旋转）

| MADCTL | 实测 |
|--------|------|
| `0x60` | 用户确认：**USB 口朝下 + 内容正立**（即本项目要的装机姿态）|
| `0xC0` | 呈 180° |
| `0xA0` | USB 口朝上 |
| `0x20` | 仅 MV（不镜像）→ 用户反馈"方向反了"，故**镜像位是必需的** |

> 官方 BSP 的映射同样是 `rotation 0/1/2/3 → MADCTL 0x00/0x60/0xC0/0xA0`。

### 4.2 撕裂与渲染耗时

| 配置 | 撕裂 | 渲染最大 | 尖刺 |
|------|------|---------|------|
| 软件 0° | 无 | 22–69 ms | 无 |
| 软件 90° | **有** | 25–33 ms | — |
| 软件 180° | 无 | — | 无 |
| 软件 270° | **有** | 28–**1005** ms | **有** |
| **硬件 270°** | **无** | 24–25 ms | **无** ✅ |

### 4.3 用标定图形测出的**轴映射**（硬件 270°，MADCTL 0x60）

在**逻辑画面**四边画 10px 彩线（后改为不与 UI 撞色的洋红/青/亮绿/白）：

| 逻辑边 | 落在物理位置 |
|--------|-------------|
| `x=0`（左） | **上** |
| `x=465`（右） | **下** |
| `y=0`（上） | **右** |
| `y=465`（下） | **左** |

即：物理位置 ≈ 逻辑坐标旋转 90°（`px = 465 - y`, `py = x` 之一）。

### 4.4 偏移标定

在逻辑边界画一圈细黑环，请用户目视"**黑环到屏幕边框的间距是否四周均匀**"：

| gap | 用户反馈 |
|-----|---------|
| (0, 0) | 不均匀 |
| (0, 6) | 好多了，但仍**左宽右窄** |
| (0, 12) | 变成**右宽左窄** |
| **(0, 9)** | 四周接近均匀，但相对软件旋转基准仍偏 1 px |

> 后续照片证明：圆环间距和四边彩线只能说明地址写入到达边缘，不能证明
> 466×466 内容与面板可见窗口逐像素重合；因此不能据此把 `(0,8)` 判定为正确值。

## 5. 硬件旋转后左右黑缺口

### 5.1 根因

旧推导把 CO5300 当成使用通用 MADCTL 坐标公式的 480×480 控制器，并据此把
原生偏移 `(6,0)` 逆变换成 `(0,8)`。这个推导与真机结果不符：移动偏移只能改变
缺口位置，不能补回内容；扩写完整 480×480 并补背景后，左右两边反而同时出现黑弦。

决定性差异来自厂商 ESP-IDF BSP：它初始化时只调用一次
`esp_lcd_panel_set_gap(panel_handle, 0x06, 0)`，之后切换 0°/90°/180°/270° 时
仅写 `MADCTL=0x00/0x60/0xC0/0xA0`，从不换轴或重算 gap。说明此面板的 MADCTL
扫描映射不能套用此前的通用公式，主控再做一次逆变换反而会造成二次偏移。

### 5.2 最终采用：厂商硬件旋转

- 默认 `DISPLAY_ROT=0`，启动时不旋转，显示完整且动画开销最低。
- 90°/270° 由 MADCTL 完成，LVGL 保持 `LV_DISP_ROT_NONE`，避免 CPU 逐像素转置。
- 所有硬件方向固定使用厂商 BSP 的原生 gap `(6,0)`；不再继续尝试经验偏移值。
- 0°/180° 保留已验证的 LVGL 低开销路径。
- 旋转策略版本升级时会一次性把旧 NVS 方向重置为 0°；之后用户从 App 设置的方向仍会持久化。
- 接受 90°/270° 下边缘黑缺口，优先保证秒针、速度指针和触摸滑页的实时性。

最终固件真机验证（2026-10-14）：

| 检查项 | 结果 |
|--------|------|
| 编译 | 通过；清理实验代码后 Flash `1,804,467 B (57%)`，静态 RAM `127,388 B (38%)` |
| 烧录与校验 | 通过；esptool 写入后哈希校验成功 |
| 默认方向 | `LVGL=0°`、`MADCTL=0x00`、触摸变换档 `0` |
| 临时切到 270° | `MADCTL=0x60`、触摸变换档 `3`，硬件旋转生效 |
| 再切回 0° | `MADCTL=0x00`、触摸变换档 `0`，恢复正常 |
| 270° 动态刷新 | 渲染最大约 `27–28 ms`，无软件转置缓冲 |
| PSRAM | 空闲约 `6.52 MB`，较转置候选多约 `434 KB` |

### 5.3 已否决：自定义 flush 软件转置

为验证黑缺口是否只能由硬件旋转引起，曾实现以下候选：面板固定
`MADCTL=0x00, gap=(6,0)`，LVGL 保持不旋转，在 `disp_flush_cb()` 中把每个脏区
按 16×16 分块转置到 PSRAM，再以原生方向写屏。

真机结果：

| 指标 | 结果 |
|------|------|
| 黑缺口 | **完全消失**，用户确认显示完整 |
| 空闲主循环 | `198–199 次/秒`，单次渲染 `2–5 ms` |
| 速度页局部更新 | 渲染最大约 `28–32 ms`，其中 flush 最大约 `14–15 ms` |
| PSRAM 全帧整屏更新 | 单帧最大约 `121 ms`，其中 flush 最大约 `62 ms` |
| 内部 1/10 屏缓冲 A/B | 整屏约 `105 ms`，旋转与传输累计约 `65 ms` |
| 主观结果 | 秒针明显卡顿，左右滑动明显卡顿，用户不可接受 |

空闲时循环频率稳定，BLE、触摸和其他任务没有持续占用，因此已排除“其他进程阻塞”。
瓶颈就是软件像素转置与同步 QSPI 提交；滑页会连续整屏无效化，实际只有约 8–10 FPS。
内部 SRAM 分块只带来小幅改善，无法解决观感问题。

**结论：不要再次恢复或重复验证自定义 flush 转置方案。** 它只能换取显示完整，代价是
所有动态 UI 的实时性下降。正式固件已经删除转置函数和约 434 KB 的旋转缓冲。

### 5.6 已排除方向（历史诊断记录）

以下是定位完成前的假设，保留供以后排查类似问题时参考：

1. **MADCTL 0x60 是否真的等价于"旋转 270°"？**
   标定结果（§4.3）显示逻辑边 → 物理边的映射成立，但**是否含镜像**尚未逐点验证。
   若含镜像，则"内容完整"与"看起来缺一块"可以同时成立（镜像 + 偏移）。
2. **面板可见区是否真的 466×466？**
   官方 BSP 只设了列偏移 6、行偏移 0；但标定出的最优偏移是 9（不是 6）。
   怀疑**行方向也有偏移**（例如可见行范围不是 [0,465]）。
3. **`_xStart/_yStart` 之外，库是否还有别处影响寻址？**
   `Arduino_TFT::setRotation()` 还会改 `_width/_height`（方形屏无影响）与 `_current*`。
4. **LVGL 侧**：`sw_rotate=1` 且 `rotated=NONE` 时，`lv_refr.c` 是否仍走某条特殊路径？
   （`disp_drv.rotated` 已确认是 `LV_DISP_ROT_NONE`）
5. **建议的诊断手段**：把面板 GRAM 读回（CO5300 `0x2E RAMRD`，若 QSPI 读通路可用），
   或画一个**已知坐标的稀疏网格**，从照片反解仿射变换矩阵（含镜像与否）。

## 6. 本轮同时修复的问题（已完成，供参考）

### 6.1 「点一下屏幕就黑屏重启」（**已修复**）

- **现象**：点屏幕 → 黑一下 → 重启回固件初始状态（复位原因码 5 = 中断看门狗）
- **根因**：`touch_sample_cb()` 是 **100Hz esp_timer 回调**，
  其中「抬起且有位移」分支**在 `portENTER_CRITICAL()` / `portEXIT_CRITICAL()` 之间
  调用了 `Serial.printf()`** → 关中断状态下等 UART FIFO → 超过 300 ms → IWDT 复位
- **为什么只有点屏幕触发**：那两处打印只在"抬起且有位移"时执行
- **修复**：日志值先存局部变量，**出了临界区再打印**；并全文件扫描确认无同类问题
- **验证**：用户连点十余次不再重启；日志 14 条触摸事件正常，uptime 连续增长

### 6.2 触摸坐标变换（硬件旋转必需）

硬件旋转时 LVGL 不做旋转，故触摸坐标必须自己变换。
在**采样处**变换（`touch_sample_cb`），使 LVGL 的 indev 与 flick 手势判定**都自动正确**：

| 档位 | 实测 |
|------|------|
| 0 不变换 | 错位 |
| 1 顺时针 90° | 能响应但方向反了 |
| **3 逆时针 90°** | ✅ **完全跟手**（270° 的默认）|

同时因 `s_display_rot = 0`，`flick_delta_to_logical()` 自然退化为空操作。

### 6.3 MADCTL 是寄存器，NVS 记不住

必须持久化并在启动时重放（`restore_display_rotation()` 读 NVS 的 `rot`）。
本轮踩过：一次 IWDT 复位后方向跳回默认。

## 7. 当前复现与调试手段

### 串口命令

| 命令 | 作用 |
|------|------|
| `lvrot [0-3]` | 临时切换正式旋转策略，不写入 NVS |
| `ble` / `face N` / `bright N` | 状态查询 / 切表盘 / 亮度 |

诊断期间使用过的 `gap`、`edges`、`madctl`、`librot`、`swrot`、`hwrot`、
`touchrot`、`te` 和 `bufmode` 命令已在结论确定后删除，避免误入已否决路径。

### 构建（**必须先同步共享源码**）

```bash
tools/sync_firmware.sh          # simulator/ui/ → firmware/dashboard/（单一真源）
arduino-cli compile \
  --fqbn "esp32:esp32:esp32s3:FlashSize=16M,PartitionScheme=app3M_fat9M_16MB,USBMode=hwcdc,CDCOnBoot=cdc,PSRAM=opi" \
  --build-property "compiler.cpp.extra_flags=-DESP32QSPI_MAX_PIXELS_AT_ONCE=4096" \
  --libraries reference/ESP32-S3-Touch-AMOLED-1.75/examples/arduino/libraries \
  firmware/dashboard
```

### 模拟器（离线复现 UI）

```bash
cd simulator && make
./dashboard_sim --page 2 --speed 88 --rot 270 --offscreen --ms 2500 --shot /tmp/a.bmp
```

## 十二、硬件旋转的「局部遮蔽」问题（**未解决，已搁置**）

> 状态：**已知缺陷，暂缓**。用户决定"先记录文档，之后再弄"。
> 最后更新：2026-10-14。
> **动手前请先读完本节，尤其"已试过且无效的修法"——避免重复走弯路。**

### 12.1 现象

**启用面板硬件旋转（90° / 270°，MADCTL）时，速度表盘会出现局部遮蔽**
（用户描述："左侧缺一角"、"左方跟下方有一些遮蔽"、"胶囊 / BT OFF 那一块缺了"）。

- 软件旋转（0° / 180°）**不会**出现
- 用户最终归纳：**只要走硬件旋转就有这个现象**

### 12.2 已确证的事实

| 项 | 结论 | 依据 |
|----|------|------|
| 轴映射 | 逻辑 `x=0`→物理**上**、`x=465`→**下**、`y=0`→**右**、`y=465`→**左** | 四边 10px 彩线 + 照片实测 |
| 偏移标定 | `(0,6)` 左宽右窄 → `(0,12)` 右宽左窄 → **`(0,9)` 四周均匀** | 逻辑边界画细黑环，用户目视"四周间距是否均匀" |
| 但 | **间距均匀 ≠ 内容完整** —— 即使四周均匀，遮蔽仍在 | 用户实拍确认 |
| 模拟器对照 | `--rot 0` 与 `--rot 270` 的渲染**逐像素等价**（连"圆外内容像素数"都是同一个值）| 程序比对 |
| 被怀疑的 UI 元素 | 底部胶囊 `subdial`（86×86，`LV_ALIGN_BOTTOM_MID, 0, -8`，y≈372..458）**本身在画面内** | 读 `simulator/ui/ui_speed.c` |
| 面板原生偏移 | 厂商 BSP 为 **6 列**（`esp_lcd_panel_set_gap(0x06, 0)`），但本机标定出的是 **9** | 代码 + 现场标定 |

### 12.3 一次关键观察（后又被推翻）

用户曾报告：**"开机就是 270° 会有遮蔽；但从 270° 切到别的角度再切回 270° 就正常"**。
据此推测是"改 MADCTL 前已写入 GRAM 的内容错位残留，需再写一遍整屏清掉"。

### 12.4 ⚠️ 已试过且**无效**的修法（不要再试同样的）

| 尝试 | 结果 |
|------|------|
| 重写 `writeAddrWindow()`，把地址偏移改成**有符号** `int16_t`（库的 `_xStart` 是 `uint8_t`，只能加不能减）| 能标定出各种偏移，**遮蔽依旧** |
| 偏移扫参 `(0,6)` / `(0,9)` / `(0,12)` / 负值 | 只影响"黑环间距是否均匀"，**遮蔽依旧** |
| **每次开机自动"切走再切回"**（复刻那个"有效"路径：`away=(target+90)%360` 再切回 `target`）| **无效**。日志确认两次 `set_display_rotation()` 都执行了（序列 `0° → 270°`），遮蔽依旧 —— 那条"切走再切回就好了"的观察**站不住** |

> 撤除说明：该"切走再切回"已从上位机代码中删除（每次开机白做两次整屏重绘，
> 约 300ms）。`dashboard.ino` 的 `loop()` 里留有留档注释。

### 12.5 尚未排除的方向（供后续接手）

1. **MADCTL 0x60 是否真的等价于"旋转 270°"，还是含镜像？**
   轴映射（12.2）只验证了四条边的落点，**未逐点验证是否含镜像**。
   若含镜像，"内容完整"与"看起来缺一块"可以同时成立。
2. **面板可见区是否真的 466×466？**
   官方只设了列偏移 6、行偏移 0；但本机标定出 9。
   怀疑**行方向也有偏移**（可见行范围可能不是 [0,465]）。
3. **建议的取证手段**：画一个**已知坐标的稀疏网格**，从照片反解**仿射变换矩阵**（含是否镜像）
   —— 比"看四条边"信息量大得多，可直接判定 2×3 矩阵的每一项。
4. 面板 GRAM 读回（CO5300 `0x2E RAMRD`），若 QSPI 读通路可用。

### 12.6 复现与调试手段

| 手段 | 说明 |
|------|------|
| `bufmode psram\|internal` | 切换 LVGL 绘制缓冲 |
| `lvrot 0\|1\|2\|3` | 临切方向（不写 NVS）——**用于 A/B：0° 正常 vs 270° 遮蔽** |
| `madctl <hex>` | 直写面板 MADCTL，单独验证硬件旋转 |
| `edges` | 画/清四边 10px 彩线 + 逻辑边界细黑环（标定用）|
| 模拟器 | `./dashboard_sim --page 2 --rot 270 --offscreen --shot x.bmp` |

> ⚠️ 早期标定线的红/黄/蓝与表盘本身的**橙红刻度撞色**，照片里量不准 ——
> 这也是当时误判"四条边都正常"的原因。标定一律用**洋红/青/亮绿/白**等 UI 不出现的颜色。
