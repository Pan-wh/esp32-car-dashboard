# Wi-Fi 照片上传：为什么放弃（踩坑复盘）

> **结论先行**：**这块板子的内部 RAM 撑不住「Wi-Fi + HTTP + SD 写入」** ✗
> → 照片导入改用 **SD 卡直接拷文件**（`tools/import_photos.sh`）。
> 本文记录**完整证据链**，避免以后有人（或 AI）再走一遍同样的弯路。

---

## 一、功能诉求

"像蓝牙那样，手机扫到设备热点、连上就能传图" —— 需求本身合理。
目标是让 App 把裁切好的 `.pgi` 上传到仪表 SD 卡。

---

## 二、走过的弯路（按时间顺序，每条都是真踩过的）

### 弯路 1：先做了 STA（连家里 Wi-Fi），用户否掉

最初担心"手机连热点会断掉原网络"，于是做成**设备连家里 Wi-Fi**（STA）。
用户直接指出：**"不能跟蓝牙一样，扫到设备 WiFi 连上就能传吗"** —— 对，AP 才是对的。
**教训**：**先按用户的使用直觉做**，不要用自己的技术顾虑替用户改需求。

### 弯路 2：`NEHotspotConfiguration` 的三个连环坑

| 现象 | 真因 | 修法 |
|------|------|------|
| `internal error` | 手机**已连着该热点**时 `apply` 返回 `internal`（不是 `alreadyAssociated`），而代码把它当失败 | 改为**尽力而为**，失败也继续上传 |
| `The network connection was lost` | **`apply` 会重新关联网络**，把正在用的连接拆掉 | 顺序改成**先直接 POST，失败才连热点** |
| 请求根本没发出去 | 缺 **`NSLocalNetworkUsageDescription`** —— iOS 14+ 访问私有 IP 需要本地网络权限，**没声明就不弹框、直接失败** | Info.plist 声明 + `NSAllowsLocalNetworking` |

**教训**：**iOS 的"本地网络"权限**是个隐形门槛，报错信息毫无指向性。

### 弯路 3：请求走了蜂窝网络

设备日志给出决定性证据：

    [上传] 热点客户端数：1     ← 手机确实连上了
    收到请求数：0              ← 但一个请求都没到

**连上了却什么都没到，只可能是路由** —— iOS 把"无互联网"的热点降级，流量默认走蜂窝。
试过 `allowsCellularAccess = false`，**但没能解决**。

### 弯路 4：设备 **panic 重启** ← 真正的第一因

最终从串口日志里抓到：

    Guru Meditation Error: Core 1 panic'ed (LoadProhibited). Exception was unhandled.
    EXCVADDR: 0x00000000

用 `addr2line` 解 backtrace，直接指到上传回调：

    WebServer::upload()  ← HTTPUpload 的 unique_ptr 是 NULL

**根因**：App 发的是 `application/octet-stream`，而 ESP32 的 `WebServer`
**只在 `multipart/form-data` 时才创建 upload 上下文** → 回调里解引用 NULL → 崩。
设备一崩，TCP 连接就断 → 手机端看到的就是 `-1005`。

**教训**：前几轮所有"网络问题"的表象（-1005 / 请求数为 0 / 重试无效），
**都是这个崩溃造成的**。**先看设备日志，别在客户端猜**。

### 弯路 5：修好崩溃后，堆不够 —— 这才是终点

转成 multipart 后上传**通了**，但紧接着：

    [上传] 拒绝：堆不足（3776 B < 6000 B）
    [上传] 拒绝：堆不足（2680 B）

**手机一连上热点，内部堆从 20 KB 掉到 2~4 KB**（AP 的 station 连接本身吃 ~17 KB），
而且**第一次上传后堆不再回收**。

### 弯路 6：换掉 WebServer 也没救

把 `WebServer` 换成裸 `WiFiServer` + 手写最小 HTTP（不用 `String`，
只有 1.2 KB 静态缓冲，请求体边收边写 SD）—— Flash 从 78% → 77%，
**但堆只从 23,828 → 22,780 B，几乎没变**。

**原因**：80 KB 的缺口来自 **ESP-IDF 的 Wi-Fi 协议栈本身**（约 50 KB+），
不是应用层能省的。**`WebServer` 只是压垮骆驼的最后一根稻草，不是主因。**

---

## 三、最终数据（决定性）

| 场景 | 内部堆 |
|------|--------|
| 不开 Wi-Fi | 约 **104 KB** |
| 开热点（无客户端）| **22~24 KB** |
| **手机连上热点** | **2~4 KB** ✗ |

`PSRAM 6.4 MB` **完全帮不上忙** —— Wi-Fi / HTTP / `String` 只能用**内部 RAM**。

---

## 四、结论与替代方案

**放弃 Wi-Fi 上传**，改用 **SD 卡直接拷文件**：

```bash
# 卡插电脑
tools/import_photos.sh          # 从 original/ 批量转 .pgi 到 photos/
# 卡插回仪表 → 划到照片表盘
```

优点：**零风险、不占内存、可批量、能处理 HEIC 与视频**。
缺点：每次加照片要拔卡。

**保留了的 Wi-Fi 能力**：
- **`GET /list`**（文件列表）与 **`POST /delete`**（删除）—— 它们只需要几百字节堆，
  实测**可用**；
- 只放弃了 **`POST /upload`**（它要 1 KB 缓冲 + SD 写路径 + 长连接）。

---

## 五、如果以后还想做上传

按代价从低到高：

1. **换更强的板子**（PSRAM 更大 + 内部 RAM 更多，如 ESP32-S3 带 8MB PSRAM 的模组
   仍不够 —— 关键在**内部 RAM**，所以基本要换型号）；
2. **上传前临时关掉不必要的子系统**（LVGL 定时器、其他驱动）腾几 KB ——
   但实测缺口是 **~18 KB**，腾不出来；
3. **接受"上传必崩/被拒"**，只保留列表与删除。

> **一句话**：这不是代码写得好不好的问题，是**硬件内存不够**。
