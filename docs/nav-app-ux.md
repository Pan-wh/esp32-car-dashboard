## 一、现状与问题

### 1.1 当前界面结构（2026-10-15 实测）

`ContentView.swift` 的 `navTab` 共 **214 行**、**7 个 Section**，顺序如下：

| # | Section | 内容 | 何时可见 |
|---|---------|------|---------|
| 1 | 导航状态 | 状态文字、剩余距离、全程、重算次数、错误 | 恒显示 |
| 2 | 目的地 | 输入框、输入提示列表、地名候选列表、错误 | 恒显示 |
| 3 | 路线方案 | 加载指示、候选列表（策略名+距离+耗时）| 条件下 |
| 4 | 周边搜索 | 输入框、搜索按钮、结果列表 | 恒显示 |
| 5 | 当前道路 / 路况 | 道路名、路况 | 导航中 |
| 6 | 开始 / 停止 | 一个按钮（语义随状态变）| 恒显示 |
| 7 | 网关 | 地址、令牌 | 恒显示 |

### 1.2 场景 A：去一个没去过的地方（逐步复盘）

| # | 用户动作 | 系统反应 | 评价 |
|---|---------|---------|------|
| 1 | 打开导航页 | 7 个 Section 平铺 | 无主次 ✗ |
| 2 | 点「目的地」框 | — | |
| 3 | 打字「北京南」 | 300ms 防抖 → `/tips` → 出候选 | ✓ |
| 4 | **点一个候选** | **立即触发取路线**（无确认）| **跳步** ✗ |
| 5 | — | 等 1~3 秒（网关串行 3 次高德请求）| 无进度感 ✗ |
| 6 | — | 路线方案出现在**下方** | **可能看不见** ✗ |
| 7 | 点一条候选 | 开始导航 | ✓ |

**8 步、2 处意外跳转。**

### 1.3 场景 B：用户先点了「开始导航」

| # | 用户动作 | 系统反应 |
|---|---------|---------|
| 1 | **点「开始导航」** | 查地名 → 取候选 |
| 2 | — | **还是要再点一条路线** |

> 用户以为点了就开始了，结果只是换了个地方让他再点一次。

### 1.4 问题清单（按严重度）

#### 🔴 P0-1 同一按钮在不同时刻含义不同

「开始导航」按钮：

| 此刻状态 | 点了会怎样 |
|---------|-----------|
| 有目的地、未选路线 | 取候选 → **还要再点一次** |
| 刚选了候选 | 该按钮**此刻是多余的** |

同一个位置、同一个文案、两种行为 —— 典型交互反模式。

#### 🔴 P0-2 点「输入提示」= 立即取路线，缺少确认

用户点候选的意图常是**"就选这个地点"**，系统理解成**"立刻规划路线"**并跳走，
中间没有可反悔的位置。

#### 🟠 P1-1 三个列表外观相同、语义不同

`/tips`（输入提示）、`/geocode`（地名多结果）、`/around`（周边搜索）
都是"点了就跳到路线方案"，用户无法区分。
且**「周边搜索」被做成与「目的地」平级的 Section** —— 它本质只是
**另一种选目的地的方式**，不该并列。

#### 🟠 P1-2 路线候选缺少决策信息

现在只有：策略名 + 距离 + 耗时。缺的恰是用户最关心的：

| 缺什么 | 为什么重要 |
|--------|-----------|
| **ETA（几点到）** | 用户算的是"几点能到"，不是"多少秒" |
| **哪条建议走** | "速度优先/不走高速/距离最短"是机器语言 |
| **路况影响** | 堵不堵直接影响选择 |

#### 🟠 P1-3 「导航状态」占首屏最贵位置，多数时间是空的

未导航时只有"未开始" + 空白。

#### 🟡 P2-1 「网关」配置混在主流程

开发期配置占了整整一个 Section，日常使用不需要看到。

#### 🟡 P2-2 没有「常用 / 最近目的地」

每次都要重新打字。

#### 🟡 P2-3 结束导航 = 结束驾驶（耦合）

用户可能只想结束导航、继续记录行程。

#### 🟡 P2-4 导航中换路线要「停止导航」重来

#### ⚪ P3 看不到「我被定位到哪了」

只有导航中的「当前道路」。而这恰恰是排查定位失败**最重要的信息** ——
本项目 2026-10-15 连续踩了三次定位相关的坑（见 §1.6），有个位置显示会省很多时间。

### 1.5 设计原则（本次重设计遵循）

1. **一个界面只做一件事** —— 做完自动进入下一步，不要求用户"再点一次"。
2. **每一步都能退回来** —— 状态机式，而不是堆 Section。
3. **按钮文案 = 实际行为** —— 不做"同一个按钮两种含义"。
4. **给决策信息，不给参数** —— "推荐/最短/不走高速"，不是"策略 0/2/6"。
5. **失败要能自证** —— 定位/网关出问题时，界面要显示**排查所需的事实**。

### 1.6 根因（如实记录）

> **把"功能清单"直接铺成了界面** —— 每接一个网关端点就加一个 Section，
> 没有回头整理成**用户的一条动线**。

2026-10-15 当天连续暴露的三个 bug 都与此有关：

| Bug | 现象 | 根因 |
|-----|------|------|
| 四个解码器字段名全写错 | "查询失败" | 凭印象写契约，没核对真实返回 |
| 取路线前的循环依赖 | "还没有定位" | 改成"先选路线"却没把定位一起拉起来 |
| 等错了对象 | 仍报"拿不到定位" | 等 `lastVehicleWGS84`（只在时钟里流动），而没直接读 `LocationService` |

**共同点**：改动只在代码层面自洽，**没有在真机上把完整动线走一遍**。
本文的状态机正是为了让动线**可见、可逐步验收**。

## 二、目标状态机

核心：**四状态、单向推进、可回退**。

```
   ┌──────────────────────────────────────────────────────┐
   │                                                      │
   ▼                                                      │
[准备] ──打字/点快捷──▶ [选地点] ──点一个──▶ [选路线] ──开始导航──▶ [导航中]
   ▲                      │                    │                    │
   │                      │ ✕ 清空              │ ← 返回             │ 结束导航
   └──────────────────────┴────────────────────┘                    │
                                                                    ▼
                                                                 [准备]
```

**状态判定（纯函数，可单测）**：

| 状态 | 条件 |
|------|------|
| 导航中 | `isNavigating == true` |
| 选路线 | 有 `routeCandidates` 且未开始导航 |
| 选地点 | 搜索框非空 且 无候选 |
| 准备 | 其它 |

> ⚠️ 这个判定要抽成**纯函数**并配单测（与 `BLEConnectionPolicy` 同一做法）——
> 上一轮"按钮语义随状态变"正是因为判定散落在 `if` 里，没人能一眼看全。

## 三、逐状态规格

### 状态 1：准备

```
┌─────────────────────────────────────────┐
│  导航                                    │
│                                          │
│  🔍 [搜索目的地…]                        │  ← 唯一入口
│                                          │
│  ⭐ 常用                                  │
│     家 · 公司                            │  ← 可长按删除
│  🕐 最近                                  │
│     北京南站 · 首都机场                   │
│                                          │
│  📍 当前位置                              │
│     北京市东城区南池子大街                 │  ← P3：兼作定位自检
│     （定位中… / 定位失败：<具体原因>）      │
│                                          │
│  ─────────────────────────────────────   │
│  ⚙️ 设置（网关地址/令牌 → 移到「设置」页） │
└─────────────────────────────────────────┘
```

**要点**：
- 搜索框是**唯一入口**（合并原「目的地」+「周边搜索」）
- 当前位置**兼作定位自检**：拿不到定位时直接显示**原因**（权限被拒 / 未授权 / 超时）
- 「网关」移出主界面

**边界**：
- 定位失败时，搜索框**仍可用**（可以搜地点），只是取路线时会提示
- 常用/最近为空时，该区不显示（不留空壳）

### 状态 2：选地点

```
┌─────────────────────────────────────────┐
│  🔍 [北京南                    ✕]        │
│  ─────────────────────────────────────   │
│  📍 北京南站(南进站口)                    │  ← tips/geocode/around
│     北京市丰台区 · 距我 1.2 km            │     统一成一个列表
│  📍 北京南站(北进站口)                    │
│     北京市丰台区 · 距我 1.4 km            │
│  ─────────────────────────────────────   │
│  🔧 附近找： 加油站 · 停车场 · 充电站      │  ← 周边搜索降级为快捷筛选
└─────────────────────────────────────────┘
```

**要点**：
- 三类结果**合并成一个列表**（都带"距我 x km"）
- 「周边搜索」不再是独立 Section，而是**搜索框下方的快捷筛选**
- 点任意一条 → **直接进入状态 3**（不再要求额外确认）

**边界**：
- 搜索无结果 → 显示"没找到「xxx」"，并给快捷筛选兜底
- 网络失败 → 显示**具体错误**（HTTP 码 / 解码细节），不只说"查询失败"

### 状态 3：选路线

```
┌─────────────────────────────────────────┐
│  ← 去 北京南站(南进站口)                  │
│  ┌─────────────────────────────────────┐ │
│  │ ✅ ① 17 分钟 · 14:32 到             │ │ ← 默认高亮最快
│  │      16.8 km · 推荐                 │ │
│  ├─────────────────────────────────────┤ │
│  │    ② 18 分钟 · 14:33 到             │ │
│  │      16.1 km · 不走高速             │ │
│  ├─────────────────────────────────────┤ │
│  │    ③ 21 分钟 · 14:36 到             │ │
│  │      15.2 km · 最短                 │ │
│  └─────────────────────────────────────┘ │
│                                          │
│           [  开始导航  ]                 │  ← 唯一的确认动作
└─────────────────────────────────────────┘
```

**要点**：
- **ETA 放在最前**（"14:32 到"比"17 分钟"直观）
- 策略名换**人话**：`0 → 推荐`、`2 → 最短`、`6 → 不走高速`
- **默认选中耗时最短的一条**（用户最常选它，少一次点击）
- 「开始导航」**只在此状态出现** —— 语义唯一

**边界**：
- 只取到 1 条候选 → 自动选中 + 直接显示"开始导航"（不显示单选列表）
- 取候选失败 → 留在本状态并显示原因 + 「重试」

### 状态 4：导航中

```
┌─────────────────────────────────────────┐
│  ↰ 左转 380 m                            │
│  剩余 12.3 km · 预计 14:32 到达           │  ← ETA 最显眼
│  ─────────────────────────────────────   │
│  🛣 南池子大街   🚗 缓行                  │
│  ─────────────────────────────────────   │
│  [ 换一条路线 ]                          │  ← 不用停止再重来
│                                          │
│  [ 结束导航 ]                            │
│  □ 同时结束行程记录                       │  ← P2-3：解耦
└─────────────────────────────────────────┘
```

**边界**：
- 「换一条路线」→ 回到状态 3（**保留当前位置为起点**），当前路线高亮
- 未勾选"同时结束行程"时，只发 `idle` 给仪表，**继续发遥测**

## 六、待评审确认的问题

1. **常用 / 最近目的地**存哪里？本地 `UserDefaults`（简单）还是也同步到网关（跨设备）？
   → 建议 **`UserDefaults`**：自用场景，跨设备无价值。
2. **「换一条路线」** 是否重新请求网关？
   → 建议**重新请求**：路况随时在变，用旧候选可能已经堵了。
   但应**只在用户点按时请求**（每次 3 次高德调用），不做后台刷新。
3. **圆屏仪表上是否也要体现 ETA？**
   → 本文只覆盖 App。仪表侧改动需另开任务（涉及固件与 BLE 字段）。

## 七、附：状态判定伪代码（供评审）

```swift
enum NavUIState {
    case ready          // 准备：搜索目的地
    case pickingPlace   // 选地点：有输入、无候选
    case pickingRoute   // 选路线：有候选、未开始
    case navigating     // 导航中
}

func navUIState(isNavigating: Bool,
                hasCandidates: Bool,
                queryIsEmpty: Bool,
                isLoading: Bool) -> NavUIState {
    if isNavigating { return .navigating }
    if hasCandidates { return .pickingRoute }
    if !queryIsEmpty || isLoading { return .pickingPlace }
    return .ready
}
```

> 注意：`isLoading` 也算「选地点」，否则取候选期间界面会闪回「准备」，
> 用户会以为刚才的操作没生效 —— 这正是现状"点了候选没反应"的观感来源之一。

## 八、实施记录（2026-10-15）

### 8.1 与设计的偏差

| 项 | 设计 | 实施 | 原因 |
|----|------|------|------|
| 代码位置 | 改 `ContentView.swift` | **新建 `Nav/NavTabView.swift`** | ContentView 已 763 行；抽出来正好符合"一个界面只做一件事"，也让删除旧代码的边界清晰 |
| 「换一条路线」 | 未明确是否重新请求 | **重新请求** | 路况随时在变，旧候选可能已经堵了。只在用户点按时请求，不做后台刷新 |
| 常用/最近存储 | 待确认 | **`UserDefaults`** | 自用场景，跨设备无价值 |
| 「开始导航」 | 只说"只在选路线态出现" | 另加一条：**点它 = 同时启动驾驶会话** | 与既有规则「开始导航等同于开始驾驶」一致。否则会出现"导航开始了但仪表速度不动" |

### 8.2 设计里没写、实施时补的

- **剩余 ETA（导航中）**：`NavSnapshot` 里**没有剩余耗时**字段，只有剩余里程。
  实现按 `剩余里程 / 总里程` 缩放总耗时估算 —— 是估算，但用户开车时想知道的是
  "我几点到"，比只显示"还剩 12.3 km"有用得多。
- **列表里的「距我 x km」**：tips/geocode 两种来源都不带距离，用 Haversine 现算。
- **三类结果去重**：同名或同坐标只显示一条（`NavPlaceRow.id`）。

### 8.3 顺带修好的一个**静默失效的测试目标**

`make run` 长期以退出码 2 结束、**其后的 Swift 测试全都不执行** ——
因为 `test_nav_sim` 编译失败（26 个 "cannot find ... in scope"）。

根因：一次重构把 `RouteBundle / RouteProvider / RerouteDispatcher` 移进了
`GatewayClient.swift`，但 `tests/Makefile` 的 `SIM_SRC` 没同步。
