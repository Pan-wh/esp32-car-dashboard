## 三、硬约束（已核实，决定方案形状）

### 3.1 资源余量

| 资源 | 现状 | 余量 |
|------|------|------|
| Flash（3 MB 分区）| 1,901,259 B（60%）| **约 1215 KB** |
| PSRAM（8 MB）| 5 张烘焙图约 1.4 MB | **约 6.5 MB** |
| SD 卡 | SDHC 7.3 GB | **可用 5.74 GB** |

**一帧全屏 RGB565 = 424 KB** ✗ → 照片**必须放 SD 卡** ✓（与 D-010 一致）

### 3.2 单帧体积（466×466 = 217,156 像素）

| 格式 | 每帧 |
|------|------|
| RGB565 原始 | 424.1 KB |
| **8bpp 索引** | **212.1 KB**（+1 KB 调色板）|
| 8bpp + RLE（2:1）| 约 106 KB |

### 3.3 ⚠️ BLE **不能**传图片（所以必须 Wi-Fi）

**BLE 实测有效吞吐约 1 KB/s**（依据：地图窗口 50 条消息 2~3 秒、每条 ≤180 B）：

| 传什么 | BLE 需要 |
|--------|---------|
| 全屏单张（212 KB）| **212 秒** |
| 10 帧动图（2.1 MB）| **约 35 分钟** ✗ |

> 这是"传输走 Wi-Fi"的**直接原因**，不是偏好问题。

### 3.4 设备端解码与刷新

| 环节 | 成本 | 来源 |
|------|------|------|
| 索引图逐像素解码（LVGL 内置）| 全屏 **+45 ms** | `ui_img_inflate.c` 真机实测 |
| 全屏 flush（QSPI 80 MHz）| **43 ms** | PROGRESS §六 |

> **动图帧率上限：全屏 7~11 fps；240×240 可达 20~30 fps。**

### 3.5 🔴 AMOLED 烧屏（**照片表盘的核心风险**）

面板是 **CO5300 AMOLED**，烧屏**永久不可逆**。照片表盘会长时间显示同一画面 ✗ ——
这是 AMOLED 最怕的用法。防护见 §六。

## 四、照片表盘设计

### 4.1 表盘清单（5 → 6）

| id | name | label | group | 内容 |
|----|------|-------|-------|------|
| 0 | analog | Analog | clock | 模拟时钟 |
| 1 | digital | Digital | clock | 数字时钟 |
| 2 | speed | Speed | speed | 速度表 |
| 3 | color | Color | clock | 多彩时钟 |
| 4 | nav | Nav | nav | 导航卡片 |
| **5** | **photo** | **Photo** | **photo** | **照片（静态 + 动图，混合轮播）** |

- 注册进 `ui_pages` → 出现在**滑动序列** ✓
- 归 `UI_FACE_GROUP_PHOTO` → App 里显示在"照片"组 ✓
- **默认启用** ✓；SD 卡无照片时显示**占位提示**（不空白）
- 可用现成的 `face_enabled` 机制**隐藏**

### 4.2 为什么合并成一个表盘（v4 的决定）

| 理由 | 说明 |
|------|------|
| **一个相册才自然** | 用户想的是"我的照片轮播"，而不是"静态相册"和"动图相册"两个抽屉。**静态与动图混排才是电子相框的常见用法** |
| **一套代码** | 只有一条读取/解码路径、一个定时器 —— 拆成两个要维护两份几乎相同的逻辑 |
| **性能没有损失** | 当前这张是单帧时，定时器只是**等待**到切换时间（不跑逐帧），开销与"独立的静态表盘"完全相同 |
| **表盘更少** | 6 个而非 7 个，滑动序列更短 |
| **烧屏更好防** | 静态与动图交替出现，画面变化更丰富 |

**唯一的"损失"**：不能单独做"只看静态"的相册 ✗ —— 但这需求很弱：
**不放动图进去，就等于是静态相册** ✓

### 4.3 轮播（幻灯片）—— 一个定时器覆盖两种内容

```
/photos/            ← 照片表盘的全部内容（一个目录）
   01_sunset.pgi    （1 帧 = 静态）
   02_family.pgi    （1 帧）
   03_cat.pgi       （24 帧 = 动图）
   04_dog.pgi       （18 帧）
```

**播放逻辑**（`帧数` 决定行为，不需要额外类型标记）：

```
显示第 i 个文件：
  ├ 读文件头，取帧数 N 与 fps
  ├ 若 N == 1（静态）：
  │     ├ 显示唯一那帧
  │     └ 等 slide_interval（默认 30 s）→ 切下一个文件
  └ 若 N > 1（动图）：
        ├ 按 fps 逐帧播放
        ├ 播完一轮 → 再循环一轮（共 2 轮，避免一张动图霸屏）
        └ 之后 → 切下一个文件
```

**共同规则**：

- 顺序：**文件名排序**（用户可用 `01_`、`02_` 自己排）；
- **只在照片表盘可见时运行**（切走即停 ✓ 省电 ✓）；
- **只有一个文件**时：照常显示，但**强制开启像素位移**（§六）；
- **切换时做一次像素位移**（§六）。

### 4.4 占位状态（必须设计，否则首用体验很差）

| 情况 | 显示 |
|------|------|
| SD 卡未插入 | "未检测到 SD 卡" |
| `/photos/` 为空 | "还没有照片 · 用 App 上传" |
| 文件损坏 / 格式不支持 | 跳过该文件，显示下一个；全部失败则显示"照片读取失败" |
| 正在加载首帧 | 上一张画面或纯色 + 小提示（**不超过 1 秒**）|

---

### 4.5 三个开关（用户要求，App 可手动控制）

| 开关 | 默认 | 关掉后的行为 |
|------|------|-------------|
| **轮播** | **开** | **停在当前这张不动**（记住最后显示的那张，下次进表盘还是它）；⚠️ **此时强制开启像素位移** |
| **自动息屏** | **开**（30 min）| 屏幕**常亮**，不息屏 |
| **像素位移** | **开** | 画面完全静止（⚠️ 烧屏风险最高，见 §六）|

**它们的相互作用（重要，必须按这个实现）**：

```
轮播开 + 位移开  → 正常轮播，每次切图顺带位移
轮播开 + 位移关  → 正常轮播，但不位移
轮播关            → 停在一张 且 **强制位移开**（即使用户把位移调成关，也要强制开）
                  ↑ 用户明确要求："不轮播时候就是像素位移的方法会开启"
```

**设置持久化**：三个开关 + 轮播间隔都写 **NVS**（与表盘/亮度同一套机制），
**重启后保持**。

**App 侧**：一张设置卡（见 §8.1），改动即时通过 BLE 下发 + 设备回执。

## 五、格式：`.pgi`（一个格式覆盖静态与动图）

```
┌ 文件头 32 B ─────────────────────────────┐
│ magic "PGI1" | 宽 u16 | 高 u16            │
│ 帧数 u16 | fps u8 | flags u8（bit0=逐帧调色板）│
├ 调色板 256×4 B（全局一份，或每帧一份）────┤
├ 帧索引表（帧数 × 8 B）───────────────────┤
│ 每帧：偏移 u32 | 长度 u32                  │
├ 帧数据（8bpp 索引流，可选 RLE）───────────┤
└──────────────────────────────────────────┘
```

- **帧数 == 1 → 静态照片**；**帧数 > 1 → 动图** —— **不需要额外的"类型"字段**
- 设备端只做**查表 / memcpy**，不解 GIF/PNG/JPEG ✓
- RLE 留作后补（等 §十 的 S1 实测读速再定）

## 六、🔴 AMOLED 烧屏防护（默认全开）

| # | 措施 | 说明 | 可配 |
|---|------|------|------|
| 1 | **轮播** | 画面整体变化是最好的防烧屏 | 间隔 10~300 s |
| 2 | **像素位移** | 每次切图 / 每 2 分钟整体平移 **±3 px**（四周各裁 3 px，不露边）| 开关 |
| 3 | **亮度上限** | 照片表盘下亮度**封顶 180** | 开关 |
| 4 | **自动息屏** | 30 分钟无交互 → 息屏（触摸唤醒）| 时长可配 |

**两条硬规则**：

- **不轮播时强制开启像素位移**（用户明确要求；目录只有 1 个文件时同理）；
- **禁止长期停在纯亮画面**（白底图）→ 此时自动降低亮度上限。

> ### ⚠️ 关于"全部关掉"
>
> 三个开关都可以手动关 —— **用户已知晓烧屏风险并接受**。
> 但实现上要**留一条记录**：当"轮播关 + 位移关 + 自动息屏关"**三者同时为关**时，
> 固件在启动日志里打一行警告（`[照片] 烧屏防护全部关闭`），便于日后排查
> "这块屏为什么有烙印"。**功能上不阻止**，只记录。

## 七、传输：Wi-Fi

### 7.1 流程

设备默认**不开 Wi-Fi**（省电、减攻击面）。App 点"上传照片"时：

```
App ──BLE {"cmd":"wifi","op":"on"}──▶ 设备
                                       ├ 开 AP（SSID/密码随机）
                                       ├ 屏幕显示 SSID + 密码 + IP
                                       └ 起 HTTP（只接受 /upload）
App ──连该 AP──▶ HTTP POST 文件 ──▶ 设备写入 /photos/
App ──BLE {"cmd":"wifi","op":"off"}──▶ 关 AP，恢复 BLE-only
```

### 7.2 关键约束

| 项 | 设计 |
|----|------|
| AP 生命周期 | **5 分钟无操作自动关闭**（防忘记关）|
| 认证 | 随机密码（屏幕 + BLE 告知 App）；**只接受一个客户端** |
| 写入范围 | **只能写 `/photos/`**，绝不暴露任意路径 |
| 文件名 | 设备生成（`p_<时间戳>.pgi`），不接受客户端指定路径 |
| 大小上限 | 单文件 ≤ 8 MB |
| 冲突 | 上传期间**暂停轮播**（避免同时读同一文件）|
| 失败 | 返回明确错误码（磁盘满 / 写入失败 / 超限），App 显示 |

### 7.3 ⚠️ 必须先验证的风险（Spike S2）

本板是 **octal PSRAM（opi）**，S3 上 **PSRAM 与 Wi-Fi 有已知的带宽/稳定性权衡**。
**开发前必须验**：开 AP + HTTP 传 1 MB，检查 ① 不崩 ② LVGL 渲染仍正常 ③ 实测吞吐。

**若不可行**，退路是 **SD 卡插拔**（把文件拷到 `/photos/`）—— 会失去 App 内上传体验，属降级。

## 八、App 端设计

### 8.1 照片管理（需求 C）

```
┌ 照片 ──────────────────────────────┐
│ [上传照片]  [上传动图]    ← 都进 /photos/  │
│ ─────────────────────────────     │
│ 照片 (5)                           │
│  📄 01_sunset.pgi   212 KB   [删]  │  ← 1 帧
│  📄 03_cat.pgi      1.8 MB   [删]  │  ← 24 帧（角标标"动图"）
│ ─────────────────────────────     │
│ SD 卡：SDHC 7.3 GB / 可用 5.74 GB  │
│ ─────────────────────────────     │
│ 轮播      [开]   间隔 [30 s ▾]     │
│ 自动息屏  [开]   时长 [30 min ▾]   │
│ 像素位移  [开]  ⚠️ 轮播关闭时强制开 │
│ [进入 Wi-Fi 上传]                  │
└────────────────────────────────────┘
```

- **上传**：选图/选视频 → 裁切预览 → 转 `.pgi` → Wi-Fi 上传
  （App 侧区分"静态"与"动图"只影响**转码时产出的帧数**，目录都是 `/photos/`）
- **删除**：BLE `{"cmd":"photo","op":"del","name":"..."}`（只允许删 `/photos/` 内）

### 8.2 裁切 / 预览 / 转 GIF（需求 E，**全 iOS 内置框架，零依赖**）

| 功能 | 框架 |
|------|------|
| 选图 / 选视频 | `PhotosPicker` |
| **裁切 + 圆屏预览** | `UIGraphicsImageRenderer` + 手势；**466×466 + 圆形遮罩，所见即所得** |
| **动图 → GIF** | `CGImageSource`（GIF / APNG / WebP / Live Photo）|
| **视频 → GIF** | `AVAssetImageGenerator` 抽帧 → `CGImageDestination` 写 GIF |
| **GIF/图片 → `.pgi`** | App 内量化（256 色）+ 打包；静态图产出 1 帧，动图产出 N 帧 |

### 8.3 SD 卡管理（需求 F）

| 操作 | BLE 消息 | 说明 |
|------|---------|------|
| 查状态 | `{"cmd":"sd","op":"info"}` | 挂载状态 / 类型 / 总容量 / 可用 / 照片数 |
| 列文件 | `{"cmd":"sd","op":"list"}` | 分页返回文件名、大小、**帧数**（区分静态/动图）|
| 删除 | `{"cmd":"photo","op":"del","name":"..."}` | 只允许删 `/photos/` 内 |
| **格式化** | `{"cmd":"sd","op":"format"}` | ⚠️ **建议不做**（见 §九 #5）|
| 查设置 | `{"cmd":"photo","op":"get"}` | 回 `{"slide":1,"interval":30,"screenoff":1,"screenoffMin":30,"shift":1}` |
| 改设置 | `{"cmd":"photo","op":"set","slide":0}` | 任一字段可单独下发；设备写 NVS 并回执 |

## 十点五、🔬 Spike 实测结果（2026-10-19，真机）

**S1（SD 读写）** 与 **S3（解码耗时）** 都已实测，命令在固件里（`sdbench` / `pgibench`）。

### 结果

| 项 | 数值 | 说明 |
|----|------|------|
| **SD 读速** | **2.37 MB/s** | 1-bit SDMMC 的**硬件上限**（这块板只接了 D0），换卡也不会更快 |
| SD 写速 | 0.16 MB/s | 只在 App 上传时用，不是瓶颈 |
| **解码一帧 466×466** | **平均 21 ms / 最慢 23 ms** | 比原先估计的 45 ms **还快**（那个 45 ms 是 LVGL 逐行解码，我们走的是"一次解到 PSRAM"）|
| 解析文件头 | 0 ms | 可忽略 |
| 全屏 flush | 43 ms | 已知值 |

### 由此得出的每帧成本

| 环节 | 耗时 | 占比 |
|------|------|------|
| **SD 读 217 KB** | **约 93 ms** | **58% ← 瓶颈** |
| 解码 | 23 ms | 14% |
| flush | 43 ms | 27% |
| **合计** | **约 159 ms** | **→ 6.3 fps** |

> **瓶颈是 SD 读，不是解码。** 这改变了 P2 的做法（见下）。

### 🔴 顺带发现并修掉一个存在已久的 bug

`SD_MMC.begin()` 的签名是：
`begin(mountpoint, mode1bit, format_if_mount_failed, **sdmmc_frequency**, maxOpenFiles)`

固件原来写的是 `begin("/sdcard", true, false, 5)`，注释以为是 `max_files` ——
**实际是 `sdmmc_frequency`，于是卡一直跑在 5 kHz**。
实测：**读 0.05 MB/s**（读 1 MB 要 21 秒）。
改成 `SDMMC_FREQ_HIGHSPEED` 后：**2.37 MB/s（47 倍）**。

> 这个 bug 之前没被发现，是因为 SD 卡只被用来"列个目录"。**一旦要读图片就致命**。

### P2 的实现调整（基于实测）

原计划"直接按 fps 逐帧读+解+画"，只能到 **6.3 fps** ✗。改为：

1. **分片预读（read-ahead）**：把下一帧按 **32 KB 一片**、分摊到多个主循环里读，
   **与当前帧的显示时间重叠** —— 主循环约 200 Hz，7 片 ≈ 35 ms 读完，不阻塞。
2. 这样每帧耗时 ≈ `max(读数, 解码+flush)` ≈ `max(93, 66)` = **93 ms → 10.8 fps** ✓
3. **若还不够**，再上 RLE（格式里已留 `flags` bit0）：
   2:1 压缩 → 读 46 ms → `max(46,66)` = 66 ms → **15 fps**。

**v1 目标定为 10 fps（分片预读，不上 RLE）**，RLE 留作后续可选项。

### S2 / S4 仍未验

- **S2（Wi-Fi + octal PSRAM 共存）** —— 到 P5 才需要；若不可行退回 SD 插拔。
- **S4（PSRAM 双缓冲余量）** —— 本次 S3 已实际分配过 2.1 MB 文件 + 424 KB 帧缓冲，
  未报分配失败；进 P2 时再用 `mem` 复核。

## 十一、开发前必须先验的 Spike

| # | 验证 | 怎么验 | 不行的退路 |
|---|------|--------|-----------|
| **S1** | SD 卡 1-bit 读速 | 串口命令读 1 MB 计时 | 上 RLE / 降分辨率 |
| **S2** | **Wi-Fi + octal PSRAM 共存** ⚠️ | 起 AP + HTTP 传 1 MB | 退回 **SD 卡插拔**（降级）|
| **S3** | 全屏解码 + flush 真实耗时 | 计时打印 | 限定 240×240 |
| **S4** | PSRAM 双缓冲（850 KB）+ 现有 1.4 MB 余量 | `mem` 观察 | 减缓冲 / 单缓冲 |

> **S1+S3 约半天**（只需串口命令与日志，不动 UI）；
> **S2 是唯一的"可能推翻方案"的风险**，建议紧跟着做。

## 十二、明确不做

| 不做 | 原因 |
|------|------|
| 设备端解 GIF/PNG/JPEG | 无硬件解码，软解 50~100 ms，动图不可行 |
| 图片进 Flash | 余量 1.2 MB，装不下一帧 |
| BLE 传图片 | 1 KB/s，动图要半小时（§3.3）|
| 独立的"相框模式"覆盖层 | 用户已定：要**表盘** |
| 照片上叠加时钟/速度 | 用户要求纯照片 |
| 拆成"静态/动图"两个表盘 | 一个表盘就能覆盖（§4.2），拆开是重复维护 |
| 淡入淡出切换 | 466×466 上要多两帧缓冲，收益不大 |
| SD 格式化（建议）| 风险/收益不划算 |
| 云端相册 | 与"个人自用"定位无关 |
