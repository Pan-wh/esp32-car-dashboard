## 二、硬约束（本方案的全部依据）

### 2.1 资源余量（实测）

| 资源 | 现状 | 余量 |
|------|------|------|
| Flash（应用分区 3 MB）| 1,901,259 B（**60%**）| **约 1215 KB** |
| PSRAM（8 MB）| 5 张烘焙图充气后约占 1.4 MB | **约 6.5 MB** |
| SD 卡 | SDHC 7.3 GB | **可用 5.74 GB** |

> **结论**：**Flash 放不下图片/GIF**（一帧全屏 RGB565 就 424 KB，GIF 更是几十帧）。
> **必须放 SD 卡** —— 这与 D-010 的判断一致。

### 2.2 单帧体积（实测尺寸推算）

屏是 **466×466 圆屏**，即 **217,156 像素**：

| 格式 | 每帧体积 | 备注 |
|------|---------|------|
| RGB565 原始 | **424.1 KB** | 太大，不适合存储 |
| **8bpp 索引** | **212.1 KB** | 项目已在用；+1 KB 调色板 |
| **8bpp 索引 + RLE（2:1）** | **约 106 KB** | 取决于画面复杂度 |
| 240×240 8bpp | 56.2 KB | 若允许"照片不做满屏" |

### 2.3 传输速度（**这是最硬的约束**）

**BLE（当前唯一的通信方式）实测有效吞吐约 1 KB/s 量级** ——
依据：地图窗口一个 50 条消息的窗口要 2~3 秒，每条 ≤180 B，即约 **1~1.5 KB/s**。

| 要传什么 | 体积 | **BLE 需要** |
|---------|------|-------------|
| 全屏单张（8bpp 索引）| 212 KB | **约 212 秒** |
| 全屏单张（RLE）| 106 KB | **约 106 秒** |
| 240×240 单张 | 56 KB | **约 56 秒** |
| **一个 10 帧的 GIF** | 2.1 MB | **约 35 分钟** |

> ### 🔴 结论 1：**图片/GIF 不可能走 BLE 传**
> 一张图两分钟还算"能忍"，但**动图直接不可行**（半小时以上）。
> **必须换传输通道**，见 §4.2。

### 2.4 设备端解码与刷新成本（实测/推算）

| 环节 | 成本 | 来源 |
|------|------|------|
| 索引图逐像素解码（LVGL 内置路径）| 全屏约 **+45 ms** | `ui_img_inflate.c` 头注释的真机实测 |
| 全屏 flush（QSPI 80 MHz）| **43 ms** | PROGRESS §六 |
| 充气（一次性解码到 PSRAM）| 约 50~100 ms | 推算，待实测 |

> ### 🟡 结论 2：**动画帧率有硬上限**
> 解码（≈45 ms）+ flush（43 ms）≈ **90~150 ms/帧 → 7~11 fps**（全屏）。
> 若允许 **240×240** 的显示区域，解码降到约 1/4 → **20~30 fps**（可用）。
> 这是**物理上限，不是实现问题** —— 需要在"画质/区域大小/帧率"之间选。

### 2.5 SD 卡读取速度（**待实测**）

1-bit SDMMC 的读速**没有实测过**（现有代码只做过挂载与列目录）。
理论上 1-bit 模式下 10~25 MB/s 是常见值，但这块板/这张卡必须实测。
**这决定了 §4.1 是否需要用 RLE。**

---

## 三、三条硬结论（先看这里）

1. **存储必须在 SD 卡**（Flash 余量 1.2 MB，装不下一帧全屏）。
2. **传输必须换通道**（BLE 约 1 KB/s，动图要半小时）。
3. **动画帧率上限 7~11 fps（全屏）/ 20~30 fps（240×240）**，
   **且设备端只解"索引色/RLE"这种零成本格式**（不做 JPEG/PNG/GIF 解码）。

## 四、方案设计

### 4.1 设备端格式：**沿用项目的 8bpp 索引图，扩成"多帧包"**

**不给设备加 GIF/PNG/JPEG 解码器** —— 理由：

| 方案 | 代价 | 判断 |
|------|------|------|
| 设备端解 GIF（LZW + 多帧）| 需引入第三方库（许可审查）、CPU 高、帧率更低 | ❌ |
| 设备端解 JPEG | ESP32-S3 **无硬件 JPEG 解码**；软解 466×466 约 50~100 ms，动画不可行 | ❌ |
| 设备端解 PNG | 需 zlib/inflate，Flash 与 CPU 都不划算 | ❌ |
| **设备端只解 8bpp 索引（+RLE）** | **解码 = 查表/memcpy，接近零成本；项目已有实现与 28 项测试** | ✅ **推荐** |

**格式设计（`.pgi`，Photo/GIF Indexed）**：

```
┌ 文件头（固定 32 B）──────────────────────┐
│ magic "PGI1" | 宽 u16 | 高 u16           │
│ 帧数 u16 | flags u8（bit0=逐帧调色板）     │
│ 保留                                     │
├ 调色板（可选，256×4 B = 1 KB）────────────┤
│ 每帧一份（若 flags.bit0）或全局一份        │
├ 帧索引表（帧数 × 8 B）───────────────────┤
│ 每帧：偏移 u32 | 长度 u32（或含延时）      │
├ 帧数据（每帧 = RLE 编码的索引流）─────────┤
└─────────────────────────────────────────┘
```

- **为什么 RLE**：索引图的相邻像素高度相关 ✓；解码只需两个指针，**比逐像素查表还便宜**。
  若 §2.5 实测 SD 读速够快，**第一版可以不做 RLE**（简单优先），RLE 留作 v2。
- **为什么逐帧调色板**：GIF 的典型特征就是每帧可以有自己的调色板。
  `flags.bit0` 打开即可，代价 **1 KB/帧**。
- **帧延时**放帧索引表（`u16` 毫秒）—— 或者**固定 fps**（更简单，先做固定 fps）。

**工具链**：这个格式由 **App 侧生成**（§4.4），设备只读。

### 4.2 传输：**Wi-Fi 上传（推荐）** vs **SD 卡插拔（兜底）**

| 方案 | 用户操作 | 速度 | 固件工作量 | 判断 |
|------|---------|------|-----------|------|
| **A. SD 卡插拔** | 拔卡 → 插电脑 → 拷文件 → 插回 | 快 | **几乎为零** | ✅ **第一阶段先做这个** |
| **B. Wi-Fi 上传** | App 点"上传"→ 等几秒 | **500 KB/s 量级** | 中（起 AP + HTTP 服务）| ✅ **最终形态** |
| C. BLE 传 | 同上 | 1 KB/s（**不可用**）| 小 | ❌ |
| D. USB 大容量存储（MSC）| 插 USB 线 → 电脑出现盘符 | 快 | 中，且**与现有 CDC 串口冲突** | ⚠️ 备选 |

> ### 推荐：**A 先做（立刻可用），B 作为目标**
>
> **A** 让你**今天就能验证**图片/GIF 的显示与动画（把文件拷到 SD 卡的 `/photos/`），
> 固件只需"启动时扫目录 + 读文件"。
> **B** 是真正的日常体验：ESP32-S3 **本身有 Wi-Fi**，被 BLE 命令触发后起一个
> **临时 AP + HTTP 上传服务**，App 直接 POST 文件，几十秒传完一个 GIF。
>
> **B 的风险**（必须在开发前验证，见 §六）：
> 本板用 **octal PSRAM（opi）**，PSRAM 与 Wi-Fi 在 S3 上有已知的**带宽/稳定性权衡**。
> **必须先跑一个 spike**：开 Wi-Fi + AP + 传 1 MB 文件，确认：
> ① PSRAM 不崩；② 传完 LGVL 仍正常；③ 实测吞吐。
> **若 B 不可行**，退到 **A + USB MSC**。

**安全设计（B 方案）**：
- AP **只在被 BLE 命令触发后开启**，默认关闭；**5 分钟无操作自动关闭**；
- AP 有随机密码（显示在屏幕上 + 通过 BLE 告知 App）；
- 只接受**一个**客户端（上传完即断开）；
- **绝不**暴露任何"读取 SD 卡任意路径"的接口 —— 只允许写 `/photos/`。

### 4.3 设备端渲染与动画

**沿用 `ui_img_inflate` 的思路，但改成"流式"**：

```
启动/切换照片表盘：
  ├ 读文件头 + 帧索引表（小）
  ├ 解码第 1 帧 → PSRAM 缓冲 A → 立即显示
  └ 启动 LVGL 定时器（按 fps）

定时器（每 1/fps）：
  ├ 解码下一帧 → PSRAM 缓冲 B
  ├ 把 lv_img 的 src 指向 B（或双缓冲交替）
  └ 不阻塞主循环 —— 解码分片或控制在 45 ms 内
```

**关键约束**：
- **只分配 2 个帧缓冲**（全屏 2×424 KB ≈ 850 KB PSRAM ✓ 余量 6.5 MB 充足）；
- **不做"预解码所有帧"**（10 帧就要 4.2 MB，会把 PSRAM 吃光）；
- **动画在"照片表盘可见"时才跑**（切走即停，省电省 CPU）；
- **动画与其它表盘/页面并存时的降级**：若 fps 撑不住，**自动降帧**并在状态行提示。

**"照片表盘"的形态（需你定，见 §七）**：
1. **纯照片**（满屏铺一张图片；GIF 则满屏动画）
2. **照片背景 + 时钟**（待办里原本的"图片背景 + 时钟"就是这个）
3. **照片 + 速度**（照片当背景，速度叠在上面）

### 4.4 App 端设计

#### 4.4.1 裁切与预览（需求 D 的前半）

全部用 **iOS 内置框架**，**不引入第三方依赖**：

| 功能 | 框架 | 说明 |
|------|------|------|
| 选图 | `PhotosPicker`（SwiftUI）| 系统相册选择器，无需权限弹窗 |
| **裁切** | `UIGraphicsImageRenderer` + 手势 | 圆屏 → **默认提供"圆形裁切"** 引导框；也允许方形（设备端再按圆屏裁掉四角） |
| **预览** | 直接渲染成 **466×466** 的目标尺寸 + 圆屏遮罩 | **所见即所得**（避免"上传后比例不对"） |
| **格式转换** | `ImageIO`（`CGImageDestination`）| 生成 GIF / 读取 GIF、Live Photo 的帧 |
| **视频 → GIF** | `AVAssetImageGenerator` | 抽帧 → 调色板量化 → 写 GIF。**全内置** ✓ |
| **动图 → GIF** | `CGImageSource`（逐帧读）| 支持 GIF/APNG/WebP 动图；Live Photo 取 `photo` + `video` 两段 |

> **重要**：App 端**不生成 `.pgi`** —— 而是 **GIF** 或**逐帧图片**，
> 由**上传前的一步转码**生成 `.pgi`（即在 App 内做，见下）。

**转码在哪做**（需你定，见 §七）：
- **方案 1（推荐）**：**App 内转 `.pgi`** —— App 有完整算力，量化 + RLE + 打包都在手机上，
  设备端只 memcpy。**设备固件最薄**。
- **方案 2**：App 上传 GIF，**网关转**（Node 有 `sharp`/`gifuct` 之类）。
  多一个服务依赖；但**App 代码更薄**。
- **方案 3**：设备端解 GIF ❌（§4.1 已否）。

#### 4.4.2 SD 卡管理（需求 C）

**现状**：SD 卡信息只能通过**串口** `sd` 命令看 ✗ —— App 完全看不到。

**设计**：新增 **BLE 命令 + 状态上报**：

| 操作 | BLE 消息（草案）| 设备行为 | 风险 |
|------|----------------|---------|------|
| 查状态 | `{"cmd":"sd","op":"info"}` | 回 `{"sd":{"mounted":1,"type":"SDHC","totalMB":7476,"freeMB":5878,"files":3}}` | 无 |
| 列文件 | `{"cmd":"sd","op":"list"}` | 分页返回 `/photos/` 下的文件名与大小 | 无 |
| 删除 | `{"cmd":"sd","op":"del","name":"a.pgi"}` | 只允许删 `/photos/` 内的 | 低（可恢复不了）|
| **格式化** | `{"cmd":"sd","op":"format"}` | **双重确认**后 `SD_MMC` 低级格式化 | **🔴 极高** |

**格式化必须做的防护**（这是本方案里唯一"能毁用户数据"的功能）：

1. **App 端**：二次弹窗 + **要求手输 `FORMAT`** 才能点确认（防误触）；
2. **固件端**：收到命令后**再回一次**"确认请求"，App 必须再发一次带
   **随机挑战码**的确认（超时 10 秒作废）—— **防重放与误发**；
3. **屏幕同步显示**"正在格式化，请勿断电"；
4. **格式化前先检查是否有人在用**（照片表盘正在显示 → 提示先切走）。

> ⚠️ 另一个选择是 **App 端完全不做格式化**（只做"看状态 + 删单个文件"），
> 格式化永远留给电脑。**我倾向这个** —— 见 §七。

## 五、分阶段实施计划

| 阶段 | 内容 | 交付标准（可验收）| 依赖 |
|------|------|-----------------|------|
| **P0** | **格式 + 工具**：定 `.pgi` 规格；写一个 **Mac 侧生成器**（`tools/pgi.py`），能把 PNG/一组帧打成 `.pgi` | 生成的 `.pgi` 能被 PC 单测解码回原图（逐像素比对）| 无 |
| **P1** | **设备端静态图片显示**：新增"照片表盘"，读 SD 卡 `/photos/*.pgi` 显示第一帧 | 插卡 → 划到照片表盘 → **看到图**；`sd list` 能看到文件 | P0 |
| **P2** | **设备端 GIF 动画**：多帧 + 固定 fps + 双缓冲，仅在照片表盘可见时运行 | 播放一个 10 帧动画，实测 **≥8 fps**；切走立即停 | P1 |
| **P3** | **App 端裁切 + 预览 + 视频/动图转 GIF** | 从相册选一段视频 → 裁切预览 → 导出 GIF → 存到相册 | 无（可与 P1/P2 并行）|
| **P4** | **传输**：先做 **SD 卡插拔**（其实 P1 就顺带满足了）；再做 **Wi-Fi 上传 spike**，通过则实现 | Wi-Fi 传一个 2 MB GIF **< 30 秒**；AP 5 分钟自动关闭 | P2 + **§六 的 spike** |
| **P5** | **SD 卡管理**（状态 / 列表 / 删除；格式化**待定**）| App 能看到容量与文件列表；删除后 `sd list` 同步 | P4（走 Wi-Fi）或独立小命令 |

> **P3 可以先做** —— 它纯 App 侧、无硬件依赖，**能立刻交付价值**（用户能拿它做 GIF 玩）。
> **P1 也能先做**（SD 插拔就够），不必等 Wi-Fi。

## 六、开发前必须验证的 Spike（按风险排序）

| # | 要验证什么 | 怎么验 | 若不行的退路 |
|---|-----------|--------|------------|
| **S1** | **SD 卡读速**（1-bit SDMMC）—— 决定要不要 RLE、以及动画 fps | 加一个串口命令：读 1 MB 计时 | 上 RLE；再不行降分辨率 |
| **S2** | **Wi-Fi + octal PSRAM 共存**—— 决定 P4 走 A 还是 B | 起 AP + HTTP，传 1 MB，观察 PSRAM/LVGL | 退回"SD 插拔 + USB MSC" |
| **S3** | **全屏解码 + flush 的真实耗时**（现有 +45 ms 是 LVGL 逐行解码，不是"一次性充气"）| 加计时打印 | 限定照片区域（如 300×300）|
| **S4** | PSRAM 双缓冲（2×424 KB）加现有 1.4 MB，会不会挤压 LVGL 池 | `mem` 命令观察 | 减缓冲尺寸 / 单缓冲 |

**S1 与 S3 加起来约半天**，而且**只需要串口命令 + 日志**，不动 UI。
**建议先做 S1+S3 再决定 P2 的 fps 目标。**

## 八、明确不做的事

| 不做 | 原因 |
|------|------|
| 设备端解 GIF / PNG / JPEG | 无硬件解码；软解太慢，动画不可行（§4.1）|
| 用 Flash 存图片 | 余量 1.2 MB，装不下一帧（§2.1）|
| 把图片/GIF 写进固件（烘焙）| 每换一张图都要重新烧录，且吃 Flash |
| 通过 BLE 传图片 | 1 KB/s，动图要半小时（§2.3）|
| 设备端做裁切/转码 | 算力与内存都不划算；App 做这些是免费的 |
| 照片云同步 | 与"个人自用"定位无关 |

## 九、与既有决策的关系

| 决策 | 影响 |
|------|------|
| **D-010**（地图不放设备，SD 卡给字模）| ✅ 完全一致：**SD 卡就是给图片/GIF 的** |

> ⚠️ **一个安全约束要写进实现**：照片表盘**不得遮挡**速度/导航等行车信息 ——
> 若选"纯照片"形态，**必须在照片上保留（或可切换出）速度显示**。
