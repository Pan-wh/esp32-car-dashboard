## 三、硬约束（已核实，决定方案形状）

### 3.1 资源余量

| 资源 | 现状 | 余量 |
|------|------|------|
| Flash（3 MB 分区）| 1,901,259 B（60%）| **约 1215 KB** |
| PSRAM（8 MB）| 5 张烘焙图约 1.4 MB | **约 6.5 MB** |
| SD 卡 | SDHC 7.3 GB | **可用 5.74 GB** |

**一帧全屏 RGB565 = 424 KB** ✗ → 图片**必须放 SD 卡** ✓（与 D-010 一致 ✓）

### 3.2 单帧体积（466×466 = 217,156 像素）

| 格式 | 每帧 |
|------|------|
| RGB565 原始 | 424.1 KB |
| **8bpp 索引** | **212.1 KB**（+1 KB 调色板）|
| 8bpp + RLE（2:1）| 约 106 KB |

### 3.3 ⚠️ BLE **不能**传图片（所以必须 Wi-Fi）

**BLE 实测有效吞吐约 1 KB/s**（依据：地图窗口 50 条消息 2~3 秒、每条 ≤180 B）：

| 传什么 | BLE 需要 |
|--------|---------|
| 全屏单张（212 KB）| **212 秒** |
| 10 帧 GIF（2.1 MB）| **约 35 分钟** ✗ |

> **这是"传输走 Wi-Fi"的直接原因** —— 不是偏好问题。

### 3.4 设备端解码与刷新

| 环节 | 成本 | 来源 |
|------|------|------|
| 索引图逐像素解码（LVGL 内置）| 全屏 **+45 ms** | `ui_img_inflate.c` 真机实测 |
| 全屏 flush（QSPI 80 MHz）| **43 ms** | PROGRESS §六 |

> **动画帧率上限：全屏 7~11 fps；240×240 可达 20~30 fps。**

### 3.5 🔴 AMOLED 烧屏（**两个新表盘都必须防**）

面板是 **CO5300 AMOLED**，烧屏**永久不可逆**。而**静态照片表盘**恰恰是
"长时间显示同一张图" ✗ —— 这是 AMOLED 最怕的用法。防护见 §六。

## 四、两个新表盘的设计

### 4.1 表盘清单（5 → 7）

| id | name | label | group | 内容 |
|----|------|-------|-------|------|
| 0 | analog | Analog | clock | 模拟时钟 |
| 1 | digital | Digital | clock | 数字时钟 |
| 2 | speed | Speed | speed | 速度表 |
| 3 | color | Color | clock | 多彩时钟 |
| 4 | nav | Nav | nav | 导航卡片 |
| **5** | **photo** | **Photo** | **photo** | **静态图片 + 轮播** |
| **6** | **gif** | **GIF** | **photo** | **动图播放 + 轮播** |

- **两个都注册进 `ui_pages`** → 出现在**滑动序列** ✓（用户要的）
- **两个都归 `UI_FACE_GROUP_PHOTO`** → App 里同组显示 ✓
- **默认启用** ✓；但**若 SD 卡无照片，显示占位提示**（不空白）✓
- 用户可在 App 里**隐藏**任一表盘（现成的 `face_enabled` 机制）✓

### 4.2 为什么分成两个表盘（而不是一个表盘两种内容）

| 理由 | 说明 |
|------|------|
| **语义清晰** | "我要看静态照片"和"我要看动图"是两个不同的使用意图 |
| **目录分开** | `/photos/still/` 与 `/photos/gif/`，各自轮播自己那组，互不干扰 |
| **运行路径简单** | 静态表盘只读单帧、动图表盘只读多帧 —— 各走各的循环，不必在每张图上判断类型 |
| **性能可预测** | 静态表盘不跑动画定时器（省电、无帧率压力）；动图表盘才跑 |

> 底层格式仍是**同一个 `.pgi`**（单帧 = 静态、多帧 = 动图），只是**按目录区分用途** ——
> 这样一个编解码器就够，不需要两套代码。

### 4.3 表盘内的轮播（需求 D）

**两个表盘各自独立轮播自己的照片集合**：

```
/photos/still/   ← 静态照片表盘（id 5）轮播这里
   01_sunset.pgi
   02_family.pgi
/photos/gif/     ← 动图表盘（id 6）轮播这里
   01_cat.pgi     （多帧）
   02_wave.pgi    （多帧）
```

**行为**：

| 表盘 | 行为 |
|------|------|
| **静态（id 5）** | 每 **N 秒**切下一张（N 默认 30 s，可配）；**切换时做像素位移**（§六）|
| **动图（id 6）** | 播放当前动图的帧 → 播完**循环 2 次** → 切下一个动图；同样有位移 |

**共同规则**：

- 顺序：**文件名排序**（用户可用 `01_`、`02_` 前缀自己排）；
- **只在表盘可见时运行**（切走即停 ✓ 省电 ✓）；
- 集合为空 → 显示**占位提示**（"请用 App 上传照片" ✓）而不是黑屏 ✗；
- **只有一个文件**时：照常显示，但**强制开启像素位移**（§六）✓。

### 4.4 占位状态（必须设计，否则首用体验很差）

| 情况 | 显示 |
|------|------|
| SD 卡未插入 | "未检测到 SD 卡" |
| SD 卡已插但 `/photos/still/` 为空 | "还没有照片 · 用 App 上传" |
| 文件损坏 / 格式不支持 | 跳过该文件，显示下一张；全部失败则显示"照片读取失败" |
| 正在加载首帧 | 上一张的画面或纯色 + 小提示（**不超过 1 秒**）|

## 五、格式：`.pgi`（一个格式，两种用途）

```
┌ 文件头 32 B ─────────────────────────────┐
│ magic "PGI1" | 宽 u16 | 高 u16            │
│ 帧数 u16 | fps u8 | flags u8（bit0=逐帧调色板）│
├ 调色板 256×4 B（全局一份，或每帧一份）────┤
├ 帧索引表（帧数 × 8 B）───────────────────┤
│ 每帧：偏移 u32 | 长度 u32                  │
├ 帧数据（8bpp 索引流，可选 RLE）───────────┤
└──────────────────────────────────────────┘
```

- **单帧 = 静态照片**、**多帧 = 动图** —— 一个解码器覆盖两种表盘 ✓
- 设备端只做**查表 / memcpy**，不解 GIF/PNG/JPEG ✓
- RLE 留作后补（等 §十一 的 S1 实测读速再定）

## 六、🔴 AMOLED 烧屏防护（两个表盘都要，默认全开）

| # | 措施 | 说明 | 可配 |
|---|------|------|------|
| 1 | **轮播** | 画面整体变化本身就是最好的防烧屏 | 间隔 10~300 s |
| 2 | **像素位移** | 每次切图 / 每 2 分钟整体平移 **±3 px**（四周各裁 3 px，不露边）| 开关 |
| 3 | **亮度上限** | 两个照片表盘下亮度**封顶 180** | 开关 |
| 4 | **自动息屏** | 30 分钟无交互 → 息屏（触摸唤醒）| 时长可配 |

**两条硬规则**：

- **只有 1 张照片时强制开启像素位移**（否则等于静态烙印）；
- **禁止长期停在纯亮画面**（白底图）→ 此时自动降低亮度上限。

> 静态照片表盘是**烧屏风险最高的用法**（一张图挂几小时），这一节不是可选项。

## 七、传输：**Wi-Fi**（需求 E，用户已定）

### 7.1 方案

设备启动后**默认不开 Wi-Fi**（省电、减攻击面）；App 点"上传照片"时：

```
App ──BLE 命令 {"cmd":"wifi","op":"on"}──▶ 设备
                                             ├ 开 AP（SSID/密码随机）
                                             ├ 屏幕显示 SSID + 密码 + IP
                                             └ 起 HTTP 服务（只接受 /upload）
App ──连该 AP──▶ HTTP POST 文件 ──▶ 设备写入 /photos/{still|gif}/
App ──BLE 命令 {"cmd":"wifi","op":"off"}──▶ 设备关 AP，恢复 BLE-only
```

**关键设计**：

| 项 | 设计 |
|----|------|
| AP 生命周期 | **5 分钟无操作自动关闭**（防忘记关）|
| 认证 | 随机密码（屏幕 + BLE 告知 App）；**只接受一个客户端** |
| 写入范围 | **只能写 `/photos/still/` 与 `/photos/gif/`**，绝不暴露任意路径 |
| 文件名 | 设备生成（`p_<时间戳>.pgi`），不接受客户端指定路径 |
| 大小上限 | 单文件 ≤ 8 MB（防止塞爆卡 / 占满 PSRAM）|
| 冲突 | 上传期间**暂停轮播**（避免同时读同一文件）|
| 失败 | 返回明确错误码（磁盘满 / 写入失败 / 超限），App 显示 |

### 7.2 ⚠️ 必须先验证的风险（Spike S2）

本板是 **octal PSRAM（opi）**，S3 上 **PSRAM 与 Wi-Fi 有已知的带宽/稳定性权衡**。
**开发前必须验**：开 AP + HTTP 传 1 MB，检查 ① 不崩 ② LVGL 渲染仍正常 ③ 实测吞吐。

**若 Wi-Fi 不可行**，退路是：**SD 卡插拔**（把文件拷到 `/photos/`）——
但这会失去"App 内上传"的体验，属于降级。

## 八、App 端设计

### 8.1 照片管理（需求 C：新增 / 删除）

```
┌ 照片 ──────────────────────────────┐
│ [上传到静态照片]  [上传到动图]       │
│ ─────────────────────────────     │
│ 静态照片 (3)                       │
│  📄 01_sunset.pgi   212 KB   [删]  │
│  📄 02_family.pgi   198 KB   [删]  │
│ 动图 (2)                           │
│  📄 01_cat.pgi      1.8 MB   [删]  │
│ ─────────────────────────────     │
│ SD 卡：SDHC 7.3 GB / 可用 5.74 GB  │
│ 轮播间隔 [30 s ▾]  像素位移 [开]   │
└────────────────────────────────────┘
```

- **新增**：选图 → 裁切预览 → 转 `.pgi` → Wi-Fi 上传 ✓
- **删除**：BLE 命令 `{"cmd":"photo","op":"del","dir":"still","name":"..."}` ✓
  （**只允许删 `/photos/` 内** ✓ 且删除后立即刷新列表 ✓）

### 8.2 裁切 / 预览 / 转 GIF（需求 F，**全 iOS 内置框架，零依赖**）

| 功能 | 框架 |
|------|------|
| 选图 / 选视频 | `PhotosPicker` |
| **裁切 + 圆屏预览** | `UIGraphicsImageRenderer` + 手势；**466×466 + 圆形遮罩，所见即所得** |
| **动图 → GIF** | `CGImageSource`（GIF / APNG / WebP / Live Photo）|
| **视频 → GIF** | `AVAssetImageGenerator` 抽帧 → `CGImageDestination` 写 GIF |
| **GIF/图片 → `.pgi`** | App 内量化（256 色）+ 打包 |

> 转码放 App 的理由：App 有完整算力；设备只做 memcpy；也不需要给网关加服务端依赖。

### 8.3 SD 卡管理（需求 G）

| 操作 | BLE 消息 | 说明 |
|------|---------|------|
| 查状态 | `{"cmd":"sd","op":"info"}` | 挂载状态 / 类型 / 总容量 / 可用 / 两个目录的文件数 |
| 列文件 | `{"cmd":"sd","op":"list","dir":"still"}` | 分页返回文件名与大小 |
| 删除 | `{"cmd":"sd","op":"del",...}` | 同 §8.1 |
| **格式化** | `{"cmd":"sd","op":"format"}` | ⚠️ **建议不做**（见 §十 #5）|

| 阶段 | 内容 | 可验收标准 | 依赖 |

## 十一、开发前必须先验的 Spike

| # | 验证 | 怎么验 | 不行的退路 |
|---|------|--------|-----------|
| **S1** | SD 卡 1-bit 读速 | 串口命令读 1 MB 计时 | 上 RLE / 降分辨率 |
| **S2** | **Wi-Fi + octal PSRAM 共存** ⚠️ | 起 AP + HTTP 传 1 MB | 退回 **SD 卡插拔**（降级）|
| **S3** | 全屏解码 + flush 真实耗时 | 计时打印 | 限定 240×240 |
| **S4** | PSRAM 双缓冲（850 KB）+ 现有 1.4 MB 余量 | `mem` 观察 | 减缓冲 / 单缓冲 |

> **S1+S3 约半天**（只需串口命令与日志，不动 UI）；
> **S2 是唯一的"可能推翻方案"的风险**，建议紧跟着做。

## 十二、明确不做

| 不做 | 原因 |
|------|------|
| 设备端解 GIF/PNG/JPEG | 无硬件解码，软解 50~100 ms，动画不可行 |
| 图片进 Flash | 余量 1.2 MB，装不下一帧 |
| BLE 传图片 | 1 KB/s，动图要半小时（§3.3）|
| 独立的"相框模式" | 用户已澄清：要的是**两个表盘**，不是覆盖层 |
| 照片上叠加时钟/速度 | 用户要求纯照片 |
| 淡入淡出切换 | 466×466 上要多两帧缓冲，收益不大 |
| SD 格式化（建议）| 风险/收益不划算 |
| 云端相册 | 与"个人自用"定位无关 |
