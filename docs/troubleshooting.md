## 2026-10-10 烧录后 USB 串口无任何输出（真机实测）

- **现象**：官方 `01_HelloWorld` 烧录成功、屏幕有显示，但打开串口监视器（`/dev/cu.usbmodem101`）
  完全收不到数据（esptool 能正常通信、烧录正常）。
- **原因**：ESP32-S3 板卡选项默认 `USB CDC On Boot = Disabled`（`CDCOnBoot=default`）。
  此时 Arduino 的 `Serial` 指向**硬件 UART0（GPIO43/44）**，而不是原生 USB CDC；
  本板没有 USB-UART 桥接芯片，因此 USB 口只能烧录、看不到应用日志。
- **解决**：编译时显式打开 USB CDC：
  ```
  --fqbn "esp32:esp32:esp32s3:FlashSize=16M,PartitionScheme=app3M_fat9M_16MB,USBMode=hwcdc,CDCOnBoot=cdc"
  ```
- **验证结果**：重新烧录后 8 秒收到 40 行 `loop`（每 200 ms 一次，与 HelloWorld 程序一致）✓
- **对本项目的影响**：固件与所有官方示例的调试都必须带该选项，否则看不到 `Serial` 日志
  （我们的 `dashboard.ino` 依赖 Serial 输出启动信息与心跳）。

## 2026-10-11 RTC 显示 2024-09-24（不是故障）

- **现象**：烧录官方 `03_LVGL_PCF85063_simpleTime` 后，RTC 时间恒为 `2024-09-24 11:09`。
- **原因**：**官方示例自己写死了时间** —— `rtc.setDateTime(2024, 9, 24, 11, 9, 41)`
  在每次上电时执行（示例源码第 78-87 行）。RTC 芯片本身走时正常（跨分钟进位正确）。
- **处理**：本工程固件改为「RTC 早于编译时间才用编译时刻兜底」，并提供串口
  `set YYYY-MM-DD HH:MM:SS` 手动校准；后续接入 GNSS 后用 RMC 的 UTC 时间自动校准。
- **验证**：烧录本工程固件后 RTC 显示 2026-10-11，串口 `set` 校准到 16:11:22，
  复查 16:11:24（正常走时）✓

## 2026-10-11 真机滑动手势不切页（三个连环坑，全部已修）

**现象**：真机上左右滑动无法切换页面；串口诊断显示 LVGL **确实识别出了手势**
（LEFT=6 RIGHT=3），但页面不切换；速度页显示也与模拟器不同（另见下方第 4 条）。

**排查手段**（可复用）：固件内置串口命令 `mem` / `dump` / `touch`，
配合模拟器的 `--gesture-test`（自动注入拖拽并打印 LVGL 输入内部状态与命中测试）。

### 坑 1：`lv_obj` 默认给子对象加 `GESTURE_BUBBLE`

`lv_obj.c` 构造函数：`if(parent) obj->flags |= LV_OBJ_FLAG_GESTURE_BUBBLE;`
手势检测会沿父链上移目标（`lv_indev.c: while(has_flag(GESTURE_BUBBLE)) gesture_obj = parent`），
于是手势被转发给**屏幕**，页面容器的回调永远不执行。
→ 解决：页面/子对象统一清掉 `GESTURE_BUBBLE`（连同 `SCROLLABLE` 等一组默认标志）。

### 坑 2：`SCROLLABLE` 会吞掉手势

`lv_indev.c` 的 `indev_gesture()` 开头即 `if(scroll_obj) return;` ——
**滚动与手势互斥**；而 `lv_obj_remove_style_all()` 只清样式、**不清标志**，
基类默认带 `SCROLLABLE`，于是拖拽被判为"滚动"、手势不发。

### 坑 3：隐藏"被按住的页面"会连环触发手势

即便修好 1、2，自己用 `LV_EVENT_GESTURE` 切页仍有问题：切页要隐藏当前页，
而隐藏被按住的页面会让 LVGL 重置输入状态，同一次拖拽反复判定手势
（实测一次拖拽触发 3 次：0→2→1→0，**转回原点**，看起来就是"滑不动"）。

**最终方案**：改用 LVGL 标准的**横向滚动容器 + 吸附分页**（`lv_tileview` 同款机制），
不再自己处理手势：容器尺寸 = **视口大小**，页面在其中并排摆放并超出边界，
`SCROLLABLE + SCROLL_SNAP_CENTER + 子对象 SNAPPABLE`，滚动结束用 `scroll_x` 反推当前页。

> 附带坑：容器若做成 `页数 × 屏宽`，则内容刚好填满容器 → **没有可滚动区域** → 依然滑不动。

### 坑 4：速度页与模拟器不一致（变体默认值）

`ui_speed.c` 的 `s_variant` 默认是 0（V1），而模拟器一直用 `--variant 4` 启动，
固件从未设置变体 → 真机显示 V1（数字+外环弧）而非 V5（驾驶员表盘）。
→ 解决：默认值改为 4（V5 定稿设计）。**排查用 `dump` 打印元素树**即可发现
（V1 只有 arc+label，V5 应有 img 300×300 + meter + 6 个刻度数字）。

**验证**：模拟器 `--gesture-test`：从第 1 页右拖 400px → 第 0 页；左拖 400px → 第 1 页 ✓

## 2026-10-11 屏幕旋转 90°：实测不可行（性能与撕裂），已放弃

**需求**：USB 口在左侧，希望 USB 朝下，因此屏幕内容需旋转 90°。

**两条路线都验证过**：

1. **面板 MADCTL 旋转（理论上零开销）— 不可用**
   - `Arduino_CO5300::setRotation()` 只做 X/Y 翻转，源码注释即 "CO5300 does not support rotation"；
     上游 Arduino_GFX master 同样如此（已拉取比对）。
   - 库内常量 `CO5300_MADCTL_X_AXIS_FLIP 0x02 / Y_AXIS_FLIP 0x05 / BGR 0x08` 与标准 MADCTL
     位定义（MX=0x40, MY=0x80, MV=0x20）**互相矛盾**，且初始化序列里 MADCTL 是被注释掉的，
     前面还有 `WRITE_C8_D8, 0xFE, 0x00` 的页/命令集切换 —— 该控制器在本库下的寄存器语义无法确认。
   - **不猜寄存器**：向面板写未经验证的 MADCTL 值有把屏幕置于异常状态的风险，故放弃此路线。

2. **LVGL 软件旋转（sw_rotate）— 能转，但不可用**
   - 真机实测：**时钟明显卡顿、左右滑动切换卡顿、并出现撕裂/果冻效应**。
   - 原因：每帧 flush 都要经 `LV_DISP_ROT_MAX_BUF`（官方 lv_conf.h = 10KB）临时缓冲做
     分块旋转；且 LVGL 源码 `lv_refr.c` 明确禁止 `full_refresh + sw_rotate`
     （打印 "cannot rotate a full refreshed display!"）。分页滚动时旋转条带次序错乱 → 撕裂。
   - 优点：触摸坐标无需自己处理，LVGL 会按同一角度反变换（`lv_indev.c: indev_pointer_proc`）。

**结论**：466×466 分辨率下**不做整屏旋转**。最终选择**改安装方向**（设备不再转 90°）。
若日后确需竖屏，正确做法是**按目标方向重新排版界面**（零每帧开销、无撕裂），而不是旋转像素。

**保留的调试能力**：串口命令 `rot 0|1|2|3` 可运行时切换（`lv_disp_set_rotation`），
用于将来快速验证方向，但已知有上述性能代价。

## 2026-10-10 模拟器里时钟不走 / 秒针不动

- **现象**：模拟器界面能正常显示，但数字时钟不刷新、模拟时钟秒针静止不动。
- **复现步骤**：`./dashboard_sim` 打开窗口观察数十秒。
- **原因**：`simulator/main.c` 主循环**从未调用 `lv_tick_inc()`**，且 `lv_conf.h` 未启用
  `LV_TICK_CUSTOM`（默认 0，即需要手动喂心跳）。结果 LVGL 内部时间恒为 0，
  `lv_timer_handler()` 认为没有时间流逝 → **所有 `lv_timer` 都不触发**。
  界面只在初始化时渲染了一次，所以看起来"卡住"。
- **解决**：在主循环中按经过的真实毫秒调用 `lv_tick_inc(delta)`：
  ```c
  Uint32 now_tick = SDL_GetTicks();
  if (now_tick != last_tick) { lv_tick_inc(now_tick - last_tick); last_tick = now_tick; }
  lv_timer_handler();
  ```
- **验证结果**：间隔约 4 秒截取两张图，橙色秒针角度从 144.2° 变为 168.1°（差 24° ≈ 6°/s
  的每秒一跳）→ 确认定时器已正常工作。

### 真机注意事项（重要）

ESP32 上同样需要**稳定的 LVGL 心跳源**，通常由硬件定时器周期性调用 `lv_tick_inc()`。
微雪官方 Arduino 示例已包含该机制（`EXAMPLE_LVGL_TICK_PERIOD_MS 2` + 定时器回调），
因此**移植 UI 代码到固件时必须沿用官方示例的 tick 配置**，否则会出现与本条完全相同的
"界面静止"现象。这是本坑对固件阶段的直接启示。

## 2026-10-12 并发缺陷：取锁失败被误判为"从未收到"→ 状态闪跳

**代码**：`ble_telemetry_age_ms()`（原实现）

```cpp
uint32_t r = 0;
if (s_mtx && xSemaphoreTake(s_mtx, pdMS_TO_TICKS(10)) == pdTRUE) { r = s_rx_ms; ... }
if (r == 0) return UINT32_MAX;   // ← 取锁失败时 r 也是 0
```

**缺陷**：`s_rx_ms == 0` 被用来表示"从未收到过"，但**取锁超时**时 `r` 同样保持 0，
于是偶发地把"并发中取不到状态"误报成"从未收到"。调用方 `ble_update()` 见
`age == UINT32_MAX` 即判为**数据超时（STALE）**，导致正常行驶中出现
**LIVE → STALE → LIVE 闪跳**（UI 观感与告警都受影响）。

**修复**：
1. 新增显式标志 `s_have_rx`（收到首条有效遥测时置位），与 `s_rx_ms == 0` 解耦；
2. 取锁失败返回独立哨兵 `BLE_AGE_UNKNOWN (UINT32_MAX-1)`；
3. 调用方遇到 `BLE_AGE_UNKNOWN` 时**保持上一次状态**，不判超时。

**通用教训**：跨任务共享状态时，不要把"未初始化/从未发生"的哨兵值与
"本次读取失败"混用同一返回值——两者语义不同，混用会造成间歇性误判
（且极难复现）。

## 2026-10-12 真机全局卡顿（滑动掉帧、秒针卡住）—— 无效化风暴（已修复）

**现象**（用户实机反馈）：设备整体很卡；左右滑页掉帧；模拟时钟秒针跳动也会卡住。

**根因**（回归，本会话第 7 轮引入）：`ble_update()` 每圈主循环（约 100Hz）调用
`ui_speed_set_fix()/set_speed()`，而这些 setter **不做变更检测**直接调
`apply_state()`。LVGL 8.4 的 `lv_meter_set_indicator_value()` **无条件 invalidate**
（值相同也会把指针区域标脏），`lv_img_set_src()`/`lv_label_set_text()` 同理
（源码 lv_meter.c:207 起：inv_line 不判断新旧值是否相等）。
→ 空闲时也以每秒数十次把速度页大块区域标脏，CPU 全耗在重绘"没变的像素"。

**客观证据**（模拟器复现工具 `--ble-sim` + flush 计数）：
- 复刻固件每帧调用：**55.5 flush/秒**
- 正常数据驱动基线：**2.6 flush/秒**
- 修复后（同样复刻调用）：**2.6 flush/秒** —— 与基线完全一致，风暴消除

**修复**（两层）：
1. `ui_speed_set_speed/fix/heading/driver_state` 全部加**变更检测**（值不变直接 return）；
   `apply_state()` 内部对插画与状态标签同样加已显示状态判断（速度动画期间不重复 set）
2. 固件 `ble_update()` 限频 50Hz（数据本身 2Hz，限频只降空转）

**回归**：指针随速度变化仍正常动（y 重心 305→73）；UI 像素回归 10 项 +
单测 167 项全绿；固件编译通过（50% Flash）。

**教训**：LVGL 8 的多数 setter 不做同值短路；高频调用方必须自己做变更检测。
凡是以循环频率调用 UI setter 的代码，都要问一句"值没变时会怎样"。

## 2026-10-13 滑页仍卡：逐项实测定位（单帧 ~240ms）

**背景**：无效化风暴修复后时钟不卡了（空闲重绘 0–2/s），但左右滑页依然掉帧。
新增固件内计时（心跳输出「渲染最大 / 占空 / QSPI 传输」）后逐项测量：

| 测量项 | 数值 | 说明 |
|--------|------|------|
| 单帧渲染峰值（滑页时）| **240 ms** | 一次 lv_timer_handler 的最长耗时 → 约 4 fps |
| 其中 QSPI 传输（单次最大）| **56 ms** | 全屏 434KB → 实测 7.75 MB/s（40MHz QSPI 理论 20MB/s）|
| 其中 LVGL 绘制 | **~185 ms** | 主要成本 |
| 占空比（5s 窗口）| 63–64% | CPU 大部分时间在渲染 |

**按页面拆分**（成对滑页反解，cost(a+b) = cost(a)+cost(b)）：
- 模拟时钟页 ≈ **145 ms**（61 小节刻度 + 13 整点刻度 + 3 指针）
- 速度表页 ≈ **98 ms**（41 刻度 + 渐变弧 + 300×300 插画）
- 数字时钟页 ≈ **98 ms**（138px 抗锯齿大字体）

**结论**：瓶颈是 LVGL 软件绘制（77%），不是 QSPI（23%）。lv_meter 是单对象，
任一脏区都会重算**全部**刻度；滑页时两页同时可见 → 两页的表盘都要重画。

**PSRAM 全帧缓冲的效果**（已实装并保留）：重绘次数从 10–67/s 降到 2–6/s
（脏区只切 1 块，符合设计），但单帧耗时未降——说明分块开销不是主因。

**下一步候选优化**（按收益排序，均未实施）：
1. **静态表盘烘焙为图片**：刻度/数字/渐变弧都是静态的，只有指针在动。
   离线用 PIL 渲染成 466×466 RGB565（外观不变甚至更精细），页面 = 1 次图片
   拷贝 + 指针线。预计单帧 240ms → 70–90ms。Flash 成本约 434KB/张（现有余量
   1.5MB，可放 2–3 张）。
2. **大号字体去抗锯齿**（138px → 1bpp 点阵）：预计数字时钟页 98ms → ~35ms，
   但边缘会有锯齿（视觉有损，需用户确认）。
3. **提高 QSPI 时钟**（40→80MHz）：若面板支持，传输 56ms → ~30ms；有花屏风险。
4. **缩短/取消滑页动画**：不改单帧成本，只缩短卡顿持续时间。

**教训**：LVGL 8 的 lv_meter 是「整对象重绘」模型；刻度越多、对象越大，
滑页（整屏重绘）成本越高。静态表盘应烘焙成图片，只保留动态的指针。
