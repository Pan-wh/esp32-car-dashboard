### 2026-10-10 写 ~/Library/Arduino15 被沙盒拒绝

- 原因：AI 会话文件沙盒仅允许写项目工作区。

## 2026-10-10 烧录后 USB 串口无任何输出（真机实测）

- **现象**：官方 `01_HelloWorld` 烧录成功、屏幕有显示，但打开串口监视器（`/dev/cu.usbmodem101`）
  完全收不到数据（esptool 能正常通信、烧录正常）。
- **原因**：ESP32-S3 板卡选项默认 `USB CDC On Boot = Disabled`（`CDCOnBoot=default`）。
  此时 Arduino 的 `Serial` 指向**硬件 UART0（GPIO43/44）**，而不是原生 USB CDC；
  本板没有 USB-UART 桥接芯片，因此 USB 口只能烧录、看不到应用日志。
- **解决**：编译时显式打开 USB CDC：
  ```
  --fqbn "esp32:esp32:esp32s3:FlashSize=16M,PartitionScheme=app3M_fat9M_16MB,USBMode=hwcdc,CDCOnBoot=cdc"
  ```
- **验证结果**：重新烧录后 8 秒收到 40 行 `loop`（每 200 ms 一次，与 HelloWorld 程序一致）✓
- **对本项目的影响**：固件与所有官方示例的调试都必须带该选项，否则看不到 `Serial` 日志
  （我们的 `dashboard.ino` 依赖 Serial 输出启动信息与心跳）。

## 2026-10-11 RTC 显示 2024-09-24（不是故障）

- **现象**：烧录官方 `03_LVGL_PCF85063_simpleTime` 后，RTC 时间恒为 `2024-09-24 11:09`。
- **原因**：**官方示例自己写死了时间** —— `rtc.setDateTime(2024, 9, 24, 11, 9, 41)`
  在每次上电时执行（示例源码第 78-87 行）。RTC 芯片本身走时正常（跨分钟进位正确）。
- **处理**：本工程固件改为「RTC 早于编译时间才用编译时刻兜底」，并提供串口
  `set YYYY-MM-DD HH:MM:SS` 手动校准；后续接入 GNSS 后用 RMC 的 UTC 时间自动校准。
- **验证**：烧录本工程固件后 RTC 显示 2026-10-11，串口 `set` 校准到 16:11:22，
  复查 16:11:24（正常走时）✓

## 2026-10-11 真机滑动手势不切页（三个连环坑，全部已修）

**现象**：真机上左右滑动无法切换页面；串口诊断显示 LVGL **确实识别出了手势**
（LEFT=6 RIGHT=3），但页面不切换；速度页显示也与模拟器不同（另见下方第 4 条）。

**排查手段**（可复用）：固件内置串口命令 `mem` / `dump` / `tp`（**没有 `touch`**：那只是早期临时入口，已删除），
配合模拟器的 `--gesture-test`（自动注入拖拽并打印 LVGL 输入内部状态与命中测试）。

### 坑 1：`lv_obj` 默认给子对象加 `GESTURE_BUBBLE`

`lv_obj.c` 构造函数：`if(parent) obj->flags |= LV_OBJ_FLAG_GESTURE_BUBBLE;`
手势检测会沿父链上移目标（`lv_indev.c: while(has_flag(GESTURE_BUBBLE)) gesture_obj = parent`），
于是手势被转发给**屏幕**，页面容器的回调永远不执行。
→ 解决：页面/子对象统一清掉 `GESTURE_BUBBLE`（连同 `SCROLLABLE` 等一组默认标志）。

### 坑 2：`SCROLLABLE` 会吞掉手势

`lv_indev.c` 的 `indev_gesture()` 开头即 `if(scroll_obj) return;` ——
**滚动与手势互斥**；而 `lv_obj_remove_style_all()` 只清样式、**不清标志**，
基类默认带 `SCROLLABLE`，于是拖拽被判为"滚动"、手势不发。

### 坑 3：隐藏"被按住的页面"会连环触发手势

即便修好 1、2，自己用 `LV_EVENT_GESTURE` 切页仍有问题：切页要隐藏当前页，
而隐藏被按住的页面会让 LVGL 重置输入状态，同一次拖拽反复判定手势
（实测一次拖拽触发 3 次：0→2→1→0，**转回原点**，看起来就是"滑不动"）。

**最终方案**：改用 LVGL 标准的**横向滚动容器 + 吸附分页**（`lv_tileview` 同款机制），
不再自己处理手势：容器尺寸 = **视口大小**，页面在其中并排摆放并超出边界，
`SCROLLABLE + SCROLL_SNAP_CENTER + 子对象 SNAPPABLE`，滚动结束用 `scroll_x` 反推当前页。

> 附带坑：容器若做成 `页数 × 屏宽`，则内容刚好填满容器 → **没有可滚动区域** → 依然滑不动。

### 坑 4：速度页与模拟器不一致（变体默认值）—— ⚠️ **已过时**

> **2026-10-14 更新**：速度表盘已**定稿为单一设计**（驾驶员表盘），
> V1–V4 与运行时 `--variant` 机制**已全部移除**，因此该问题**不可能再出现**。
> 以下保留原始记录，作为"同一份代码有两种取值来源"的案例。

原始记录：`ui_speed.c` 的 `s_variant` 默认是 0（V1），而模拟器一直用
`--variant 4` 启动，固件从未设置变体 → 真机显示 V1（数字+外环弧）而非 V5。
解决：默认值改为 4。**排查用 `dump` 打印元素树**即可发现
（V1 只有 arc+label，V5 应有 img 300×300 + meter + 6 个刻度数字）。

**仍适用的通用教训**：同一份代码若存在"编译期默认值"与"启动参数"两个来源，
不一致时**只有真机才暴露**。定稿后应把多余分支**删掉**，而不是靠默认值对齐 ——
本项目后续正是删除了变体机制。

**验证**：模拟器 `--gesture-test`：从第 1 页右拖 400px → 第 0 页；左拖 400px → 第 1 页 ✓

## 2026-10-13 屏幕旋转：**可行**（更正 2026-10-11 的错误结论）

> ⚠️ **本文早先记录的「90° 旋转不可行」是错误结论**，根因是当时的**配置错误**。
> 本节为更正后的完整结论，旧结论保留在末尾「历史记录」中以免重蹈覆辙。

### 结论：LVGL 软件旋转**官方支持且实测可用**

**依据**：官方示例 `06_LVGL_Widgets.ino` 正是这么做的——
```c
disp_drv.sw_rotate = 1;              // add for rotation
...
lv_disp_set_rotation(NULL, LV_DISP_ROT_90);   // 按 IMU 姿态切 0/90/180/270
```
官方 `troubleshooting_ZH.md` 也要求「保持随附的旋转和触摸变换成套使用」。

### 之前为什么失败（关键教训）

当时**开着 `full_refresh`**。LVGL 在 `lv_refr.c` 里对这种情况会**直接放弃旋转**：

```c
if(disp_repr->driver->full_refresh && drv->sw_rotate) {
    LV_LOG_ERROR("cannot rotate a full refreshed display!");
    return;                      // ← 直接返回，画面根本不更新
}
```

于是屏幕上出现陈旧/错乱内容 —— 当时被我误判为"性能不足导致的撕裂/果冻效应"，
实际是 **LVGL 拒绝旋转后画面没刷新**。

**正确配置**（本工程现已采用）：
- `disp_drv.sw_rotate = 1`（常开；方向为 NONE 时**零开销**，不进旋转路径）
- **不要**开 `full_refresh` / `direct_mode`（本工程用 partial 模式，本就满足）

### 实测性能（真机，iPhone 12 无关；8 次整屏重绘取最大）

| 方向 | 渲染最大 | 相对 0° | 实现 |
|------|---------|--------|------|
| 0° | 102 ms | 基线 | 不进旋转路径 |
| 180° | 115 ms | **+13 ms** | `draw_buf_rotate_180`：原地首尾反转，**无需临时缓冲** |
| 90° | 123 ms | **+21 ms** | 见下 |
| 270° | 122 ms | **+20 ms** | 见下 |

**90°/270° 为何不贵**：本屏是**正方形** 466×466，全屏脏区满足 `area_h >= area_w`
→ 走 `draw_buf_rotate_90_sqr()`，是**原地 4 向旋转**（`draw_buf_rotate4`），
**不分配临时缓冲**。只有**非正方形**的小脏区才回落到 10KB 临时缓冲分块转置
（`LV_DISP_ROT_MAX_BUF`），但那种情况下面积本身就小。

### 正确性验证（模拟器，像素级）

真机无法回读面板内容，故用模拟器（同一份 LVGL 代码）量化验证：

| 方向 | 与「自身旋转」的平均像素差 | 与未旋转原图 |
|------|------------------------|-------------|
| 90° | **0.00**（精确匹配逆时针 90°）| 32.66 |
| 180° | **0.00** | — |
| 270° | **0.00** | — |

即旋转结果**像素级精确**。

### 圆形屏带来的额外好处

本屏为 **1.75" 圆形** 466×466：
- 旋转后**仍是同一个圆** → 无长宽比/布局副作用，**不需要重新设计界面**
- 触摸坐标由 LVGL 自动做逆变换（`lv_refr.c` / `indev_pointer_proc`），无需自行处理

> 这也是"按竖向重排界面"这一方案**不再需要**的原因：
> 想要竖屏效果，直接旋转即可（且开销仅 +20ms/整屏帧）。

### 运行方式

## 2026-10-10 模拟器里时钟不走 / 秒针不动

- **现象**：模拟器界面能正常显示，但数字时钟不刷新、模拟时钟秒针静止不动。
- **复现步骤**：`./dashboard_sim` 打开窗口观察数十秒。
- **原因**：`simulator/main.c` 主循环**从未调用 `lv_tick_inc()`**，且 `lv_conf.h` 未启用
  `LV_TICK_CUSTOM`（默认 0，即需要手动喂心跳）。结果 LVGL 内部时间恒为 0，
  `lv_timer_handler()` 认为没有时间流逝 → **所有 `lv_timer` 都不触发**。
  界面只在初始化时渲染了一次，所以看起来"卡住"。
- **解决**：在主循环中按经过的真实毫秒调用 `lv_tick_inc(delta)`：
  ```c
  Uint32 now_tick = SDL_GetTicks();
  if (now_tick != last_tick) { lv_tick_inc(now_tick - last_tick); last_tick = now_tick; }
  lv_timer_handler();
  ```
- **验证结果**：间隔约 4 秒截取两张图，橙色秒针角度从 144.2° 变为 168.1°（差 24° ≈ 6°/s
  的每秒一跳）→ 确认定时器已正常工作。

### 真机注意事项（重要）

ESP32 上同样需要**稳定的 LVGL 心跳源**，通常由硬件定时器周期性调用 `lv_tick_inc()`。
微雪官方 Arduino 示例已包含该机制（`EXAMPLE_LVGL_TICK_PERIOD_MS 2` + 定时器回调），
因此**移植 UI 代码到固件时必须沿用官方示例的 tick 配置**，否则会出现与本条完全相同的
"界面静止"现象。这是本坑对固件阶段的直接启示。

## 2026-10-12 并发缺陷：取锁失败被误判为"从未收到"→ 状态闪跳

**代码**：`ble_telemetry_age_ms()`（原实现）

```cpp
uint32_t r = 0;
if (s_mtx && xSemaphoreTake(s_mtx, pdMS_TO_TICKS(10)) == pdTRUE) { r = s_rx_ms; ... }
if (r == 0) return UINT32_MAX;   // ← 取锁失败时 r 也是 0
```

**缺陷**：`s_rx_ms == 0` 被用来表示"从未收到过"，但**取锁超时**时 `r` 同样保持 0，
于是偶发地把"并发中取不到状态"误报成"从未收到"。调用方 `ble_update()` 见
`age == UINT32_MAX` 即判为**数据超时（STALE）**，导致正常行驶中出现
**LIVE → STALE → LIVE 闪跳**（UI 观感与告警都受影响）。

**修复**：
1. 新增显式标志 `s_have_rx`（收到首条有效遥测时置位），与 `s_rx_ms == 0` 解耦；
2. 取锁失败返回独立哨兵 `BLE_AGE_UNKNOWN (UINT32_MAX-1)`；
3. 调用方遇到 `BLE_AGE_UNKNOWN` 时**保持上一次状态**，不判超时。

**通用教训**：跨任务共享状态时，不要把"未初始化/从未发生"的哨兵值与
"本次读取失败"混用同一返回值——两者语义不同，混用会造成间歇性误判
（且极难复现）。

## 2026-10-12 真机全局卡顿（滑动掉帧、秒针卡住）—— 无效化风暴（已修复）

**现象**（用户实机反馈）：设备整体很卡；左右滑页掉帧；模拟时钟秒针跳动也会卡住。

**根因**（回归，本会话第 7 轮引入）：`ble_update()` 每圈主循环（约 100Hz）调用
`ui_speed_set_fix()/set_speed()`，而这些 setter **不做变更检测**直接调
`apply_state()`。LVGL 8.4 的 `lv_meter_set_indicator_value()` **无条件 invalidate**
（值相同也会把指针区域标脏），`lv_img_set_src()`/`lv_label_set_text()` 同理
（源码 lv_meter.c:207 起：inv_line 不判断新旧值是否相等）。
→ 空闲时也以每秒数十次把速度页大块区域标脏，CPU 全耗在重绘"没变的像素"。

**客观证据**（模拟器复现工具 `--ble-sim` + flush 计数）：
- 复刻固件每帧调用：**55.5 flush/秒**
- 正常数据驱动基线：**2.6 flush/秒**
- 修复后（同样复刻调用）：**2.6 flush/秒** —— 与基线完全一致，风暴消除

**修复**（两层）：
1. `ui_speed_set_speed/fix/heading/driver_state` 全部加**变更检测**（值不变直接 return）；
   `apply_state()` 内部对插画与状态标签同样加已显示状态判断（速度动画期间不重复 set）
2. 固件 `ble_update()` 限频 50Hz（数据本身 2Hz，限频只降空转）

**回归**：指针随速度变化仍正常动（y 重心 305→73）；UI 像素回归 10 项 +
单测 167 项全绿；固件编译通过（50% Flash）。

**教训**：LVGL 8 的多数 setter 不做同值短路；高频调用方必须自己做变更检测。
凡是以循环频率调用 UI setter 的代码，都要问一句"值没变时会怎样"。

## 2026-10-13 滑页仍卡：逐项实测定位（单帧 ~240ms）

**背景**：无效化风暴修复后时钟不卡了（空闲重绘 0–2/s），但左右滑页依然掉帧。
新增固件内计时（心跳输出「渲染最大 / 占空 / QSPI 传输」）后逐项测量：

| 测量项 | 数值 | 说明 |
|--------|------|------|
| 单帧渲染峰值（滑页时）| **240 ms** | 一次 lv_timer_handler 的最长耗时 → 约 4 fps |
| 其中 QSPI 传输（单次最大）| **56 ms** | 全屏 434KB → 实测 7.75 MB/s（40MHz QSPI 理论 20MB/s）|
| 其中 LVGL 绘制 | **~185 ms** | 主要成本 |
| 占空比（5s 窗口）| 63–64% | CPU 大部分时间在渲染 |

**按页面拆分**（成对滑页反解，cost(a+b) = cost(a)+cost(b)）：
- 模拟时钟页 ≈ **145 ms**（61 小节刻度 + 13 整点刻度 + 3 指针）
- 速度表页 ≈ **98 ms**（41 刻度 + 渐变弧 + 300×300 插画）
- 数字时钟页 ≈ **98 ms**（138px 抗锯齿大字体）

**结论**：瓶颈是 LVGL 软件绘制（77%），不是 QSPI（23%）。lv_meter 是单对象，
任一脏区都会重算**全部**刻度；滑页时两页同时可见 → 两页的表盘都要重画。

**PSRAM 全帧缓冲的效果**（已实装并保留）：重绘次数从 10–67/s 降到 2–6/s
（脏区只切 1 块，符合设计），但单帧耗时未降——说明分块开销不是主因。

**下一步候选优化**（按收益排序，均未实施）：
1. **静态表盘烘焙为图片**：刻度/数字/渐变弧都是静态的，只有指针在动。
   离线用 PIL 渲染成 466×466 RGB565（外观不变甚至更精细），页面 = 1 次图片
   拷贝 + 指针线。预计单帧 240ms → 70–90ms。Flash 成本约 434KB/张（现有余量
   1.5MB，可放 2–3 张）。
2. **大号字体去抗锯齿**（138px → 1bpp 点阵）：预计数字时钟页 98ms → ~35ms，
   但边缘会有锯齿（视觉有损，需用户确认）。
3. **提高 QSPI 时钟**（40→80MHz）：若面板支持，传输 56ms → ~30ms；有花屏风险。
4. **缩短/取消滑页动画**：不改单帧成本，只缩短卡顿持续时间。

**教训**：LVGL 8 的 lv_meter 是「整对象重绘」模型；刻度越多、对象越大，
滑页（整屏重绘）成本越高。静态表盘应烘焙成图片，只保留动态的指针。

### 滑页优化第一轮结果（2026-10-13 实测）

**已实施并实测的改动**：

| 改动 | 效果（实测） |
|------|------------|
| PSRAM 全帧绘制缓冲（partial 模式，默认启用）| 重绘 10–67/s → **2–6/s**（脏区由 10 块降为 1 块）|
| QSPI 分块 1024 → 4096 像素（`-DESP32QSPI_MAX_PIXELS_AT_ONCE=4096`）| 事务数 212 → 53；单次传输 56 → 54 ms |
| QSPI 时钟 40 → 80 MHz（`QSPI_SPEED_HZ`）| 单次全屏传输 **56 → 43 ms**（约 10 MB/s 有效带宽）|
| 合计（滑页单帧）| 243 → **228 ms** |

**刻度成本实测（决定性实验）**：把模拟时钟的分钟刻度 61→13、整点 13→4
（仅测量用，已还原），滑页单帧 228 → **180 ms**。
→ **74 个刻度约值 50 ms**（每刻度 ~0.7ms，lv_meter 每 tick 都要三角函数
+ 线/弧绘制）。这直接证明「静态表盘烘焙成图片」能省下这 ~50ms。

**仍未解释的基座成本**：滑页一帧 = QSPI 43ms + 刻度 ~50ms + **其余 ~130ms**。
推测与「两个页面各做一次整屏不透明底色填充」（434K 像素写入 PSRAM）有关，
✅ 已实施（见下方「页面背景透明化」小节）。

**注意**：80MHz 属硬件时序变更，需目视确认无花屏/噪点；若异常则改回
`QSPI_SPEED_HZ 40000000`（4096 分块的收益可保留）。

### 触摸「滑不动/操作无反应」根因与修复（2026-10-13）

**现象**（用户实测）：滑页很困难、经常完全无反应。

**根因**：单帧渲染约 200ms，LVGL 的 indev 读取被拖慢到 **约 4 次/秒**。
用户快速滑动时，「按下 → 移动 → 抬起」整个序列可能**全部落在一次渲染阻塞内**，
LVGL 下一次读取时手指已经离开 → 完全感知不到这次触摸。

**修复**：`touch_sample_cb` 用 esp_timer 以 **100Hz 独立采样**触摸（不受渲染阻塞
影响），并**锁存按下事件**（`s_tp_press_latch`）：
LVGL 每次读取时，若期间发生过按下，就补报一次 PRESSED，下一次读取才报 RELEASED，
从而保证 LVGL 一定看到一个完整的「按下→移动→松开」序列。

**实测**：修复后用户确认「能翻页了」（此前是操作无反应）。

**注**：手势计数（LV_EVENT_GESTURE）恒为 0 属正常——分页由滚动容器消费拖拽实现，
不会触发屏幕级手势事件。

### 页面背景透明化（2026-10-13）

三个页面的 `bg_opa` 由 `LV_OPA_COVER` 改为 `LV_OPA_TRANSP`：整屏黑色底色改由
`scr` 统一提供。滑页时两页同时可见，原来每页各做一次整屏不透明填充
（434K 像素 × 2），现在只填一次。
实测滑页单帧 228 → **217–222 ms**（小幅收益，但零风险且视觉不变）。

**当前滑页单帧构成**：QSPI 43ms + 刻度 ~50ms + 其余 ~130ms。
QSPI 43ms 是硬件数据通路的硬下限（434KB，实测 ~10MB/s），即**即使零渲染成本，
上限也只有约 23fps**；要把滑页做到真正顺滑，需要「blit 平移 + 只重绘新露出条带」
的自定义滚动（利用现有全帧 PSRAM 缓冲），预计单帧可降到 ~20–30ms。

### 滑页优化第二轮：静态表盘烘焙（2026-10-13，已完成）

**做法**：把「刻度 + 渐变弧 + 刻度数字」这些**不随数据变化**的元素离线渲染成
466×466 RGB565 图片（`tools/make_dial_faces.py`，4× 超采样 + LANCZOS 缩放，
边缘比运行时逐刻度绘制更平滑），运行时只保留会动的指针：

- `dial_analog`：61 分钟刻度 + 13 整点刻度 + 数字 1-12（原 74 个 lv_meter 刻度 + 12 个 lv_label）
- `dial_speed`：41 小刻度（按速度渐变着色）+ 7 大刻度 + 数字 0/40/…/200
  （原 48 个刻度 + 2 条渐变 scale_lines + 6 个 lv_label）

layer 顺序很关键：**表盘图必须最先创建（最底层）**，否则整屏白底图片会盖住
驾驶员插画（第一版就踩了这个坑，已修）。

**实测效果（滑页单帧峰值）**：

| 页面组合 | 优化前 | 优化后 |
|---------|-------|-------|
| 模拟时钟 ↔ 数字时钟 | 243 ms | **91–109 ms** |
| 数字时钟 ↔ 速度表 | 196 ms | **113 ms** |
| 模拟时钟 ↔ 速度表 | 243 ms | **117 ms** |

**总体：滑页单帧 243 ms → 约 110 ms（−53%，约 4fps → 9fps）**，
其中 QSPI 传输 43ms 已是硬件下限。Flash 占用 50% → **77%**（两张表盘 868KB）。

**回归**：UI 像素 10 项 + 单测 167 项全绿；两张表盘图与设计几何一致
（几何常量在生成器里与 ui_analog.c / ui_speed.c 对应）。

### 「滑一下要等一会才能再滑」根因与修复（2026-10-13，真机日志定位）

**现象**（用户实测）：滑到一页后必须等一会才能继续滑，无法连续切换多个仪表。

**诊断方法**：给 100Hz 触摸采样加日志，打印每次「按下→抬起」的位移/时长、
flick 判定结果、以及翻页前后的页码。真机日志显示：

```
[触摸] flick dx=424 dy=-47 dt=181 ms
[翻页] flick dir=-1：页 2 → 2（未翻动：可能原生滚动已处理或已到边界）
```

采样器**每次都正确识别出 flick**（21/32 次抬起），但翻页被我自己加的守卫
挡掉了。守卫逻辑是「容器已被原生拖拽带走就不翻页」——而用户每次快滑都会把
容器拖走几十到几百像素，于是**几乎每一次 flick 都被拒绝**。

**根因**：100Hz 采样拿到的是完整轨迹，而 LVGL 的输入读取只有约 4 次/秒，
两者对「容器是否已滚动」的判断不一致。用 LVGL 的状态去否决采样器的判定，
在慢渲染场景下必然出错。

**修复**：
1. `ui_pages_flick()` **去掉该守卫**：快滑是明确的用户意图，一律按当前页翻一页
2. 翻页动画改为**自定义 130ms 短动画**（`page_scroll_anim_cb`）；
   LVGL 内置吸附按像素速度计算、时长 200–400ms，偏钝
3. 启动自定义动画前先 `lv_anim_del(s_cont, NULL)`，避免与 LVGL 内部
   `scroll_x_anim` 同时跑而互相抢 scroll_x
4. 新增 `ui_pages_settle()`：缓慢拖拽（未达 flick 阈值）松手后按最近页吸附，
   同样走 130ms 短动画

**验证**（真机日志）：连续快滑 12 次，每次 flick 都立即翻页，
边界正确不循环：
```
[翻页] flick dir=-1：页 2 → 1    [翻页] flick dir=-1：页 1 → 0
[翻页] flick dir=1：页 0 → 1     [翻页] flick dir=1：页 2 → 2（已到边界）
```

**教训**：慢渲染下不要用「LVGL 已处理过」去否决高频采样器的判定——
两个数据源的时序粒度差一个数量级，以低频方为准必然丢事件。

### 大号时钟字体去抗锯齿（2026-10-13 已完成，即方案 B）

数字时钟页的 138px 时间数字原用 `--bpp 4`（抗锯齿）——整屏重绘时每个字形

换来约 12-20ms/帧 的滑页收益与 143KB 的 Flash 节省。
`tools/make_fonts.sh` 已同步改为 bpp=1。

顺带删除已无引用的 `font_num_dial_38.c`（表盘数字 1-12 已烘焙进 dial_analog 图片）。

**滑页单帧总账：243 ms（优化前）→ 约 100 ms（−59%）**，

## 真机联调：速度 0 但指针指向 90（2026-10-13，已修复）

**现象**（用户真机实测）：iPhone 静止、仪表收到速度 0.00 m/s，但速度表指针
停在约 90 km/h 的位置。

**根因**：`ui_speed.c` 里残留着 GNSS 时代的**模拟默认值**：

```c
static float s_speed = 88.0f; /* GNSS 接入前模拟值 */
static bool  s_valid = true;
```

数据源改为 iPhone 后这两个默认值从未清理。链路进入 LIVE 时固件调用
`ui_speed_set_fix(true, 0)` 把 `s_valid` 置为 true，而 `s_speed` 仍是默认的 88
（因为 `ui_speed_set_speed()` 只在 `speed_ok` 为真时才被调用，速度为 0 时不会调用）
→ `apply_state()` 算出 `v = 88` → 指针停在 88 ≈ 用户看到的"90"。

**历史诊断方法**：当时用临时 `spd` 串口命令和速度状态查询接口，
真机直接读出「当前=88.0 km/h 有效=1」，一步定位。问题解决后这些临时入口已删除。

**修复**：
1. 默认值改为 `s_speed = 0.0f; s_valid = false;` —— 数据源为 iPhone 后，
   **任何时刻都不应存在「有效但没数据」的状态**
2. `ui_speed_set_fix()` 在置为无效时**同时清零 s_speed**，避免「无效→再次有效」
   的瞬间用旧速度画一帧（指针闪旧值）
3. 模拟器默认速度也改为 0（原本也是 GNSS 时代的 88）

**验证**：真机启动即 `当前=0.0 km/h`；`spd 120` → `spd reset` 可正确设置与归零；
模拟器速度 0 与 120 的帧差分析显示指针角度分别落在 135°（左下）与 297°（正上方），
与量程映射一致。

**教训**：数据源切换（GNSS → iPhone）时必须清理**所有**模拟/占位默认值。
「默认有效 + 非零默认值」是危险组合——它会在首个真实无效数据到来前伪造一个速度。

## 室外实测三 bug 修复（2026-10-13）

用户室外实测反馈三个问题，根因与修复如下。

### #1 时钟表盘隔几秒重置 —— 时间反复重校

**根因**：`time_sync_maybe()` 的重校阈值判断有缺陷：

```c
time_t now = time(NULL);                    // ← 只有**秒级**精度
int64_t diff_ms = (int64_t)now * 1000 - utc_ms;   // 与毫秒级 utc_ms 相减
if (s_time_synced && diff_ms >= -2000 && diff_ms <= 2000) return false;
```

手机发来的是**毫秒级** UTC，而 `time(NULL)` 截断到秒，两者边界错开时
`diff_ms` 天然可达 ±1000ms，叠加传输/处理延迟就逼近 ±2000 阈值
→ **频繁触发重校 → 反复写 RTC → 时钟界面跳变**。

**修复**：
1. 阈值 2s → **30s**（`TIME_RESYNC_THRESHOLD_MS`），正常驾驶期间零重写；
2. 改用 `gettimeofday()` 取毫秒级本地时间，消除精度不匹配；
3. 语义改为「**首次校时 + 仅偏差过大才重校**」——手机持续 2Hz 发时间戳，
   仪表本地走时足够准，无需实时校时。

**验证**：真机 40 秒零次重校（修复前会反复触发）。

### #2 速度指针跳针、更新慢 —— 阶梯式运动

**根因**：指针值是「**每 500ms 收到新包才走一段**」的阶梯运动：

- 旧 EMA 按**调用次数**收敛（每次 45%），
  但数据源只有 2Hz → 每个新包来后指针快速跳一下，然后停住等下一个包；
- 减速分支是**瞬时赋值**（`value = kmh`），完全无动画，跳变更明显。

**修复**：改为**按时间的固定时长斜坡**（`telemetry_ramp_*`，用户选择的"假线性"）：

- 每帧代入实际经过的 `dt_ms`，加速约 450ms、减速约 250ms 到达目标；
- **与帧率无关**：无论 50Hz 还是 5Hz 调用，相同时长走相同距离
  （有单测验证：50×20ms 与 5×200ms 结果一致）；
- 首次拿到有效值直接对齐（起步即准，不从 0 爬）；
- 无效数据时目标归零，经斜坡收回（不闪现旧值）。

固件侧：`ble_update()` 只调 `set_target()`，主循环 50Hz 调 `ramp_step()`。

### #2b 开机扫表动画（新增需求）

切到速度表盘时指针 **0 → 满量程 → 回落**，类似汽车启动自检：

- 两段动画（上升 420ms ease_out + 回落 460ms ease_in_out），
  用第一阶段 ready 回调启动第二阶段（不依赖延迟启动 API 的版本差异）；
- 动画期间置 `s_sweeping` **屏蔽数据驱动**，否则 2Hz 遥测会把扫表打断；
- 结束后解除屏蔽并用最新真实速度落位；
- 触发点：BLE 切表盘 / 滑动 flick / 松手吸附，统一走
  `ui_face_sweep_if_speed()`（集中"什么算速度表"的知识）。

**踩坑**：模拟器里首次验证「零差异」，原因是 `ui_speed_sweep()` 被放在
`ui_pages_init()` **之前**调用，此时指针尚未创建（`s_meter == NULL`）直接返回。
移到页面构建之后即生效（指针角度随时间 260°→336°→350°→落位）。

### #3 底部信息超框 —— 精简为数字速度 + 航向

原文案 `NE 45° · 12.3 km · MAX 87` 过长导致超框。
按用户要求改为 **`68 km/h  NE 45°`**，里程/最高速移到串口 `trip` 命令查询。
无有效速度时显示 `-- km/h`，避免把 0 误读成"真的静止"。

## 强退 App 重开后「BLE 状态一直初始化中」（2026-10-13，已修复）

**现象**（用户真机实测）：强退 App 再打开，BLE 状态卡在"初始化中"，
但点一下「开始驾驶」就恢复正常。

**根因**：`DriveSessionManager` 没有把子对象的 `@Published` 变化转发出去。

```swift
// ContentView 观察的是 session（DriveSessionManager）
// 而 BLE 状态在 session.ble 里：
var bleConnected: Bool { ble.isConnected }   // ← 普通计算属性，不触发本类重绘
```

链路：`BLEClient.state` 变化 → 只触发 `ble.objectWillChange` →
**`session` 的 objectWillChange 从未触发** → SwiftUI 不重绘 →
界面停在首次渲染时的快照（那时 `state` 还是 `.unknown` = "初始化中"）。
点「开始驾驶」会改 `session.isDriving`（`@Published`）→ 顺带触发重绘 → 界面才正确。

**修复**：
1. `DriveSessionManager` 订阅 `ble` 与 `location` 的 `objectWillChange`
   并向上转发（`forwardChanges()`，用 Combine 的 `sink` + `Set<AnyCancellable>` 持有）；
2. `ContentView` 增加 `.onAppear` **启动即自动连接**（`didAutoConnect` 防重复），
   用户不必先点「开始驾驶」。

**验证**：模拟器 XCUITest `BLEStateUITests`——启动后**不点任何按钮**，
界面即显示真实 BLE 状态（模拟器无 BLE 硬件 → 正确显示"不支持 BLE"），
断言"不应停留在初始化中"通过。

**顺带修的测试基建问题**：`LinkDiagnosticsUITests` 依赖模拟器 Freeway Drive
定位场景，而测试进程无法调用 simctl。直接跑 `xcodebuild test` 全量时会因场景
未启动而报 3 项失败，**极易误判为代码回归**（本次就踩了）。
已新增 `tools/run_ios_tests.sh` 自动起场景 + 设置 `DEVELOPER_DIR`，
并在测试文件顶部标注该环境依赖。

## 状态标签瞬态 STALE 闪烁（2026-10-13，已修复）

**现象**（用户观察 + 长稳测试数据）：仪表状态标签偶尔瞬间跳一下 STALE 又回到 LIVE。

**根因**（数据驱动）：室内**静止**时 iOS 主动降低定位更新频率到约 **1.25Hz**
（设备不动时的省电策略，非缺陷——长稳实测 Δ包 37-43/30s ≈ 1.25Hz，
而设计目标是 2Hz）。此时若某次定位回调略延迟，累计 2.5s 无包即触及
`BLE_STALE_MS` 超时阈值 → 状态标签闪一下。

**修复**：新增链路状态**显示防抖** `telemetry_debounce_apply()`：

- STALE 需**连续 3 次**判定才真正切换（抑制抖动闪烁）；
- 恢复 LIVE 等"好消息"**立即生效**（不延迟告知已恢复）；
- 非 STALE 状态（CONNECTING/WAIT_LOC/INVALID/HOLD）直接透传不参与防抖。

**关键设计——显示与指针分离**（安全优先）：

```c
link_raw  = 原始判定     → 驱动指针/数据有效性（过期即归零，绝不冒充当前值 §6.3）
link_disp = 防抖后状态   → 仅用于屏幕标签
```

防抖**只影响显示**，指针行为仍严格遵循"数据过期立即归零"。

**测试**：新增 12 项单测（含"交替抖动 10 轮不产生 STALE"这一用户所见场景的
回归），共 115 项 telemetry 断言通过。

**为何不改超时阈值**：放宽阈值会让真实断流时降级变慢（安全性下降）。
防抖方案在"消除闪烁"与"及时降级"之间取得平衡。

## 表盘列表上报超过 BLE 184 字节被截断（2026-10-20，已修复）

**现象**（用户视角）：仪表上滑得到照片表盘，但 **App 的表盘列表里没有它**；
更早一版甚至**一个表盘都看不到**。串口看设备自己是好的（`face` 能列出 6 个）。

**诊断顺序**（这次做对的地方：先看设备上报的真实数据）：

```
[表盘] 启动恢复：当前=5(photo)，5/6 启用     ← 先查出"照片表盘是关的"（见下一条）
[表盘] 已上报列表（476 字节，6 个表盘）      ← 修完掩码后仍然看不到，量体积
```

**根因（两层）**：

| 层 | 原因 | 结果 |
|----|------|------|
| 体积 | iOS 单次 BLE Read/Notify 上限约 **184 字节**，而对象格式（每项带 `label`/`group`/`on`）6 个表盘要 **476 字节** | 被截断 → JSON 解析失败 → App 认为"没有列表" |
| 判别字段 | 压缩时把 `"t":"faces"` 改成了 `"t":"f"`，而 App 的入口是 `guard root["t"] == "faces"` | 整包被判成"不是表盘上报" → **一个表盘都没有** |

中间版本压到 **371 字节**，仍然超过 184 —— **不够**，必须换结构。

**修法（最终）**：只发**名字数组**，顺序即 id：

```json
{"t":"f","c":6,"m":63,"u":5,"bright":200,"rot":0,"screen":1,
 "f":["analog","digital","speed","color","nav","photo"]}
```

- `id` = 数组下标；`group` 由名字映射；`on` = `(m >> id) & 1`；
- 去掉 `label`（App 本来就有 `?? name` 兜底）；
- App 同时接受 `"t":"faces"` 与 `"t":"f"`，两边任一边单独升级都不会挂；
- 结果：**173 字节**，稳在 184 以内。

**验证**：真机 `[表盘] 已上报列表（173 字节，6 个表盘）`，App 列表 6 个齐全。

**教训**：

1. "设备设置了但 App 看不到" → **先量上报体积对不对得上传输上限**，别先怀疑展示层。
2. **改协议判别字段名时，生产端与消费端必须同时看一遍**（这次只改设备端，
   症状从"少一个"恶化成"一个都没有"）。
3. 单次 BLE 载荷是**硬上限**，不是建议值；表盘继续增加时要走 Read Blob 分片。

> 协议细节见 [`ble.md`](ble.md#载荷格式read-取回紧凑数组)。

## NVS 掩码导致新增表盘看不到（2026-10-20，已修复）

**现象**：固件新加了「照片表盘」（id 5），滑动能到，但 **App 的表盘列表里没有**；
串口 `face` 能看到它，但启动日志写着 **`5/6 启用`**。

**根因**：表盘的"启用/隐藏"是**位掩码**，存在 NVS 里。这个掩码是**只有 5 个表盘时**
存的（bit0..4），后来加了第 6 个 → **旧掩码里 bit5 = 0**。
`restore_face_state()` 无法区分"用户主动隐藏"与"新增表盘还没设过"，
于是把照片表盘当成被隐藏，`ui_face_enabled(5)` 一直是 false。

**修法**：存掩码时**一起存当时的表盘总数**（`fcount`）。恢复时：

```
index >= saved_fcount  →  视为新增，强制启用
没有 fcount 的老设备    →  按 5 处理（正是当时的总数）
```

**验证**：

```
修前：[表盘] 启动恢复：当前=…，5/6 启用      ← 照片表盘是关的
修后：[表盘] 启动恢复：当前=5(photo)，6/6 启用
```

**教训**："新功能在设备上不出现"这类问题，**先看设备上报的数据**
（`6 个表盘` 里到底几个 enabled），不要先怀疑 App 的展示层；
**凡是"持久化的集合 + 后来会扩容"的结构，都要把"元素个数"一起持久化**。

## App 打开提示「不再可用」/ 无法验证 App

**症状**：iPhone 上点 App 图标，弹窗说「不再可用」「无法验证」或直接闪退。

**原因**：**描述文件过期**。免费 Apple ID 的 App Development 描述文件**只有 7 天有效期**，
到期后系统拒绝启动 App。

**排查顺序**：

1. **Xcode 的 Apple 账号是否还登录着**
   ```bash
   xcodebuild -project ios/CarDashboardPhone/CarDashboardPhone.xcodeproj \
     -scheme CarDashboardPhone -allowProvisioningUpdates build
   ```
   - 报 `No Accounts: Add a new account in Accounts settings`
     → **账号登录失效**，去 Xcode → Settings → Accounts 重新登录（要密码 + 2FA）。
   - 报 `No profiles for 'com.cardashboard.CarDashboardPhone' were found`
     → 同上；登录后会自动生成描述文件。

2. **账号正常，只是过期了** → 重跑一次：
   ```bash
   tools/install_app.sh
   ```
   （脚本带 `-allowProvisioningUpdates`，会自动续期并重装。）

3. **仍然不行** → 重启手机后重试；或先在手机上删掉 App 再装。

**长期省事**：付费 Apple Developer 账号（$99/年）描述文件有效期 **1 年**，
不用每 7 天折腾一次。
