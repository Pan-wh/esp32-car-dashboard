## 二、架构与职责边界

### 2.1 数据流

```
iPhone CoreLocation (WGS84)
      │ HTTPS
      ▼
自建 Node 网关 ──> 高德 Web 服务 API
      │ RouteBundle (GCJ-02)
      ▼
iPhone 上的导航核心（路线进度 / 偏航判定 / 重算 / 到达）
      │ BLE（现有 JSON 协议，见 docs/ble.md）
      ▼
ESP32：nav_parse → ui_nav（只做显示）
```

### 2.2 职责划分（**关键设计**）

| 端 | 负责 | **不负责** |
|----|------|-----------|
| **网关** | 持有高德 Key；转发路线/路况请求；坐标系转换；限流 | 不做导航状态机 |
| **iPhone** | 定位、路线匹配、进度跟踪、偏航判定、重算、到达判定 | 不直接持有高德 Key |
| **ESP32** | **只做显示**：把收到的快照画出来 | ❌ 不跑路线规划、不跑偏航、不查地图 |

> 这一划分参考自 moto-gps 的架构（其 `docs/ARCHITECTURE.md` 明确写了
> "ESP32 不再次运行高德、路线匹配或偏航状态机，也不得把 BLE 字段直接写入 LVGL"）。
> **原因**：ESP32 内存/算力有限，且把状态机放在手机端才能在 App 切后台/重连时保持连续。

### 3.3 第三步：部署网关

**核心与副作用的边界（重要设计约定）**：

导航核心（`NavCore.swift`）**只做纯计算，不自己发网络请求**。
偏航时它返回一条**命令**（`NavCommand.requestRoute`），由平台适配层执行：

```
handle(fix:nowMs:) -> NavOutcome { snapshot, commands }
                                    │         └─ 需要调用方执行的副作用
                                    └─ 给 UI / BLE 的显示状态
```

这样做的好处：核心保持纯逻辑（可单测、不依赖网络、不绑定数据源），
网关故障也不会让核心进入未定义状态。这与参考项目 `nav_core.hpp`
（命令由平台适配器分发）的思路一致，代码为独立实现（见 decisions.md D-009）。

**网关职责**：接收 App 请求 → 附加 Key → 调高德 → 转换坐标 → 返回精简 RouteBundle。

> ✅ **本项已实现**：代码在 [`gateway/`](../gateway/README.md)（Node，**零依赖**）。
> 已含坐标转换、高德客户端、响应归一化、认证、限流、无缓存。
> 下面保留设计说明作为验收对照；具体用法见 gateway README。

已实现的接口：

| 接口 | 作用 | 状态 |
|------|------|------|
| `GET /health` | 存活与配置自检（不回显 Key）| ✅ |
| `POST /route` | 起终点 → 路线（含 steps：动作/距离/道路名）| ✅ |
| `POST /convert` | WGS84 → GCJ-02 | ✅ 已并入 `/route` 内部（手机端需本地转换，见 §3.6）|
| `POST /traffic` | 路况刷新 | ⬜ 未实现（可选）|

**环境变量（Key 绝不入库、绝不进 App）**：

```bash

PORT=8080
ALLOWED_ORIGIN=                 # 空表示不启用 CORS（见 §3.5）
```

### 3.4 第四步：App 侧接入（✅ 2026-10-14 完成）

- App 只请求**自己的网关**，不直连高德。
- 复用现有 BLE 通路下发导航消息（协议见 [ble.md](ble.md)），
  `{"t":"nav","state":…,"maneuver":…,"dist_m":…}`。
- 路名当前**不显示**（决策见 [ble.md](ble.md)）→ 暂不需要中文字模。

#### 已实现的接入内容

| 组件 | 作用 |
|------|------|
| `Nav/GatewayClient.swift` | 网关客户端、`RouteBundle` 解码、`RouteProvider`、`RerouteDispatcher`。**与 `tools/nav_sim` 共用同一份**（模拟器构建时直接编译此文件）|
| `Nav/NavPacket.swift` | 下发格式 `{t:nav,state,maneuver,dist_m}`；`dist_m` 未知时**省略字段**而非发 0 |
| `Nav/NavSession.swift` | 唯一中枢：定位 →（WGS84→GCJ-02）→ `NavCore` → 快照 → BLE；处理偏航重算 |
| `BLEClient.sendNav(snapshot:)` | 复用遥测特征下发；**断连不补发**（导航指引时效性极强）|
| `navTab`（ContentView）| 状态/剩余里程、目的地输入（**中文地名或经纬度**）、开始/停止、网关配置（@AppStorage）|

#### 实现时踩过并已修的坑（改动前务必先看）

1. **`NavCore` 不是 `Sendable`** → 绝不跨线程。网络请求放后台，拿纯数据回主线程才 `core.setRoute`。
   为此把 `RerouteDispatcher` 拆出 `fetchNewRoute()`（只取路线），使"坐标换算+折线校验"仍只有一处实现。
2. **`GatewayClient.fetchRoute` 是同步实现**（信号量）→ 在主线程调用会冻住界面。
3. **定位时间戳必须用 `location.timestamp`**，不能用"当前时间"——否则核心无法判定数据已过期。
4. **`@Published` 赋值即发通知** → 抑制无效刷新只能靠"不赋值"，不能靠补发 `objectWillChange`。
5. **漏 `"t":"nav"`** → 固件会把它当遥测解析而失败（两者共用同一特征）。
6. **导航必须能独立于「开始驾驶」** → 否则用户只点「开始导航」会永远停在"等待定位"。
   现约定：**「开始导航」等同于「开始驾驶」**（自动连仪表 + 启动定位与遥测），
   停止时只回收"导航顺手开的那次驾驶"。

#### 目的地输入与地理编码

`POST /geocode {address, city?}` → `{results:[{name,address,lon,lat}]}`（高德 `v3/geocode/geo`）。

⚠️ **坐标系陷阱**：高德返回 **GCJ-02**，而客户端约定"目的地一律 **WGS84**"（客户端内部还会再转 GCJ-02）。
网关必须**先转回 WGS84** 再返回，否则会双重转换、**偏移数百米**。

### 3.5 安全基线

| # | 要求 | 原因 |
|---|------|------|
| 1 | **Key 只放服务端** | 客户端可被反编译；Key 泄露会导致配额被盗用（协议 §4.5 要求妥善保管）|
| 2 | **CORS 不是认证** | 若网关公网可达，必须加访问控制（token / IP 白名单 / mTLS）|
| 3 | **必须 TLS** | 否则 Key 与位置数据明文传输 |
| 4 | **限流** | 防止误用刷爆配额（协议 §3.7 超限会被拒绝或计费）|
| 5 | **不记录完整轨迹日志** | 位置属个人信息，遵循最小化原则 |
| 6 | **依赖定期更新** | Node/上游库漏洞 |

> 参考项目在此处的自述："网关当前只有基础输入校验、限流和 CORS；
> **CORS 不是认证**。公开部署前必须自行配置访问控制、TLS、上游配额限制与监控，
> 不要无保护公开高德代理。" 本项目沿用同样的告警。

### 3.6 坐标系转换（WGS84 与 GCJ-02）

| 数据源 | 坐标系 |
|--------|--------|
| iOS CoreLocation | **WGS84** |
| 高德 | **GCJ-02**（火星坐标）|

**必须转换**，否则会有数十~数百米偏移。两种做法：

| 做法 | 优点 | 注意 |
|------|------|------|
| 用高德的**坐标转换接口** | 合规、准确 | 消耗配额；见官方文档 |
| 本地实现转换算法 | 不耗配额、离线可用 | 属公开算法；**但要注意协议 §3.5 关于数据缓存/存储的限制** |

⚠️ **协议 §3.5 提示**：不得直接存储、缓存或抓取高德服务内容。
**路线几何的缓存策略需评估** —— 本项目倾向**只在内存中保存当前路线**，
不落盘、不做离线包。

## 五、后续开发任务

> 用户 2026-10-14 提出，尚未开始。**动手前先读每条的"前置/风险"**。

### 5.1 路显（路名显示）

现状：仪表 nav 表盘**只显示"距离 + 箭头"**（用户当初的决策 j2，见
[ble.md](ble.md)）。协议里也**没有路名字段**，这样设备侧就不需要中文字模。

要加上路名，三处都得动：

| 层 | 要做的事 |
|----|---------|
| 协议 | `{t:nav,...}` 增加 `road` 字段（**UTF-8 中文**）；注意 MTU：iOS 实到约 185 字节，路名要限长 |
| 固件 | 需要**中文字模**（现有字体是拉丁/数字）；nav 表盘加一行路名 |
| App | `NavSnapshot` 已有 `NavStep.roadName`，把它带进 `NavPacket` 即可 |

**风险**：
- **字模体积**：中文字模动辄数百 KB～数 MB。当前 Flash 已用 **59%**（1.88 MB / 3 MB）。
  要么按需子集化（只含常用字 + 路名用字），要么放 **SD 卡**（见 5.2）。
- **更新频率**：路名随路段变化，不必每包都发（变了才发可省带宽）。

### 5.2 地图包 / 离线资源放 SD 卡

现状：**TF 卡已实测可用**（原生 1-bit SDMMC：CLK=GPIO2 / CMD=GPIO1 / D0=GPIO3；
`sd` 串口命令可查状态与目录）。实测卡：**SDHC 7.3 GB，可用 5.74 GB**。

固件已有 `SD_MMC` 挂载（启动时自动尝试；失败不影响启动）。
**尚未做**：把资源真正放到卡上。

可放的东西与收益：

| 内容 | 收益 | 备注 |
|------|------|------|
| **中文字模**（见 5.1）| ⭐ **省下数 MB Flash**（现 Flash 已 59%）| **SD 卡的首选用途**，见 decisions.md D-010 |
| 图片/背景素材 | 功能②（图片背景 + 时钟）| 已有 9.9 MB 未用 ffat 分区也可用 |
| 行程日志 / 轨迹 | 数据留存 | — |
| ~~离线地图瓦片~~ | — | ❌ **不放设备**：本板无 GNSS，地图放设备无法让设备独立工作；参考项目同样选择放手机侧。见 D-010 |

**风险**：
- ⚠️ **高德协议 §3.5 明确禁止"直接存储、缓存或抓取本服务内部数据、图片"** ——
  地图瓦片若来自高德则**不能落盘**。要做离线地图须换**允许离线**的数据源（如 OSM）。
- SD 卡是**可插拔**的：所有依赖它的功能都必须能**优雅降级**（拔卡不能崩、不能黑屏）。
- 挂载要在启动早期完成，且**不能阻塞**（当前实现是失败即放弃，不重试）。
