《高德地图开放平台服务协议》（更新日期 2025-12-03）**第 3.4 条**原文：

> **3.4** 除非我们专门授予您明确清晰的书面许可，**您不得将本服务及相关内容应用于车载场景**
> （包括但不限于将本服务及相关内容以任何方式集成在**车载设备**、或用于投射至车载设备的应用等），
> 不得将本服务及相关内容用于模型或算法训练及相关数据集构建，若您有上述服务场景需求，
> **应当另行与我们协商相关许可事宜**，具体以双方另行签署的书面协议的约定为准。

来源：<https://developer.amap.com/pages/terms/>

**本项目属于该条描述的场景**（ESP32 车载仪表 + 手机侧投射导航指引）。
协议**未对"个人自用"作例外**。

## 二、架构与职责边界

### 2.1 数据流

```
iPhone CoreLocation (WGS84)
      │ HTTPS
      ▼
自建 Node 网关 ──> 高德 Web 服务 API
      │ RouteBundle (GCJ-02)
      ▼
iPhone 上的导航核心（路线进度 / 偏航判定 / 重算 / 到达）
      │ BLE（现有 JSON 协议，见 docs/ble.md）
      ▼
ESP32：nav_parse → ui_nav（只做显示）
```

### 2.2 职责划分（**关键设计**）

| 端 | 负责 | **不负责** |
|----|------|-----------|
| **网关** | 持有高德 Key；转发路线/路况请求；坐标系转换；限流 | 不做导航状态机 |
| **iPhone** | 定位、路线匹配、进度跟踪、偏航判定、重算、到达判定 | 不直接持有高德 Key |
| **ESP32** | **只做显示**：把收到的快照画出来 | ❌ 不跑路线规划、不跑偏航、不查地图 |

> 这一划分参考自 moto-gps 的架构（其 `docs/ARCHITECTURE.md` 明确写了
> "ESP32 不再次运行高德、路线匹配或偏航状态机，也不得把 BLE 字段直接写入 LVGL"）。
> **原因**：ESP32 内存/算力有限，且把状态机放在手机端才能在 App 切后台/重连时保持连续。

## 三、部署

### 3.1 前置条件

| 项 | 要求 |
|----|------|
| 高德账号 | 个人开发者认证（研究学习用途）|
| 服务器 | 能跑 Node.js 的机器（本地 / VPS / Docker 均可）|
| 域名 + TLS | **若对公网开放则必需**（见 §3.5 安全基线）|
| 网络 | 网关需能访问 `restapi.amap.com` |

### 3.2 第二步：申请高德 Web 服务 Key

1. 注册 / 登录 <https://lbs.amap.com/>，完成**个人开发者认证**
   （认证类型区别见 <https://lbs.amap.com/faq/account/certification/39670>）。
2. 控制台 → **应用管理** → 创建应用 → **添加 Key**。
3. **服务平台必须选「Web 服务」**（服务端调用用；不要选 Web 端/JS API）。
4. ⚠️ 一个 Key 只用于一个应用（协议 §4.5）。

> **待核实**：免费配额的具体数值与 QPS 限制会调整，请以
> <https://lbs.amap.com/upgrade#price> 当时的说明为准。
> **本文不写死配额数字**，避免过期误导。

### 3.3 第三步：部署网关

**网关职责**：接收 App 请求 → 附加 Key → 调高德 → 转换坐标 → 返回精简 RouteBundle。

需要实现的最小接口：

| 接口 | 作用 |
|------|------|
| `POST /route` | 起终点 → 路线（含 steps：动作/距离/道路名）|
| `POST /convert` | WGS84 → GCJ-02 坐标转换（或本地算法，见 §3.6）|
| `POST /traffic` | （可选）路况刷新 |

**环境变量（Key 绝不入库、绝不进 App）**：

```bash
AMAP_KEY=你的Web服务Key          # 只存在于服务端环境变量
PORT=8080
ALLOWED_ORIGIN=                 # 空表示不启用 CORS（见 §3.5）
RATE_LIMIT_PER_MIN=60           # 按自用规模设置
```

> **高德接口的确切 URL / 参数名 / 返回字段**请以官方文档为准：
> <https://lbs.amap.com/api/webservice/guide/api/direction>
> （路径规划）、<https://lbs.amap.com/api/webservice/guide/api/georegeo>（地理编码）。
> 本文**不复制**其字段表，避免与上游不同步。

### 3.4 第四步：App 侧接入

- App 只请求**自己的网关**，不直连高德。
- 复用现有 BLE 通路下发导航消息（协议见 [ble.md](ble.md)），
  `{"t":"nav","state":…,"maneuver":…,"dist_m":…}`。
- 路名当前**不显示**（决策见 [ble.md](ble.md)）→ 暂不需要中文字模。

### 3.5 安全基线

| # | 要求 | 原因 |
|---|------|------|
| 1 | **Key 只放服务端** | 客户端可被反编译；Key 泄露会导致配额被盗用（协议 §4.5 要求妥善保管）|
| 2 | **CORS 不是认证** | 若网关公网可达，必须加访问控制（token / IP 白名单 / mTLS）|
| 3 | **必须 TLS** | 否则 Key 与位置数据明文传输 |
| 4 | **限流** | 防止误用刷爆配额（协议 §3.7 超限会被拒绝或计费）|
| 5 | **不记录完整轨迹日志** | 位置属个人信息，遵循最小化原则 |
| 6 | **依赖定期更新** | Node/上游库漏洞 |

> 参考项目在此处的自述："网关当前只有基础输入校验、限流和 CORS；
> **CORS 不是认证**。公开部署前必须自行配置访问控制、TLS、上游配额限制与监控，
> 不要无保护公开高德代理。" 本项目沿用同样的告警。

### 3.6 坐标系：WGS84 ↔ GCJ-02

| 数据源 | 坐标系 |
|--------|--------|
| iOS CoreLocation | **WGS84** |
| 高德 | **GCJ-02**（火星坐标）|

**必须转换**，否则会有数十~数百米偏移。两种做法：

| 做法 | 优点 | 注意 |
|------|------|------|
| 用高德的**坐标转换接口** | 合规、准确 | 消耗配额；见官方文档 |
| 本地实现转换算法 | 不耗配额、离线可用 | 属公开算法；**但要注意协议 §3.5 关于数据缓存/存储的限制** |

⚠️ **协议 §3.5 提示**：不得直接存储、缓存或抓取高德服务内容。
**路线几何的缓存策略需评估** —— 本项目倾向**只在内存中保存当前路线**，
不落盘、不做离线包。

## 四、维护

### 4.1 日常监控

| 项 | 做法 |
|----|------|
| 配额用量 | 高德控制台查看；接近上限时告警 |
| 网关可用性 | 健康检查端点 + 外部探活 |
| 错误率 | 记录高德返回码（如 `INVALID_USER_KEY`、超限） |
| 延迟 | 记录网关→高德往返耗时（影响重新规划体感）|

### 4.2 Key 轮换

1. 控制台新建 Key（新 Key 与新应用绑定，注意协议 §4.5 一个 Key 一个应用）。
2. 网关环境变量切换 → 滚动重启。
3. 观察无错误后，停用旧 Key。
4. **不要**在代码、日志、Git 历史里出现 Key。

### 4.3 上游变更跟进

| 关注对象 | 渠道 |
|---------|------|
| 高德 Web 服务 API | <https://lbs.amap.com/api/webservice/summary> |
| 高德服务协议变更 | <https://developer.amap.com/pages/terms/>（协议 §1.5 说明会修订并通知）|
| 配额/定价调整 | <https://lbs.amap.com/upgrade#price> |

> **建议**：每季度复核一次协议正文，尤其 **§3.4（车载场景）** 是否变化。

### 4.4 故障排查

| 现象 | 先查 |
|------|------|
| `INVALID_USER_KEY` | Key 是否正确 / 是否选了「Web 服务」平台 |
| 返回超限 | 配额或 QPS（协议 §3.7）|
| 位置偏移几百米 | 坐标系没转（§3.6）|
| 导航不更新 | 手机侧状态机是否在跑（网关只管取路线）|
| 仪表显示过期 | BLE 链路 / `NAV_STALE_MS`（见 [ble.md](ble.md)）|
