## 0. 五分钟版

| 项 | 结论 |
|----|------|
| **通道** | **BLE 直传**（独立 WRITE_NR 特征 + 分片 + 窗口流控）。iOS 侧**零新权限**；设备侧无需 Wi-Fi。 |
| **为什么现在可行** | 历史"BLE 只能 1 KB/s"是**误判**（那是 withResponse 发一条等一条的往返口径，实测 3.6 KB/s）。bulk 现实吞吐 **25–35 KB/s**（保守 15–20），依据三份独立实测 + 理论核算。 |
| **传什么** | 静态照片改传 **JPEG**（466×466 q80，**约 40–60 KB**），设备端用 **ESP32-S3 ROM 自带 TJpgDec**（`esp_jpeg` 已预编译，Flash 代价 ≈0~2 KB）解码一次到 PSRAM → 全彩。**体积 ÷4~7 ⇒ 传输时间 ÷4~7**。 |
| **体验** | 单张静态照片 **1~3 秒**传完（30–60 KB @ 25–35 KB/s）；对比"传旧 213 KB 索引图"要 6~9 秒。 |
| **性能分档** | **LITE**（默认，当前板）：只支持静态照片。**FULL**：静态 + 动图，仅在「设备实测动图 fps ≥ 8」且「App 实测上传 ≥ 30 KB/s」时自动开放；否则 App 隐藏动图入口。**当前板大概率落在 LITE —— 与你说"性能不够就砍 GIF/视频"一致。** |
| **存储** | v1：仍写 SD 卡（照片不占 Flash、容量 5.7 GB、写入 0.16 MB/s 够用）。**可选 P6**：启用那 9.8 MB 闲置内置 FAT 分区，做成"完全不用 SD 卡"模式。 |
| **必须先验** | S0 运行时内部堆（当前固件开机开 AP，可能只剩 22~24 KB）→ S1 BLE 吞吐探针（**≥20 KB/s 且 512 KB 0 缺口**）→ S3 JPEG 端到端（**解码 ≤300 ms**）。三步都是半天级。 |
| **最大风险** | S1 不达标。退路：① 先传旧 `.pgi`（慢但能跑，7~9 s）；② 再谈 Wi-Fi（需先把 LVGL 48 KB + 废弃绘制缓冲 42 KB 搬 PSRAM，是另一场手术）。 |

> ⚠️ **实现结果与设计差异（2026-10-27 真机）**：iOS 17 上 `WRITE_NR` 的
> `canSendWriteWithoutResponse`/`peripheralIsReady` 不可靠，最终改为**逐片 `WRITE`（带确认）**，
> 实测 **≈2.6 KB/s**（70 KB ≈ 30 s）。下表“1~3 秒”是设计期基于 WRITE_NR 的目标预算，
> 不是最终实测；实际数据、问题与取舍见 [`photo-implementation.md`](photo-implementation.md)。

## 1. 为什么重做：把"不满意"拆成可修的三件事

### 1.1 现状：照片能显示，但"加照片"是一条断掉的链

| # | 环节 | 现状 | 判定 |
|---|------|------|------|
| 1 | App 选图 → 裁切 | ✅ 可用（`Photo/PhotoTabView.swift`，圆屏手势、捏合/拖动/旋转） | 保留 |
| 2 | App 产出设备格式 | ⚠️ `PgiEncoder` 完整实现但**零调用点**（唯一调用在死代码 `upload()` 里）→ 手机端**实际产不出** `.pgi` | 重做 |
| 3 | 手机 → 设备 | ❌ **不存在任何文件通道**。Wi-Fi 上传已放弃（内部堆 2~4 KB），BLE 只有小 JSON | 重做 |
| 4 | 手工补救 | 用户把 GIF 存相册 → 传到电脑 → `tools/import_photos.sh` → 拔卡拷 `/photos/` → 插回 | 要消灭 |

**结论**：不是"照片功能不好用"，是**加照片的入口根本不存在**。当前 App 里那句
「① 卡插电脑 ② 用 tools/import_photos.sh 批量转换 ③ 放进 /photos/ ④ 插回仪表」就是痛点本体。

### 1.2 现有设计的 4 个结构性缺陷

| # | 缺陷 | 证据 | 本方案的修法 |
|---|------|------|-------------|
| 1 | **传输通道缺失**，且历史上被"1 KB/s"这个错误数字否掉 | `docs/photo-gif-design.md:97-110`；纠错见 `research-transport.md §1.3` | 新增 BLE bulk 特征（WRITE_NR + 分片 + 流控） |
| 2 | **格式太重**：静态图用 8bpp 索引 = 213 KB/张、256 色 | `pgi.h`、`docs/photo-gif-design.md §3.2` | 新增 `.pgj`（32 B 头 + JPEG），全彩、约 40–60 KB |
| 3 | **没有性能分档**：动图在弱设备上是 3~4 fps 的残废功能，却和静态图绑在同一套 UI 里 | `PROGRESS.md §六` | 设备上报能力 + 自检，App 按档位渲染；LITE 自动隐藏动图 |
| 4 | **App 与设备状态脱节**：设备不上报照片清单/播放设置真值；照片页不读连接态，命令静默失败 | `research-ios.md §1.3、§5.1` | 新增 `PhotoState`（Read+Notify），照片页重写为"设备状态驱动" |

### 1.3 顺手要还的债（不修就会让新功能跑不动）

| 债 | 事实 | 影响 | 处理 |
|----|------|------|------|
| **开机就开 Wi-Fi AP** | `firmware/dashboard/dashboard.ino:3368` 无条件 `wifi_start_ap()`；App 侧已无任何入口 | 内部堆从 ~104 KB 掉到 **22~24 KB**（postmortem 实测）；且 2.4 GHz 与 BLE 争射频 | **删掉**（一次性还回 ≈80 KB，Flash 也省 8~12 KB） |
| 内部 1/10 屏 fallback 绘制缓冲 | 42.4 KB 静态数组，PSRAM 全帧缓冲成功后已是死代码（`dashboard.ino:1487`） | 白占内部 RAM | 改小/按需（仅当不走 Wi-Fi 时可选） |
| LVGL 堆 48 KB 在内部 RAM | `lv_conf.h` 静态数组 | 白占内部 RAM | **本次不动**（搬 PSRAM 有 cache 关闭风险）；若将来救 Wi-Fi 再说 |
| `/photos/` 无排序 | 文档写"文件名排序"，代码按 FAT 目录顺序（`dashboard.ino:432-466`） | 轮播顺序不可预期 | 补 `qsort`（按名字） |
| 文档口径过时 | Bluedroid、Flash 余量 580 KB（实为 ~678 KB）、"JPEG 需 vendor 库"等 6 处 | 误导实现 | 见 §16 修订清单 |

## 2. 设计目标（可验收）

| # | 目标 | 验收标准 |
|---|------|---------|
| G1 | **不用拔卡** | 手机 App 里选图 → 3 分钟内出现在设备上（单张静态 ≤10 s 为硬指标，目标 ≤3 s） |
| G2 | **画质不倒退** | 静态照片全彩 466×466（JPEG q80），不再是 256 色索引 |
| G3 | **弱设备可用** | LITE 档（仅静态）在**当前板**上稳定工作；动图不可用时 App 明确说明原因，而不是给一个 3 fps 的残废功能 |
| G4 | **失败可恢复** | 断连/切后台/断电后能续传；绝不留下"半张图"被当成正常照片播放 |
| G5 | **状态一致** | 设备照片清单、当前播放张、播放设置都以设备为准，App 只读+改，不本地猜测 |
| G6 | **不伤现有功能** | 遥测 2 Hz、导航地图、滑页/触摸、烧屏防护全部不受影响；上传期间 UI 可交互 |

**非目标（本次不做）**：云端相册、多设备同步、照片编辑（滤镜/文字）、视频直接在设备播放、设备端解码视频/GIF 原始格式、Wi-Fi 上传。

## 3. 硬约束（每个数字都有出处）

### 3.1 内存：内部 RAM 是唯一的真墙

| 项 | 数值 | 出处 |
|----|------|------|
| 内部堆 · 不开 Wi-Fi | **约 104 KB** | `docs/wifi-upload-postmortem.md:87` |
| 内部堆 · 开 AP（无客户端） | **22~24 KB** | 同上 `:88` |
| 内部堆 · 手机连上 AP | **2~4 KB** | 同上 `:89` |
| 当前固件实际状态 | **开机即开 AP** → 真实起点待测（**S0**） | `firmware/dashboard/dashboard.ino:3368` |
| 应用侧可搬走的两块 | LVGL 堆 **48 KB** + 废弃绘制缓冲 **42.4 KB** | `research-transport.md §3.3` |
| BLE 栈常驻 | NimBLE host 栈 5,120 B + MSYS 10.7 KB + ACL 24×255；缓存**只能内部 RAM** | `research-firmware.md §1.5` |
| PSRAM 空闲 | 约 **6.4~6.5 MB** | `docs/wifi-upload-postmortem.md:91` |
| PSRAM 现有大户 | 烘焙图 ~1.4 MB + LVGL 全帧 434 KB + 照片三块缓冲 1.04 MB | `research-firmware.md §2.2` |

> **设计含义**：新增接收缓冲/解码输出**必须放 PSRAM**；内部 RAM 只新增
> 「BLE 回调落地缓冲 ≈512 B + NimBLE ACL 缓冲增量（可选 +6 KB）」量级。
> **前置动作：删 Wi-Fi AP（§9.6）**，否则 22~24 KB 的起点上什么都加不了。

### 3.2 显示与解码

| 环节 | 耗时 | 出处 |
|------|------|------|
| 8bpp 索引解码 466² | 21~23 ms | `PROGRESS.md §六` |
| **JPEG 解码 466²（ROM TJpgDec）** | **约 200~260 ms**（官方 320×180 = 52 ms 线性外推，**待 S3 实测**） | `research-firmware.md §6.3` |
| 全屏 flush | 43 ms | `PROGRESS.md §六` |
| 现有动图实测 | **3~4 fps**（瓶颈是 SD 读 104 ms/帧） | 同上 |

> **设计含义**：JPEG 解码只适合**静态照片**（每 30 s 一次无感）。
> 动图仍用 `.pgi` 索引帧（解码 21 ms），且**不承诺比现在更快** → 正好支持"弱设备砍动图"。

### 3.3 SD 卡（1-bit SDMMC）

| 项 | 数值 | 出处 |
|----|------|------|
| 读 | **2.37 MB/s**（物理上限） | `docs/photo-gif-design.md §10.5` |
| 写 | **0.16 MB/s** | 同上 |
| 写一张 50 KB JPEG | ≈ **0.31 s**（必须摊到多拍） | 计算 |
| 写一张 213 KB `.pgi` | ≈ 1.36 s（整段同步写会让 `loop()` 冻结） | `research-firmware.md §4.2` |

> **设计含义**：接收写盘必须**分片**（每拍 ≤4 KB ≈ 25 ms），且上传期间**暂停照片读帧**（同一张卡不能一边读一边写）。

### 3.4 BLE（实测 + 理论）

| 项 | 数值 | 出处 |
|----|------|------|
| 栈 | **NimBLE**（不是 Bluedroid） | `research-firmware.md §1.1` |
| iOS ATT MTU 上限 | **185**（有效载荷 **182**），请求 247 会被截断，**无 API 可破** | `research-transport.md §2.1` |
| 现有 4 个特征 | 全是**带响应写**；无 WRITE_NR、无连接参数、无 PHY 配置 | `research-firmware.md §1.2-1.3` |
| 现有实测 | ≈3.6 KB/s（地图窗口"发一条等一条"，**往返受限**，不是空口能力） | `research-transport.md §1.3` |
| bulk 预期 | **保守 15–20 / 现实 25–35 / 乐观 40–50 KB/s** | `research-transport.md §2.4` |
| 并发流量 | 遥测 2 Hz ≈0.4 KB/s（占 1~2%），不是带宽问题，是**回调/主循环争用** | `research-transport.md §2.8` |
| 线程约束 | BLE host 在 **core 0**，`loop()` 在 **core 1**；回调里**禁止**阻塞 IO（CPU0 idle 有 5 s 任务看门狗） | `research-firmware.md §1.6` |

### 3.5 Flash / 分区

| 项 | 数值 | 出处 |
|----|------|------|
| `app0/app1` | 各 3 MiB | `partitions.csv` |
| 当前占用 | **77%（约 2.45 MB）**，余量 **≈678 KiB** | `docs/ai-bootstrap.md:154` |
| `ffat` 分区 | **9.875 MB，当前完全未使用** | `partitions.csv` |
| 新增 JPEG 解码 | **≈0~2 KB**（ROM 里已有 TJpgDec，`esp_jpeg` 1.3.1 已预编译） | `research-firmware.md §6.1-6.2` |

### 3.6 烧屏（不能因为加功能而丢）

现有三开关（轮播 / 自动息屏 / 像素位移）+ 亮度封顶 180 **全部保留**；
上传期间画面冻结时，**强制开启像素位移**（复用"不轮播时强制位移"的既有规则）。

### 4.2 关键决策（与旧文档的差异）

| 决策 | 旧（v4/现状） | **新（v5）** | 理由 |
|------|--------------|-------------|------|
| 加照片通道 | SD 卡（Wi-Fi 已放弃） | **BLE 直传** | 用户明确要"App 发送"；BLE 无需切网/权限，设备侧零 Wi-Fi 栈 |
| 静态格式 | 8bpp 索引 `.pgi` 213 KB | **`.pgj` = 32 B 头 + JPEG（≈40–60 KB）** | 体积 ÷4~7，传输时间 ÷4~7；全彩 |
| 动图格式 | `.pgi` 索引帧 | **保持 `.pgi`**（不无线传 / FULL 档才传） | JPEG 解码 200~260 ms，动图不会更快；索引帧解码仅 21 ms |
| 能力分档 | 无 | **LITE / FULL + 设备上报 + 自检** | 你要的"性能低就只留照片" |
| 存储 | SD | **SD（v1）**；内置 9.8 MB FFat 作为 P6 可选 | 风险最小；FFat 可做"无卡模式" |
| 播放设置 | App 本地乐观值 | **设备上报真值（PhotoState）** | 修掉"App 与设备漂移" |
| Wi-Fi | 代码还在、开机即开 | **删掉** | 80 KB 内部 RAM + 射频共存 + 死代码 |

## 5. 传输通道：BLE 主选

### 5.1 先把历史误判纠正掉

`docs/photo-gif-design.md:99` 写"BLE 实测有效吞吐约 1 KB/s"，据此判定"BLE 不能传图"。复核代码：

- App 用 `.withResponse` **发一条等一条**（`BLEClient.swift:879`、`:734-754`）；
- 50 条 × 180 B = 9,000 B，耗时 2~3 s → **3.6 KB/s**（不是 1 KB/s），本质是**往返次数**的度量；
- 与空口能力无关。三份独立实测：iPhone SE 12.2 KB/s（1M PHY 无 DLE）、
  **iPhone→ESP32 GATT 32 KB/s**、新机型经验上限 ~50 KB/s（见 `research-transport.md §2.4`）。

**结论**：旧数字**低估 3~4 倍**（3.6 KB/s vs 1 KB/s），而且它度量的是**往返次数**、不是空口能力；
用它否定 BLE 传图是错误推论。这不代表必然能跑 30 KB/s —— 必须按 §13 做 S1 探针，
但**预期区间已经足以支撑"静态照片 1~3 秒"**。

### 5.2 吞吐预算与目标

| 场景 | 体积 | @15 KB/s | @25 KB/s | @35 KB/s | 判定 |
|------|------|---------|---------|---------|------|
| 静态 `.pgj`（本方案） | 40–60 KB | 2.7–4.0 s | 1.6–2.4 s | 1.1–1.7 s | ✅ 达标（目标 ≤10 s） |
| 静态旧 `.pgi`（退路 B1） | 213 KB | 14 s | 8.5 s | 6.1 s | ⚠️ 可接受但慢 |
| 动图 `.pgi` 300² × 12 帧 | ≈1.09 MB | 73 s | 44 s | 31 s | ❌ 不无线（除非实测 ≥30 KB/s 且用户接受 ~45 s） |

**硬指标**：LITE 档要求 **sustained ≥ 12 KB/s**（单张 60 KB ≤ 5 s）；
FULL 档动图要求 **sustained ≥ 30 KB/s**。
S1 探针的通过线定在 **≥20 KB/s**，比 LITE 的下限（12 KB/s）留约 40% 余量 ——
因为实测速率会随环境抖动，卡在 12 KB/s 边缘的方案不算通过。

### 5.3 为什么不用其它通道（一句话各一条）

| 通道 | 判定 | 原因 |
|------|------|------|
| Wi-Fi AP + HTTP | ❌ 暂不做 | 内部堆 2~4 KB 的根因未修；且需 iOS 热点三连坑（`wifi-upload-postmortem.md`）。**仅当 S1 失败时作为退路**（先做内存手术） |
| Wi-Fi AP + UDP/TFTP | ⚠️ 备选 | 比 HTTP 省 ≈12.7 KB（TCP 窗口 + 解析），实现更简单；但仍需内存手术与热点坑 |
| BLE L2CAP CoC | ❌ 不做 | iPhone↔iPhone CoC 实测 28 KB/s，**不快于 GATT**；ESP32 需重建库（`COC_MAX_NUM=0`） |
| 提高 MTU | ❌ 不可能 | iOS 上限 185，无 API |
| USB MSC / CDC | ❌ 不做 | MSC 需在 Files 里手动拖（App 无法自动化）；CDC 需 MFi |
| 云端中转 | ❌ 不做 | 把本地 0.1 s 的事变成联网 + 服务器成本 |

### 5.4 让 BLE 跑满的 6 条工程要求

1. **独立服务/特征**，不复用 Telemetry（JSON 重组语义会打架）；
2. 数据特征用 **WRITE_NR（writeWithoutResponse）**，App 侧必须检查
   `canSendWriteWithoutResponse` 并实现 `peripheralIsReady(toSendWriteWithoutResponse:)`，否则 CoreBluetooth 队列满会**静默丢包**；
3. 应用层 **offset + credit 窗口**（设备按"已落盘字节数"发 credit），不是每包 ACK；
4. 连接建立后由设备 `updateConnParams(15 ms)`；**2M PHY 作为优化项**（NimBLE `ble_gap_set_prefered_default_le_phy`，收益有限，先不做也行）；
5. 上传期间**关掉 Status/Faces 的 notify 洪泛**（现有代码已有"未连接跳过"的先例，加一个"上传中跳过"即可）；
6. 回调只做 memcpy 进 PSRAM 环形缓冲；写盘在主循环，**绝不在回调里写 SD**。

## 6. 数据格式

### 6.1 为什么静态照片改传 JPEG

| 方案 | 单帧体积 | 传输 @25 KB/s | 画质 | 解码 | 结论 |
|------|---------|--------------|------|------|------|
| 8bpp 索引 `.pgi`（现状） | 213 KB | 8.5 s | 256 色 | 21 ms | 太慢 |
| RGB565 直通（434 KB） | 434 KB | 17 s | 全彩 | 0 ms | 太慢 |
| **JPEG + ROM TJpgDec** | **40–60 KB** | **1.6–2.4 s** | **全彩** | **200–260 ms** | ✅ **选它** |

关键前提已核实：ROM 里就有 `jd_prepare/jd_decomp`，`esp_jpeg 1.3.1` 的
`.a` 已在 Arduino 核心的默认链接列表里，`#include "jpeg_decoder.h"` 即可用，
**Flash 增量 ≈0~2 KB、零安装**（`research-firmware.md §6.1-6.2`）。
JPEG 只支持 **baseline**（progressive 会被库拒绝）—— App 侧编码时必须用 baseline。

### 6.2 `.pgj` 容器（32 B 头 + 1 张 JPEG）

```
偏移  长度  字段
  0     4   magic "PGJ1"
  4     2   width  u16            （1..466）
  6     2   height u16            （1..466）
  8     1   version = 1
  9     1   flags                  bit0=1 表示 baseline JPEG（必须为 1）
 10     2   quality u16            （10..100，仅记录，设备不解析）
 12     4   jpeg_bytes u32         （必须 == 文件大小 - 32）
 16     4   crc32 u32              （仅 JPEG 载荷的 CRC32）
 20     4   created_unix u32       （0 = 未知，仅记录）
 24     8   reserved               （全 0）
```

- **一张 `.pgj` 只放一帧**（静态照片）；动图继续用 `.pgi`。
- 设备扫描时只读 32 B 头即可建清单（不用解码），并**拒收** `flags.bit0=0`、
  `w/h > 466`、`jpeg_bytes` 不自洽的文件 → 从源头消灭"历史坏文件 `LOAD ERROR`"。
- 提交时设备再校验：`crc32(载荷) == 头`、`esp_jpeg_get_image_info()` 的 SOF 尺寸 == 头尺寸。

### 6.3 新旧格式共存

| 文件 | 谁来写 | 设备行为 |
|------|--------|---------|
| `*.pgj`（新） | App BLE 上传 | JPEG 解码显示 |
| `*.pgi`（旧，1 帧） | 历史 SD 导入 / `import_photos.sh` | 索引解码显示（**只读兼容，不再新增**） |
| `*.pgi`（多帧） | 历史 SD 导入 / FULL 档 App | 索引逐帧播放 |

文件名统一 `p%05d.pgj`（设备分配序号，NVS 持久化），排序 = 文件名升序（**补上现在缺失的排序**）。
单文件上限：`.pgj` **512 KB**（正常 40–60 KB，留余量）、`.pgi` 沿用 8 MB（FULL 档）。

### 6.4 体积估算（App 侧编码参数，待真机标定）

| 内容 | 参数 | 预估体积 |
|------|------|---------|
| 静态照片（默认） | 466×466，JPEG q80 | **40–60 KB** |
| 静态照片（高清） | 466×466，q90 | 60–90 KB |
| 动图（FULL 档） | 300×300，8 fps，≤12 帧，`.pgi` | ≈1.09 MB（**仅当实测 ≥30 KB/s 才开放**） |

> 体积必须实测标定（不同照片差异大）。App 显示"预估体积/传输时间"，超阈值时提示降参数。

## 7. 能力分档：性能不够就只留照片

### 7.1 两档模型

| 档位 | 能力 | 判定规则 | 对应硬件 |
|------|------|---------|---------|
| **LITE**（默认） | 静态照片：BLE 加图 / 删图 / 播放设置 / 清单；**无动图入口** | 始终可用；不需要任何自检 | 当前板（以及未来的更弱板） |
| **FULL** | LITE + 动图（`.pgi`，300²/8 fps/≤12 帧）；可选择上传动图 | **同时满足**：① 设备能力位 `cap.bit1=1`；② 设备上报"上次实测动图 fps ≥ 8"；③ App 实测上传 ≥ 30 KB/s；④ 预估传输 ≤ 90 s | 更强板 / 未来换 Wi-Fi 后 |
| **PHOTO_ONLY 构建**（可选） | 只留照片 + 时钟表盘，去掉导航/地图/遥测 | 编译期宏 | 若真要做更便宜的板子（见 §7.4） |

**关键点**：档位是**运行时协商**出来的，不是写死的。设备上报能力，App 决定 UI；两者都不猜。
设备**不会**因为 App 是旧版就拒绝静态上传（向后兼容）。

**三层门控（别把它们混成一层）**：

| 层 | 谁判断 | 判断什么 |
|----|--------|---------|
| ① 固件能力位 | 设备 | `cap.bit1`：这版固件到底**实现了**动图播放吗 |
| ② 本机推荐档 | 设备 | `tier`：**这台设备**上次实测动图 fps（`fps_meas`）够不够 8 → 不够就把自己降成 LITE |
| ③ 本次连接可用性 | App | 本次实测上传速率 ≥30 KB/s 且预估 ≤90 s |

**App 渲染动图入口的条件 = ① && ② && ③**；任何一层不满足都要**显示具体原因**（§10.5）。
这也解释了 §7.2 的示例：固件支持动图（`cap.bit1=1`），但这台机器实测只有 4 fps
（`fps_meas=4`）→ 自己报 `tier=1` → App 只给静态入口。

### 7.2 能力上报（`PhotoInfo`，READ，≤180 B）

```json
{"t":"pi","v":1,"tier":1,"cap":7,"px":466,"max_kb":512,
 "anim":{"px":300,"fps":8,"frames":12,"max_kb":2048,"fps_meas":4},
 "bench":{"dec_ms":230}}
```

| 字段 | 含义 |
|------|------|
| `tier` | 1=LITE，2=FULL（设备自己的结论；App 仍可用实测速率进一步降级） |
| `cap` | bit0 静态 JPEG，bit1 动图，bit2 删除，bit3 内置存储（FFat） |
| `px` / `max_kb` | 静态照片边长上限 / 单文件上限 |
| `anim.fps_meas` | **上一次动图实测帧率**（固件已有帧率统计 `s_photo_frames`，写入 NVS）→ 这是"性能过低"的**证据** |
| `bench.dec_ms` | 最近一次 JPEG 解码耗时（S3 之后有值） |

> 为什么不用一次 Notify：Notify 受 184 B 截断；**Read 是取数据的正途**（沿用 `Faces` 的既有教训，
> `docs/ble.md:405-416`）。App 在连接后 Read 一次，收到 `PhotoEvt` 的 `changed` 后再 Read。

### 7.3 状态上报（`PhotoState`，READ + NOTIFY，≤180 B）

```json
{"t":"ps","cur":3,"n":12,"stor":1,"free_kb":5230,
 "slide":1,"intv":30,"shift":1,"soff_s":1800,"rx":0}
```

`rx`：0=空闲，1=正在接收（App 据此判断设备侧状态）。`stor`：0=未就绪，1=SD，2=内置 FFat。
播放设置从此**以设备为准**（修掉 App 本地乐观值漂移）。

### 7.4 如果将来做更弱的硬件：裁剪顺序（回答"只保留照片模块"）

| 档 | 保留 | 砍掉 | 省下 | 代价 |
|----|------|------|------|------|
| ① 当前 | 全部 6 表盘 + 导航 + 静态/动图照片 | — | — | — |
| ② 照片优先 | 照片（静态）+ 时钟表盘 | 动图、导航/地图 | Flash ~20–30 KB、内部 RAM 数 KB、PSRAM ~1 MB | 不能导航 |
| ③ 极简 | 照片（静态）+ 时钟 | 遥测/导航/其它表盘 | 更多 | 只能当电子相框 |
| ④ 无 PSRAM 的更弱板 | 照片（小尺寸，如 240×240）+ 时钟 | 466 全彩、动图、BLE 大缓冲 | — | **必须降分辨率**：466² RGB565 = 424 KB，没 PSRAM 放不下；LITE 接口不变，只是 `px` 从 466 降到 240 |

> ④ 是这套设计的"下限验证"：**协议与 App 都不变**，只改设备上报的 `px`/能力位。
> 也就是说，**"性能过低就只保留照片"不是一句口号，而是协议里的一等公民**。

## 8. BLE 照片服务协议

### 8.1 GATT

| 项 | 值 |
|----|----|
| Service | `7D2A0010-8F4A-4B7C-9D21-5E6A3B8C1000`（`Photo`） |
| `PhotoCtl` | `7D2A0011-…` **WRITE**（带响应，命令都短）；JSON ≤180 B |
| `PhotoData` | `7D2A0012-…` **WRITE_NR**（无响应）；二进制分片 |
| `PhotoEvt` | `7D2A0013-…` **NOTIFY**；JSON ≤180 B（窗口/结果/清单分页） |
| `PhotoInfo` | `7D2A0014-…` **READ**；能力/档位（§7.2） |
| `PhotoState` | `7D2A0015-…` **READ + NOTIFY**；状态/设置（§7.3） |

> UUID 分配与该服务的存在本身就是"能力探测"：**没有 `7D2A0010` 服务 = 旧固件**，
> App 退回"SD 卡导入"文案（优雅降级，不报错）。

### 8.2 命令与事件

**App → 设备（`PhotoCtl`，JSON）**

| 命令 | 语义 |
|------|------|
| `{"t":"p","op":"begin","kind":0,"bytes":45210,"crc":282593821,"w":466,"h":466,"frames":1}` | 开始上传；`kind` 0=PGJ 静态，1=PGI 动图；设备分配 id、建 `.part` + `.meta` |
| `{"t":"p","op":"end"}` | 传输完毕 → 校验 + 原子提交 |
| `{"t":"p","op":"abort"}` | 放弃本次（删除 `.part`） |
| `{"t":"p","op":"del","id":"p00012.pgj"}` | 删除（只允许 `/photos/` 内、白名单扩展名） |
| `{"t":"p","op":"play","i":3}` | 切到第 3 张（复用现有 `photo_play` 语义） |
| `{"t":"p","op":"set","slide":1,"intv":30,"shift":1,"soff_s":1800}` | 任一字段可单独下发（写 NVS） |
| `{"t":"p","op":"list"}` | 触发清单分页推送（`PhotoEvt`） |
| `{"t":"p","op":"bench"}` | 自检（SD 读速 / JPEG 解码 / 动图 fps 复核），结果写 NVS 并回 `info` |

> 现有 `photo_next/prev/play/slide/interval/shift/screenoff` 命令**保留**（旧 App 兼容），
> 新 App 优先用 `op:"set"` 一次下发。

**设备 → App（`PhotoEvt`，JSON）**

| 事件 | 语义 |
|------|------|
| `{"t":"pe","ev":"go","off":0,"chunk":178,"win":4096}` | 开始收数据；`off`=期望起始偏移（续传时 >0） |
| `{"t":"pe","ev":"credit","off":4096}` | 已**落盘**到第 4096 字节，App 可继续发 |
| `{"t":"pe","ev":"done","id":"p00012.pgj"}` | 提交成功 |
| `{"t":"pe","ev":"err","code":"crc"}` | 失败（codes 见 §8.5） |
| `{"t":"pe","ev":"changed"}` | 清单变了（上传/删除/外部插卡）→ App 重读 `PhotoInfo`/清单 |
| `{"t":"pe","ev":"info"}` | 能力/自检结果已更新 → App 重读 `PhotoInfo` |
| `{"t":"pq","n":12}` → `{"t":"pf","i":0,"id":"p00012.pgj","b":45210,"f":1,"k":0}` × N → `{"t":"pz"}` | 清单分页（每页 1 条；12 张 ≈0.2 s） |

**数据分片（`PhotoData`，二进制）**

```
[u32 offset LE][payload ...]
```

- `payload` 长度 = `min(设备建议 chunk, iOS 协商写长 - 4)`；iOS 侧用
  `maximumWriteValueLength(for:.withoutResponse)` 取当前写长（通常 178），设备建议值仅作参考；
- 设备校验 `offset == 期望值`：不等 → 回 `err{code:"offset","want":N}`，App 从 `N` 续发；
- 无逐包 ACK：BLE 链路层本身重传；**文件级 CRC32** 兜底。

### 8.3 上传时序（含流控）

```
App                                        设备
 │ READ PhotoInfo / PhotoState               │   ← 连接后一次
 │ WRITE ctl {"op":"begin",bytes,crc,...}    │
 │ ────────────────────────────────────────▶ │  分配 id、建 .part/.meta
 │ ◀──────────── NOTIFY {"ev":"go","off":0,"chunk":178,"win":4096}
 │ WRITE_NR PhotoData [0][178B]              │
 │ WRITE_NR PhotoData [178][178B]            │   ← 连续发，in-flight ≤ win
 │ …                                         │  loop：每拍从 PSRAM 环形缓冲写 ≤4KB 到 .part
 │ ◀──────────── NOTIFY {"ev":"credit","off":4096}
 │ …（发到 bytes 为止）                        │
 │ WRITE ctl {"op":"end"}                    │  读回 .part 算 CRC32 + 校验 32B 头
 │                                           │  rename .part → p00012.pgj，更新清单
 │ ◀──────────── NOTIFY {"ev":"done","id":"p00012.pgj"}
 │ ◀──────────── NOTIFY {"ev":"changed"}
 │ READ PhotoState / 清单                     │
```

**流控规则**（App 侧）

1. `inFlight = sentOffset - ackedOffset`；`inFlight + chunk > win` 时**等 credit**；
2. 每次写前检查 `canSendWriteWithoutResponse`；false 时等 `peripheralIsReady` 回调再继续；
3. credit 每 100 ms 或每收 1 KB 检查一次，**不要每个 chunk 都 notify**（省空口）；
4. 看门狗：6 s 无 credit → 重发 `{"op":"begin"}`（设备回 `off`=已落盘位置）→ 从该处续传；
5. 取消：发 `abort`；断连则设备保留 `.part`，10 s 后标记为"可续传"，App 重连后可续。

### 8.4 续传与原子落盘（G4）

| 阶段 | 设备行为 | 断电/断连后 |
|------|---------|------------|
| begin | 建 `/photos/.incoming/p00012.part` + `.meta`（bytes/crc/kind） | 重连 begin 同 bytes+crc → 回 `off = .part` 当前大小 |
| 接收 | PSRAM 环形缓冲 → 每拍写 ≤4 KB；每 16 KB `flush()`（保证 resume 偏移可信） | `.part` 大小即可信偏移；App 从 `off` 续发 |
| end | 关闭文件 → **读回全文件算 CRC32**（50 KB 仅 ~21 ms）→ 校验 32 B 头 / JPEG 尺寸 → `SD_MMC.rename()` → 清 meta | 校验失败：删 `.part` + 回 `err{crc}`；**绝不进清单** |
| 启动 | 清理 `.incoming/` 里超过 7 天的残留；**不扫描** `.part` 进清单 | 不会显示半张图 |

### 8.5 错误码（App 文案一一对应）

| code | 含义 | App 处理 |
|------|------|---------|
| `busy` | 已有上传在进行 | 提示排队/稍后 |
| `no_space` | 存储空间不足（回 `need_kb`/`free_kb`） | 提示删除或换卡 |
| `too_large` | 超过单文件上限 | 提示降分辨率/质量 |
| `unsupported` | 格式不支持（progressive JPEG、旧 flags） | 重新编码 |
| `crc` | 校验失败 | 自动整份重传一次，仍失败报错 |
| `offset` | 分片偏移不符（回 `want`） | 从 `want` 续发 |
| `io` | 写盘失败 | 提示检查 SD 卡 |
| `not_ready` | 存储未挂载/未就绪 | 提示插卡 |
| `bad_arg` | 参数非法 | 隐藏为内部错误 |

### 8.6 与现有通道的共存规则

| 规则 | 原因 |
|------|------|
| 上传期间**暂停照片读帧/轮播**（画面冻结，触摸与滑页仍可用） | SD 一边读一边写会互相拖慢；也避免"上传时正在播的动图"抢 SD |
| 上传期间**跳过 Status/Faces 的周期 notify** | 省空口，避免 notify 与 bulk 写抢连接事件 |
| 遥测（2 Hz）与地图窗口**不禁用** | 流量小（~0.4 KB/s）；地图队列已有"待用窗口覆盖"语义，慢一点可接受 |
| 上传**只在 App 前台发起**；后台/锁屏不做保活承诺 | iOS 后台会挂起 App；断线可续传，已足够 |
| 上传前若设备在播放动图 → 先停 | 同上 |

### 9.2 内存与任务（内部 RAM 只新增 ≈2–6 KB）

| 用途 | 大小 | 位置 | 说明 |
|------|------|------|------|
| BLE 回调落地缓冲 | 512 B | 内部 RAM（静态） | 回调里只 memcpy，对齐现有 `s_asm[512]` 做法 |
| PSRAM 环形接收缓冲 | 32–64 KB | PSRAM | `ps_malloc`，懒分配（第一次上传时） |
| 帧暂存（stage） | **512 KB**（`.pgj` 上限） | PSRAM | JPEG 必须**整幅在内存**（`esp_jpeg` 的 indata 是一次性缓冲）；`.pgi` 沿用 218 KB 即可 |
| 写盘分片 | 4 KB/拍 | 直接写 SD | 每拍 +25 ms；上传期间可接受 |
| JPEG 解码工作缓冲 | 3.1 KB | 库内部 | `esp_jpeg` 默认；可选 65 KB 换约 10% 速度（不建议） |
| 清单 | 64 项 × ~48 B | 静态/PSRAM | 复用现有 `s_photo_names`（4 KB）+ 增元数据 |
| 新任务栈 | **0（不新增任务）** | — | 写盘放主循环（最省事、已验证的分片模式） |

**为什么不开新任务**：`loop()` 的 `photo_poll()` 已经证明"每拍 32 KB 读"不会卡死 UI；
把"读"换成"写 4 KB"更轻。开新任务反而要处理 SD 互斥与 core0 看门狗。

### 9.3 接收状态机（`photo_sync`）

```
IDLE ──begin──▶ WAIT_DATA ──首包──▶ RECEIVING ──end──▶ COMMITTING ──ok──▶ IDLE
                     │                  │                    └──fail──▶ ERROR → IDLE
                     └──10s 无数据──▶ IDLE（保留 .part 供续传）
RECEIVING ──断连/10s 无数据──▶ PAUSED（保留 .part；下次 begin 回 off）
```

- `begin` 时校验：存储就绪、空间够（`bytes + 1 MB` 余量）、`kind` 支持、`bytes ≤ 上限`；
- `PAUSED` 的 `.part` 在启动时不被扫描进清单（只清 >7 天残留）；
- 同一时刻**只允许一个上传**（`busy`）。

### 9.4 显示：JPEG 接入现有照片链路

```
photo_poll()（改）
 ├ 扫描：按扩展名/魔数分派 .pgj / .pgi（新增排序）
 ├ .pgj：
 │   ├ 读 32B 头（清单已有；播放时按帧需求读整文件 ≤512 KB 到 stage）
 │   ├ jpeg_decode_to_rgb565(stage, len, back_buf)   ← 阻塞 200~260 ms
 │   └ 交换双缓冲 → ui_photo_show_frame()（复用现有双缓冲 434 KB×2）
 └ .pgi：保持现有路径（索引解码 21 ms）
```

- **解码只在"切到这张图"时发生一次**（静态图不需要每帧解）→ 30 s 轮播下完全无感；
- 首次进照片表盘多花 ~250 ms（可接受；后续优化可做"空闲预解码下一张"）；
- 亮度封顶 180 / 像素位移 / 自动息屏**全部沿用**；
- 占位状态更新：
  - 无照片：`还没有照片 · 在 App 里添加`（不再是"用 App 上传"这种指向死路的文案）
  - 存储未就绪：`未检测到存储卡`（或 FFat 模式下不出现）
  - 接收中：底部小进度条 `接收 62%`（5 Hz 更新，不参与烧屏位移）

### 9.5 清单与删除

- 清单每项：`{name, kind(pgj/pgi), bytes, frames, fps, w, h}`，最多 64 项（可提到 128，见 §15-Q5）；
- `del`：只允许 `/photos/` 内、扩展名白名单、名字长度 ≤63；删除后若删的是当前张 → 自动切下一张；
- 排序：按文件名升序（补上现在缺失的 `qsort`）；
- `changed` 通知：上传完成、删除、检测到 SD 卡热插拔时推送。

   `http_*`（约 300 行）、`WiFi.h` include。
   一次性还回 **≈80 KB 内部 RAM**（`research-transport.md §3.6`），并消除 2.4 GHz 与 BLE 的射频争用。

### 10.1 照片页结构（重写，约 800 行 → 约 700 行更清晰的版本）

```
┌ 照片 ─────────────────────────────────────┐
│ ● 已连接  CarDashboard                     │

```

与现状的关键差异：
- **连接态真实可见**：未连接时"添加/切换"禁用并说明原因（现在命令静默失败）；
- **设备清单可见**：缩略图来自 App 本地缓存（上传时生成 96×96 JPEG，按 id 存沙盒）；非本机上传的照片显示占位图；
- **设置来自设备**：`PhotoState` 每 3 s 或收到 notify 后 Read 一次，不再乐观写死；
- **能力分档驱动 UI**：LITE 不渲染动图相关入口。

### 10.2 添加照片流程（多选 + 少量交互）

```
PhotosPicker（可多选 images）
  → 逐张：默认"居中方形裁切 + 466×466"
       · 可点开单张调整（复用现有捏合/拖动/旋转）
       · 视频：LITE 档 → "取一帧作静态照片"（默认中间帧，可拖时间轴）
                FULL 档 → "生成动图"（300²/8fps/≤12 帧）
  → 编码：JPEG baseline q80 → 加 32 B PGJ 头 → crc32
  → 进上传队列（串行）→ 显示每张进度 / 总进度
```

- 默认**多选 + 默认裁切**，避免"选 10 张要点 10 次裁切"；
- 编码产物先写 App 沙盒临时文件（`tmp/photo-upload/<id>.pgj`），**续传时直接从文件流式读**（不重复编码）；
- 单张超过上限（静态 > 512 KB / 动图 > 2 MB）时给明确提示（不是静默失败）。

### 10.3 上传状态机（App 侧）

```
idle → encoding → queued → uploading → verifying → done
                     │         │
                     │         ├─ 断连 → waitingReconnect（重连后 begin 续传）
                     │         ├─ 取消 → aborted
                     │         └─ 错误 → failed（可重试）
                     └─ 设备 busy/no_space → paused（提示）
```

进度 = `ackedOffset / bytes`；速率 = 最近 2 s 滑动平均；ETA = 剩余 / 速率。
**状态必须来自设备回执**（credit/done），不能靠"发送完成"自欺。

### 10.4 删除 / 播放 / 设置

- 删除：列表项左滑 → 二次确认 → `{"op":"del"}` → 收到 `changed` 后刷新；
- 播放：列表项"▶" → `{"op":"play","i":n}`（满足"选择当前播放哪张"的既有需求）；
- 设置：改动即下发 `{"op":"set"}`，并以 `PhotoState` 回读为准（失败回滚 UI）。

### 10.5 能力降级时的 UI（你要的"性能低就砍 GIF/视频"）

| 设备能力 | App 表现 |
|---------|---------|
| LITE（cap.bit1=0） | 选视频后只显示"取一帧作静态照片"；动图入口整个不渲染；顶部一行说明理由 |
| FULL 但 `anim.fps_meas < 8` | 同上（设备实测帧率不够，不给你 3 fps 的残废动图） |
| FULL 但实测上传 < 30 KB/s | 动图入口可见但**置灰**，提示"当前连接速率不足，动图需要 ≥30 KB/s" |
| 旧固件（无 Photo 服务） | 整页退回"SD 卡导入说明"，不显示任何传输入口 |

> 理由必须**可见**（"为什么不能传动图"），否则用户会以为功能坏了。

## 11. 性能预算与验收指标

### 11.1 单张静态照片（466²，q80，50 KB）

| 环节 | 预期耗时 | 备注 |
|------|---------|------|
| App 编码（选图已有，JPEG 很快） | < 300 ms | 不计入传输 |
| BLE 传输 50 KB @25 KB/s | **2.0 s** | LITE 验收线：≤10 s |
| 设备写 SD 50 KB（分片） | ≈0.31 s（摊到 13 拍） | 与传输重叠，不额外计时 |
| 设备 CRC + 头校验 + rename | ≈0.05 s | 读回 50 KB（21 ms）+ 元数据 |
| **端到端（点"上传"到"设备显示"）** | **≈2.5 s** | 目标 ≤5 s |

### 11.2 资源红线

| 指标 | 红线 |
|------|------|
| 上传期间 `loop()` 频率 | ≥100 次/秒（现状 195~199） |
| 上传期间单帧渲染峰值 | ≤300 ms（现状已知偶发 1000 ms 尖刺，**不允许恶化**） |
| 内部堆最低点 | ≥30 KB（`heap` 串口命令观测） |
| PSRAM 空闲 | ≥3 MB |
| 静态照片显示首帧 | ≤1 s |
| 动图帧率（若开 FULL） | ≥8 fps，否则自动关档 |

### 11.3 传输时间表（给 App 显示 ETA 的公式）

`ETA = bytes / max(实测速率, 8 KB/s)`；速率取最近 2 s 的滑动平均；
`预计 > 90 s` 时弹"建议缩小尺寸/降质量"。

3. "Flash 余量约 580 KB" → 按 77% × 3 MiB 应为 **≈678 KiB**；
4. "设备端解 JPEG 要 vendor 库" → **ROM 自带 TJpgDec、`esp_jpeg` 已预编译**；真实代价是 200~260 ms；
5. 内部堆"104~120 KB" → 是"不开 Wi-Fi"口径，**当前固件开机开 AP**，真实起点需 S0 复核；
6. `s_photo_frame_off` / `s_photo_next_load_ms` 是死变量，别当"预读框架已存在"。

### 16.3 与其它文档

- `wifi-upload-postmortem.md` 的结论**仍成立**（Wi-Fi 不划算），但要补两条：
  ① 当前固件仍开机开 AP（应删）；② 内部 RAM 里约 90 KB 是**应用侧**可搬 PSRAM 的，不能一句"PSRAM 帮不上忙"带过；
- `photo-gif-design.md` 的"BLE 不能传图"结论**作废**（§5.1 已纠错），其余（`.pgi` 格式、烧屏、轮播）继续有效；
- `docs/ble.md` 新增 §照片服务 协议章节（P5 落）。

## 17. 明确不做

| 不做 | 原因 |
|------|------|
| Wi-Fi 上传（HTTP/UDP/TFTP） | 内部 RAM 根因 + 热点三连坑 + 用户明确"只用蓝牙"；**仅 S1 失败时作为退路** |
| L2CAP CoC | iPhone 实测 28 KB/s，无收益；要重建库 |
| 提高 MTU | iOS 上限 185，无 API |
| USB CDC / MFi | iOS App 不能打开任意串口 |
| 云端中转 | 荒谬（本地 0.1 s 的事） |
| 设备端解码 GIF/PNG/WebP/视频 | 软解太慢；只解 JPEG（静态）与索引帧（动图） |
| 照片进应用分区 Flash | 只有 678 KiB；要进 Flash 必须用 `ffat` 分区（P6） |
| 照片叠加时钟/速度 | 用户明确要纯照片 |
| 照片排序/相册分组 | v1 不做（文件名即顺序） |
| 后台长传输保活 | v1 不做（前台 + 续传足够） |
| PSRAM 超频到 120 MHz 提速 | 官方：八线 120 MHz 实验特性，温差 ~20 ℃ 会随机崩，车载不可接受 |
