# 红绿灯功能调研（2026-10-16）

> **问题**：能否给仪表加"红绿灯"功能？是不是只能用高德 SDK？

## 一、结论速览

| 能力 | Web API（现用） | iOS 驾车导航 SDK | iOS 两轮车 SDK | **RTOS SDK**（智能手表/眼镜）|
|------|:---:|:---:|:---:|:---:|
| 路线 / 转向 | ✅ | ✅ | ✅ | ✅ |
| **本路线红绿灯数量** | ✅ **已实测可用** | — | — | ✅ |
| 红绿灯**位置** | ❌ | ❌ | ❌ | — |
| **信号灯相位 + 读秒** | ❌ | ❌ | ✅ | ✅ |

**四条要点**：

1. **倒计时确实存在，但不在 iOS 驾车 SDK 里** —— 我们逐条读完了
   `AMapNaviDriveDataRepresentable` 协议的**全部**回调（路口放大图、车道、
   电子眼、服务区、拥堵区域、转向图标、平行道路…），**没有红绿灯**。
   倒计时在**两轮车 SDK** 与 **RTOS SDK**（嵌入式 C 静态库）里。
2. **Web API 有一个被忽略的可用字段**：驾车路线响应带 `traffic_lights`
   （本路线红绿灯**数量**），我们此前没接。
3. **"智能手表方案"= RTOS SDK，是给嵌入式固件用的 C 库**（不是手机 SDK）。
   它把整套导航搬到**设备侧**，含红绿灯读秒；但对我们是"把 ESP32 变成
   完整导航仪"，工程量大一个量级，且**个人认证的智能硬件配额为 0**。
4. **用倒计时的代价不是"多接一个 API"，而是换掉自研导航核心** —— 见 §四。

## 二、各来源的实测结果

### 2.1 驾车路线 API：带红绿灯数量（本次新发现）

实测三次（网关真实 Key）：

| 路线 | 距离 | 红绿灯数 |
|------|------|---------|
| 上海 人民广场 → 静安寺 | 5619 m | **10** |
| 上海 市区短途 | 3369 m | **11** |
| 北京 国贸 → 天安门 | 5888 m | **10** |

响应里 `route.paths[0]` 的字段为：

```
distance, duration, strategy, tolls, toll_distance, steps, restriction, traffic_lights
```

**限制**：`traffic_lights` 是**路径级总数**，`steps[]` 里**没有**该字段
（单段字段只有 `instruction/orientation/road/distance/tolls/toll_distance/
toll_road/duration/polyline/action/assistant_action`）。
所以**能知道"这一趟要过 10 个灯"，但不知道"灯在第几个路口"**。

### 2.2 交通态势 API：能给出"哪条路在堵 + 平均车速"

实测（上海人民广场周边 500m）：

```
总体: 缓行 | 轻度拥堵 | 路段数: 50
  西藏南路 | 拥堵 | 车速 5 km/h  | 长 253m
  普安路   | 拥堵 | 车速 10 km/h | 长 197m
  人民路   | 缓行 | 车速 15 km/h | 长 624m
```

**要点**：返回的是**拥堵等级 + 平均车速**，**不是**信号灯状态。
但"车速 5 km/h 且状态=拥堵"在城市路口**极可能正在等红灯** —— 这是可用的旁证。

### 2.3 高德的倒计时到底是什么

据[四川观察报道（引高德官方）](https://www.sctv.com/news/2057098417707081730)：

- **不是**接交警信号灯数据，而是 **AI 大模型预测**（历史交通数据 + 实时车流 + 路口信号规律）
- 覆盖：**中国大陆及港澳台，近 50 万个红绿灯路口**（2022 年 5 月上线）
- 驾车/骑行/步行/巡航模式下，经过支持的路口都会显示
- 车流大时还会提示"需要等几轮红灯"

**准确率不是 100%**：有[用户实测误差超 10 秒](https://post.smzdm.com/p/a95elq27/)的报道。
对导航来说够用，但**不能当作可依赖的安全信息**（这影响 §五的设计取舍）。

### 2.4 SDK 侧的硬约束（关键）

| 项 | 说明 |
|---|---|
| 红绿灯在哪个 SDK | iOS **两轮车**导航 SDK（V11.1.050 起支持绿/黄灯状态）；**RTOS SDK** 的 `awk_navi_traffic_signal_info_t`（`status` + `remain_time`） |
| 认证要求 | 个人认证可申请 SDK，但**智能硬件/商用分发**通常需**企业认证 + 技术服务许可**（商业授权）—— 需向高德商务确认 |
| Key 位置 | SDK 必须把 Key **打包进 App**（我们现在是 Key 只在网关，安全边界更弱） |
| 缓存 | 高德协议 §3.5 **禁止缓存其数据**，红绿灯是实时数据，**离线不可用** |

## 三、为什么"接 SDK"对我们代价很大

现在的链路是**自研导航核心**：

```
iPhone 定位 → 网关(高德 Web API 算路) → NavCore 自算进度/偏航/到达 → BLE → ESP32 画图
```

红绿灯倒计时**只在 SDK 的导航过程中产生**（它要自己算路、自己跟车、自己判断
"前方这个灯是哪个"）。要用它，就得把整条链路换成：

```
iPhone 定位 → 高德 SDK 算路 + 导航引擎 → 回调拿红绿灯 → 转成我们的协议 → BLE → ESP32
```

**代价**：
- `NavCore`（156 项测试的偏航重算 / 进度 / 到达判定）被架空或大改
- 网关的算路、多方案、地图窗口**全部要重新评估**
- 协议要扩展（红绿灯字段要过 BLE，注意 MTU）
- 需企业认证 + 可能的商业授权

## 三·补、智能手表 / 智能眼镜方案（2026-10-16 补充调研）

高德把"智能手表"与"智能眼镜"合称 **AIoT 方案**，含三个 SDK：

| SDK | 作用 | 与我们的关系 |
|-----|------|-------------|
| Agent SDK | AI 意图识别 | 无关 |
| Link SDK | 与高德地图 **App** 建联（IPC） | ⚠️ 见下 |
| **RTOS SDK** | **屏显组件**：智能设备上的地图/导航（C 静态库） | ⭐ **红绿灯在这里** |

### 关键发现：RTOS SDK 是给**嵌入式固件**用的 C 静态库

这不是"手机上的 SDK"，而是**直接链进设备固件**的 C 库：

- 以 **C 语言静态库**发布，只暴露 C 头文件
- 目标平台是 **RTOS 手表芯片**（SiFli、杰理、聚芯、拓步、小牛…）与 **RTOS 眼镜**（rtosglass / Rokid）
- **不依赖完整 libc / 文件系统 / 图形栈** —— 全部通过 adapter 由厂商注入
- 单线程模型，`awk_init` 在哪个线程调用，后续 API 就必须在该线程
- 需要 `awk_activate_device()` **设备激活**（`device_id` + 智能硬件 key）

### 红绿灯的完整 API（RTOS SDK）

`awk_navi_view_callback_t` 里有两个相关回调：

```c
void (*update_traffic_signal)(awk_navi_traffic_signal_info_component);
void (*update_traffic_light_num)(awk_navi_traffic_num_component);
```

而 `awk_navi_traffic_signal_info_t` 的字段是：

```c
int32_t  status;       // 红绿灯状态
uint64_t remain_time;  // 倒计时剩余时间
char    *extData;      // 扩展字段
```

同协议还含：剩余距离/时间、光柱图（拥堵）、导航信息卡片、车道线、
**后方来车提醒**、速度、北向上 —— 是一整套**面向小屏的导航数据**。

### 对我们的意义（重要）

RTOS SDK 提供了**第三条路**，而且比"两轮车 SDK"更贴近我们的形态：

| | 现在（我们的架构）| 换 RTOS SDK |
|---|---|---|
| 谁算路/画图 | iPhone 算 → BLE → **ESP32 画** | **ESP32 自己**算路 + 画图 |
| iPhone 角色 | 定位 + 网关 + 导航核心 | 可能只剩定位 |
| 红绿灯 | ❌ | ✅ 相位 + 读秒 |
| 网关 | 核心 | 可能不再需要 |

**但代价是"把 ESP32 变成一台完整导航仪"**：要移植 C 静态库、实现
render/file/memory/network/thread/system 一整套 adapter、处理瓦片缓存
与离线地图目录……这比现有的"自绘地图窗口"（`nav_map.c`）工程量大一个量级。

**且 `device_id` + 设备激活意味着走"智能硬件"计费口径** —— 见下。

### 许可与费用（本次查到的硬约束）

高德 AIoT SDK 概述页写明：

> **法人或非法人组织**使用平台服务应事先购买**技术服务许可**以获取许可。
> 若未购买，平台提供的 KEY 与配额**仅供短期、少量的测试目的**。
> 超出范围（向第三方/公众提供应用、上架分发、收费或发布广告、组织内部上线运营、
> 长期或大量调用）构成**未许可使用**。

定价页（`/upgrade#business`）给出的官方数据：

| 服务 | 个人认证（非商业）| 企业认证（非商业）| 企业认证 + 技术服务许可 |
|------|------|------|------|
| 基础 LBS（含路径规划） | 15 万次/月 | 300 万次/月 | 900 万次/月 |
| 基础搜索 | 5,000 次/月 | 5 万次/月 | 50 万次/月 |
| 基础地图定位 | 150 万次/月 | 3,000 万次/月 | 9,000 万次/月 |
| 天气预报 | 5,000 次/月 | 5,000 次/月 | 900 万次/月 |
| **智能硬件定位** | **0 次/月** | 5,000 次/月 | 900 万次/月 |

**注意"智能硬件定位"给个人认证是 0 次/月** —— 这是个信号：**智能硬件方向
基本不面向个人开发者**。

超出配额的价格：基础 LBS **30 元/万次**、基础地图定位 3 元/万次、
智能硬件定位 30 元/万次。

### 自查结论

对我们这个**自用**项目：

- 目前的 Web API 用法（网关 + 个人 Key）属于"非商业目的的个人认证开发者"，
  月配额 15 万次/基础 LBS + 5,000 次搜索 —— 按我们现在的用量（`/health`
  可查，日常个位数）**远远够用**。
- 一旦改用 RTOS SDK（智能硬件口径），就落入"智能硬件定位"与 AIoT 许可范畴，
  **个人认证配额为 0**，且需购买技术服务许可。**这条路对个人基本关闭。**

## 四、可行方案对比

| 方案 | 能得到什么 | 成本 | 依赖 |
|------|-----------|------|------|
| **A. 路线红绿灯计数** | "本趟要过 10 个灯"（数字） | **低**（网关已有该字段，只需透传 + 上屏）| 无新增 |
| **B. 拥堵近似"前方红灯"** | "前方 300m 可能吃红灯"（提示）| **中**（已有 `/traffic`，需按路线匹配）| 无新增 |
| **C. 两轮车 SDK 倒计时** | 真正的读秒（手机侧）| **高**（换导航核心 + 企业认证）| 企业认证/商业授权 |
| **D. RTOS SDK 上 ESP32** | 读秒 + 整套小屏导航（**设备自算**）| **很高**（移植 C 库 + 全套 adapter）| 智能硬件许可（个人配额 0）|

### 关于 A 的实际价值

诚实说：**"要过 10 个灯"对驾驶帮助有限** —— 不像倒计时那样可行动。
它更适合做**路线选择的参考**（"这条路 10 个灯，那条 3 个灯"），
而不是行车中的实时提示。

### 关于 B 的可行性（我认为最值得先做）

把已有的 `/traffic`（拥堵 + 车速）与**当前路线**结合：

- 沿路线前方采样 → 若某段"拥堵且车速 < 10 km/h" → 提示"前方可能红灯"
- **零新增 API、零架构改动**，只是把已有数据在合适位置呈现
- 缺点：**分不清"等红灯"与"真堵车"**；且 `/traffic` 是 60 秒节流的展示信息

## 五、建议

**先做 B（低成本验证需求），A 可选；C / D 暂不做。**

理由：

1. **C 的代价与收益不成比例** —— 为"读秒"换掉带 156 项测试的导航核心，
   还要企业认证；而这个功能**准确率并非 100%**（已有误差 >10s 的实测），
   对"辅助仪表"来说不值得。
2. **D（RTOS SDK）工程量大一个量级**，且走智能硬件计费口径 ——
   **个人认证的"智能硬件定位"配额是 0**，必须先买技术服务许可。
   对个人自用项目基本关闭。
3. **B 能回答关键问题**：驾驶员到底需不需要"前方有红灯"这个信息？
   需要的话再考虑为读秒付出更大代价。
4. 若将来真要做 C/D，第一步不是写代码，而是**先向高德商务确认
   资质与费用**（个人能否用、要企业认证吗、多少钱）——拿不到就免谈。

### 若决定走 C（两轮车 SDK），需先确认

- [ ] 红绿灯能力**是否需要企业认证 + 技术服务许可**？费用？
- [ ] 个人开发者账号能否调用？（按"智能硬件定位配额=0"推测：不行）
- [ ] 是否接受把高德 Key 放进 App 二进制
- [ ] `NavCore` 是替换还是与 SDK 并存（并存会有两套进度判定，容易打架）
- [ ] 红绿灯字段经 BLE 传给 ESP32 的协议设计（注意 MTU 与 2Hz 节奏）

### 若决定走 D（RTOS SDK 上 ESP32），需先确认

- [ ] SDK 是否支持 ESP32-S3 平台（文档只列了 SiFli / 杰理 / 聚芯 / 拓步 / 小牛）
- [ ] 需要实现哪些 adapter（render / file / memory / network / thread / system）
- [ ] Flash 与 RAM 预算（我们 Flash 已 **60%**，PSRAM 要留给全帧缓冲）
- [ ] 设备激活（`awk_activate_device`）的计费与许可
- [ ] 与现有 `nav_map.c` 自绘地图的关系（替换还是并存）
